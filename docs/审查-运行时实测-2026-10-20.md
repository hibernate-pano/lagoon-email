## R-01 · `accounts.id` 与所有子表的 `account_id` 编码不一致 —— 用户被迫重连的真正原因（P0）

**文件**：`Sources/LagoonServer/Storage/AccountStore.swift`（`upsert` / `find(byId:)`）、`Sources/LagoonKit/LagoonDatabase.swift`（schema）

### 实测证据（用户真实库 `~/Library/Application Support/Lagoon/lagoon.sqlite`）

```
$ sqlite3 lagoon.sqlite "SELECT CAST(id AS TEXT), length(id) FROM accounts;"
f5661697-5dee-4711-b061-311c59cef84f|36        ← accounts.id：36 字节（UUID 的 UTF-8 文本）

$ sqlite3 lagoon.sqlite "SELECT hex(account_id) FROM message_headers LIMIT 1;"
F56616975DEE4711B061311C59CEF84F                ← 子表：16 字节（二进制 UUID）

$ sqlite3 lagoon.sqlite "PRAGMA foreign_key_check;" | wc -l
727                                              ← 727 条外键违规
```

同一个 UUID，两种编码。`accounts.id` 是**被指向的那一行**，却是唯一编码不同的。

### 因果链（逐环实测）

1. 客户端 Keychain 里的 accountId = `F5661697-5DEE-4711-B061-311C59CEF84F`（16 字节形式）
2. `AccountStore.find(byId:)` 执行 `WHERE id = ?`，参数是 16 字节
3. `accounts.id` 存的是 36 字符文本 → **WHERE 永远不匹配**
4. 账号查不到 → 同步失败 → `sync_status = 'needsReconnect'`（真实库里此刻就是这个值）
5. 用户看到「QQ 授权码失效，请重新连接」——**这是假的**。授权码可能完全有效。

### 附带的第二个伤害

`ON DELETE CASCADE` 因外键不匹配而**从未生效**：删账号会留下 356 条 message_headers、
246 条 ai_actions、124 条 advice、200 条 usage_log 变成孤儿行。README 的 "Known limitations"
里承认过"FK 指向 accounts，所以 SQLite 不会级联它们"——但没人意识到这个状态**正在损坏用户的库**。

### 来源判定

- 旧备份 `lagoon.sqlite.pre-v3.2.0-20261006-131609.bak`：`accounts.id` 是 16 字节，**外键违规 0 条**
- 当前库：36 字符文本，**727 条违规**
- 行的 `created_at` = 2026-09-29

⇒ 是**旧版本写坏了**，且**当前代码写的是 16 字节**（`upsert` 传 `account.id: UUID`，GRDB 默认编码）。
所以**全新安装无此问题，只有升级安装中招**——这正是它能一直躲过代码审查的原因。

### 修法方向

新增迁移把 `accounts.id` 归一化到 16 字节形式。**方向必须先验证**：子表已经引用 16 字节形式，
所以应当把父行改成与子行一致（而不是反过来）。迁移必须幂等、必须不丢凭据，
修完 `PRAGMA foreign_key_check` 必须为 0 条，删账号必须真的级联。

## R-02 · 重建 bundle 后 Keychain 读无限阻塞 —— App 停在启动画面（P0）

**文件**：`Sources/Lagoon/Services/KeychainStore.swift`、`Sources/Lagoon/Services/EmbeddedServer.swift:41`

### 实测证据

```
$ open dist/Lagoon.app && sleep 8
$ lsof -nP -iTCP -sTCP:LISTEN | grep Lagoon      ← 无输出：服务器根本没绑端口
$ ps -o pid,etime -p <pid>                       ← 进程活着，主线程健康
$ sample <pid> 1 -mayDie | grep SecItemCopyMatching
  + partial apply for closure #1 in static EmbeddedServer.migrateLegacyEnvIfNeeded()
  +   KeychainStore.loadString(service:)
  +     SecItemCopyMatching
  +       ... CSSM_DecryptDataFinal ... mach_msg2_trap    ← 无限等待
```

`SecurityAgent` 进程在跑但**窗口数为 0**——用户本该看到的授权对话框从未出现。

### 根因

`KeychainStore` 用的是**旧式 file-based keychain**（`login.keychain-db`），条目没有
`kSecAttrAccessControl`，靠 `acct=primary` 绑定**创建它的可执行文件**。
App 是 ad-hoc 签名的（`scripts/build-app.sh` 注明：用 personal-team 证书会被 XProtect 判为恶意软件），
**每次重建都换 cdhash** ⇒ 旧条目的 ACL 不再匹配 ⇒ macOS 要求授权 ⇒
`SecItemCopyMatching` 在 `mach_msg2_trap` 里**永久等待**。

`EmbeddedServer.bootstrap()` 在**绑定端口之前** await 一次 Keychain 读 ⇒
一次阻塞 = 服务器永不监听 = App 停在「服务器启动中」。

命令行同样复现：`security find-generic-password -s lagoon.envJSON -g` 也挂住。

### 为什么这是产品缺陷而不仅是环境问题

ad-hoc 签名是**当前的发布形态**（`README` 的 Known limitations 承认分发需要 Developer ID 签名），
所以**任何一次重新构建都会让用户撞上这个挂起**。而且挂起时：
- 界面只有一个不解释的转圈
- 没有超时、没有「钥匙串在等待授权」的提示、没有可点的下一步

⇒ 修法不只是换 keychain API（data-protection keychain，旧值需复制/验证/再删），
更要保证**端口绑定不被 Keychain 阻塞**，且阻塞时**用户看得见、点得动**。

## R-03 · 提醒功能承诺了「到点会通知你」，但通知开关默认关闭且失败静默（P1）

**文件**：`Sources/Lagoon/Localization/L10n.swift`（`reminderHelp` / `reminderEmptyHelp`）、
`Sources/Lagoon/Views/SettingsView.swift:40`、`Sources/Lagoon/Platform/MailNotificationService.swift:145`、
`Sources/Lagoon/Platform/ReminderScheduler.swift:42`

### 实测证据

- 文案承诺：「你设的提醒会在到点时通知你。」「到点时系统会通知你。」
- `notificationsEnabled` 默认 **`false`**（SettingsView.swift:40）
- `scheduleReminder` 首行 `guard isEnabled, canPost, Self.hasBundle else { return }`
  ⇒ 通知开关关着时**静默返回**，提醒**永远不会响**
- `ReminderSheet.save()` 调完 `scheduleReminder` 就 `dismiss()`，用户看到「设好了」
- `ReminderScheduler.lastError` 被 `@Published` 出来，类注释写着
  "it must not be silent"——但 `grep -rn "lastError" Sources/Lagoon/ | grep -v ReminderScheduler`
  **零命中**：没有任何视图读它

### 用户体验

设提醒 → App 说「设好了」→ 到点时什么都没有，没有通知、没有解释。

⇒ 要么在设提醒时一并取得通知授权并说明，要么明说「提醒已保存但不会通知你去开通知」。
两条文案必须和行为一致。

## R-04 · `migrateLegacyEnvIfNeeded` 会用 `"{}"` 覆盖读不到的环境变量（P1）

**文件**：`Sources/Lagoon/Services/EmbeddedServer.swift:186-198`

`try? KeychainStore.loadString(service: envService)` 把**读失败**和**条目不存在**压成同一个结果
（`alreadyMigrated == false`）。于是读失败时会走迁移分支，`.env` 读不到就
`saveString("{}", service: envService)` —— **把用户的 AI 密钥配置覆盖成空**。

密钥配置在 Keychain 里（`lagoon.envJSON`），一次读失败（正是 R-02 会造成的那种失败）
就足以清空它。用户会表现为「AI 配好了但一直没生效，且重填也留不住」。

⇒ 读失败必须与"不存在"区分：失败时**不写**，并把失败报出来。

## R-05 · AI 回复草稿以明文存储，而文档承诺「邮件正文是密文的」（P1）

**文件**：`Sources/LagoonServer/Storage/AIActionStore.swift:917`、`Sources/LagoonServer/Routes/DraftRoutes.swift`

### 实测证据（用户真实库）

```
$ sqlite3 lagoon.sqlite "SELECT substr(variants,1,300) FROM draft_replies;"

["Hi Danielle，\n\n感谢跟进，我会查看链接并评估接入事宜，如有进展再与你同步。\n\npanbo-studio",
 "Hi Danielle，\n\n谢谢再次跟进！看了一下你们提到的分成方案，挺有意思的。…",
 "Danielle 您好，\n\n感谢您的再次来信。关于贵方提出的开源维护者合作方案，我方目前仍在评估阶段…"]
```

写入路径确认无加密：`INSERT INTO draft_replies (account_id, remote_id, variants) VALUES (?, ?, ?)`，
参数是原始 JSON 数组，全程没有 `BodyCipher`。

### 为什么这算泄露

草稿是**根据邮件正文生成的**，内容就是别人邮件的实质（"关于贵方提出的开源维护者合作方案"）。
`docs/使用说明.md` 的表格明确列了「邮件正文 → 密文」和「哪些是明文（发件人/主题/时间/附件名）」，
但**草稿是第三类东西，两边都没提**，而它是可读的。

用户按文档理解「备份文件里正文是密文的」，把 .sqlite 拷到 U 盘或网盘——草稿就跟着走了。

### 全表扫描结论

逐列检查了所有表的 TEXT 列，除 `draft_replies.variants` 外没有第二处漏网：

| 列 | 内容 | 判定 |
|---|---|---|
| `message_bodies.body_cipher` / `body_html_cipher` / `message_headers.snippet_cipher` | 正文/预览 | 已密文 ✓ |
| `draft_replies.variants` | **AI 草稿正文** | **明文 ✗** |
| `message_bodies.attachments` / `to_addresses` / `cc_addresses` | 附件名、收件/抄送地址 | 文档已声明为明文 ✓ |
| `ai_actions.payload` | 操作元数据（remoteId、状态） | 不含正文 ✓ |
| `ai_overrides.from_group` / `to_group` | 分组名 | 不含正文 ✓ |

## R-06 · 四处架构注释与现状不符（P3）

**文件**：`Sources/LagoonKit/ConnectedAccount.swift:6`、`Sources/Lagoon/Services/APIClient.swift:211`、
`Sources/Lagoon/Views/ConnectView.swift:6`、`Sources/Lagoon/Localization/L10n.swift:17`

## 本轮的方法论

前两轮审查（读代码）产出的是 P1/P2 级的体验与健壮性问题。本轮（跑起来 + 查真实数据）产出的是
**两个 P0**——而且这两个 P0 都不是"代码写错了"，是"代码在真实环境下不成立"。

| 证据类型 | 能发现什么 | 本轮的例子 |
|---|---|---|
| 读源码 | 体验不一致、措辞撒谎、并发写法可疑 | P1/P2 清单 |
| 查真实数据库 | 编码不一致、级联失效、约束被绕过 | R-01（727 条外键违规） |
| 跑真实进程 | 阻塞、挂起、端口不绑 | R-02（无限等 Keychain） |
| 读文案 vs 读代码 | 承诺与行为不符 | R-03、R-04 |

⇒ 结论：**「构建通过 + 测试全绿 + 读代码审过」三者同时成立，仍然不足以说明产品能用。**
必须加上「在真实数据上跑过」这一条。
