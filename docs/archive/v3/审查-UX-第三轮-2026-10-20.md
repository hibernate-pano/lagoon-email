- **触发条件**：打开搜索面板（⌘F），输入任意关键词，在服务器不可达或请求超时时按搜索。`run()` 进入 `catch`，把 `results` 清空并挂上错误横幅；因为 `hasSearched = true` 且 `results.isEmpty`，结果区随即渲染"没找到匹配邮件 / 换个更短的关键词试试"。错误横幅由 `.noticeBanner($errorBanner)`（SearchSheet.swift:273）挂在最顶部，于是**同一屏同时出现"搜索失败，请检查网络后重试"和"没找到匹配邮件"**。

  对照组：`BriefingFeedView.swift:437` 的 `else if errorBanner != nil { errorState }` 正确地把"失败"和"空"分开——同一个 app 里两种写法，说明这不是设计意图，是漏改。
- **建议修法**：把错误态与空结果态分开。加一个 `searchFailed: Bool`（或直接用 `errorBanner != nil` 作为分支条件），失败时结果区改渲染 `ContentUnavailableView(l10n.searchFailedTitle, systemImage: "exclamationmark.triangle", description: Text(l10n.searchFailedDetail))`，**不要**渲染 `noResults` / `emptySearchHint`。
- **验证方式**：断网 → ⌘F → 输入 "invoice" → 搜索。断言：屏幕上不出现"没找到匹配邮件"，出现的是失败态 + 重试。

### U3-02 简报页同步出错时永远显示"正在首次同步邮箱…"，用户看不到错误

- **文件:行**：`Sources/Lagoon/Views/BriefingFeedView.swift:638-666`（`emptyState`）、`Sources/LagoonServer/Sync/SyncEngine.swift:304` 与 `:319`（健康状态写入）
- **代码**：

  ```swift
              } description: {

              }
          }
      }
      .frame(maxWidth: .infinity, maxHeight: .infinity)
  }
  ```
  ```swift
  // SyncEngine.swift:304
  health: SyncHealth(status: .needsReconnect, lastSyncAt: nil, lastError: label),
  // SyncEngine.swift:319
  health: SyncHealth(status: consecutiveFailures >= 3 ? .degraded : .error,
                     lastSyncAt: nil, lastError: label)
  ```
- **触发条件**：连接账号后，让同步失败（断开网络 / QQ 授权码失效）。服务端两种失败路径写入的健康状态都带 `lastSyncAt: nil`。于是客户端 `directory.active?.syncHealth.lastSyncAt == nil` 成立 → 走 `if` 分支 → 无限 `ProgressView` + "正在首次同步邮箱…"。
- **为什么是问题**：三重问题。
  1. **死路**：转圈永不结束，用户等不到任何结论。
  2. **"已同步"的反面谎言**：文案说"正在首次同步"，但真相是同步**失败了**。而且 `lastSyncAt` 在失败时为 nil，在"还没同步过"时也为 nil——**这两种状态在代码里无法区分**，所以界面必然把失败说成"进行中"。
  3. **"首次"是假的**：用户可能已经用过这个账号很久，只是一轮失败把它重置成了"首次"。
  另注意：`RootView.syncHealthBanner`（RootView.swift:872-909）确实会为 `.needsReconnect` / `.degraded` / `.error` 挂一条横幅，但那条横幅说的是"同步不稳定/需要重新连接"，与下面的"正在首次同步"**互相矛盾**，用户无法判断哪个是真的。
- **建议修法**：`lastSyncAt == nil` 这个判据不能区分"从未同步"和"同步失败"。改成以 `syncHealth.status` 为准：
  - `status == .ok && lastSyncAt == nil` → 才显示"正在首次同步"。
  - `status != .ok` → 显示一个失败态（`ContentUnavailableView` + 状态文案 + 一个"重试"按钮），不要再显示转圈。
  - 更彻底的做法是在服务端把 `lastSyncAt` 改成"最后一次尝试时间"而非"最后一次成功时间"，让"从未同步"和"同步失败"在数据层就可区分。
- **验证方式**：连上账号 → 等到有一封邮件 → 断网 → 点"获取新邮件"（⇧⌘N）→ 观察简报页。断言：不出现转圈，出现可重试的失败态。

- **触发条件**：`RootView` 用 ZStack 同时挂载简报页与收件箱页（RootView.swift:495-501），隐藏的一侧只是 `opacity(0) + disabled + allowsHitTesting(false) + accessibilityHidden`。
  **关键在于这个 `.disabled` 的作用范围**：它挂在 `BriefingFeedView` 之上，是**父视图**对子视图树的禁用。而 ⇧⌘K 的按钮在 `headerBar` 里（BriefingFeedView.swift:193 → :366 → :378），是 `BriefingFeedView` 的**内容**。SwiftUI 的 `disabled` 环境值**会向下传播**，因此这一处 ⇧⌘K 事实上是被父级的 `.disabled(surface != .briefing)` 挡住的。
  **但这不是可靠的保障**，理由有三条：
  1. **同文件的同层兄弟全部显式写了 `.disabled(!isVisible)`**：`groupJumpShortcuts`（:811）、`keyboardNavigationShortcuts`（:823 / :826 / :838 / :858 / :867）。这些快捷键被放在 `.background` 层里（BriefingFeedView.swift:815 / :869 的 `groupJumpShortcuts` 与 `keyboardNavigationShortcuts` 都是 `VStack{...}.frame(width:0,height:0)` 挂在 `.background` 上），而**代码注释明确写着**：「`.background` 是兄弟图层，RootView 给整个界面加的 `.disabled()` 到不了这里——没有这道门，隐藏的简报页仍然会响应 ⌘A」（BriefingFeedView.swift:854-856；MessageListView.swift:790-793 同样写着「`.background` is a sibling layer, so the `.disabled()` RootView applies to the surface never reaches here」）。
  2. 也就是说，**项目自己已经确认了父级 `.disabled` 不会到达 `.background` 里的快捷键**。⇧⌘K 的按钮今天恰好不在 `.background` 里（在内容层的 `headerBar` 中），所以今天被挡住了——**但这是位置带来的巧合，不是设计**。任何人把 `headerBar` 里的按钮挪进 `.background`（就像 ⌘1–⌘5 那样，为了避开别的冲突），或者把 ⇧⌘K 改成零宽背景按钮（这正是 `keyboardNavigationShortcuts` 的写法，也是这个 app 里所有列表快捷键的统一写法），这道门就消失了。
  3. **测试没有钉住它**：`SurfaceShortcutOwnershipTests.sharedKeys` 列出的是 j / k / ⌘[ / ⌘A / ⌘⌫ 五个键，**不含 ⇧⌘K**。这个键是唯一绑定在**可见的 headerBar 按钮**上、而不是零宽背景按钮上的列表快捷键——所以它也是唯一没有 `.disabled(!isVisible)` 的那一个。
- **为什么是问题**：把"安全"寄托在"这个按钮恰好不在 `.background` 里"上，是这个项目已经吃过两次亏的做法（`.memory/toolbar-items-escape-hidden-zstack-surfaces` 记录的 toolbar 项逃逸，以及 `MessageDetailView.swift:153-168` 自述的 `.keyboardShortcut` 逃逸）。一旦失守，后果是**静默的远程写**：标已读是 IMAP 上的 `\Seen` 写入，在别的客户端也看得见，用户无法撤销"为什么这 50 封突然变成已读了"，而他当前正看着的收件箱列表一行都没动。
  同时，快捷键表（ShortcutsSheet.swift:101）把它标为 `scope: .briefing`（"仅简报"），而 cheatsheet 自己的文档注释（ShortcutsSheet.swift:10-16）写着：「A row that names a key without saying *where* it applies teaches a gesture that silently does nothing in the wrong surface」——这张表是在给"作用范围"背书，那这个背书就必须由代码保证。
- **建议修法**：给 :387 的按钮加 `.disabled(isMarkingAllRead || items.isEmpty || !isVisible)`，与同文件其他快捷键保持一致。**注意** `.disabled()` 会覆盖而非与环境里的 `disabled` 合成，所以要写成一个 `.disabled(...)` 调用（`SurfaceShortcutOwnershipTests` 的注释明确说明了这一点）。同时把这条绑定补进 `SurfaceShortcutOwnershipTests.sharedKeys` 列表，让门被测试钉住——这样即使将来有人把它挪进 `.background`，CI 也会红。
- **验证方式**：切到收件箱页 → 按 ⇧⌘K → 断言简报页的邮件**没有**变成已读。（今天的代码恰好满足这一条；这条的价值在于把"恰好"变成"必然"，并让测试守住它。）

  于是按钮的实际行为永远是 `onClearLens()` → `RootView.swift:337` → `destination = .allMessages`。

- **为什么是问题**：
  1. **死按钮**：绝大多数页面下点它没有任何效果，且没有 tooltip 解释（`.help(l10n.unreadOnlyHelp)` = "只显示未读邮件"，恰恰描述了一个它并不做的事）。
  2. **语义与行为相反**：图标语言是"这是一个筛选开关"，实际行为是"清除筛选"。两者在语义上是反的——用户看到空心信封图标，预期是"打开未读筛选"，得到的却是"回到收件箱"。

### T-07【P2】撤销之后，"还有 N 条更早的记录"这个数字会**越变越多**

- **文件:行**：`Sources/Lagoon/Views/ActionHistorySheet.swift:119-137`（撤销处理）、`:216-219`（`remainingCount`）、`Sources/LagoonServer/Storage/AIActionStore.swift:186-219`（`pageSQL` / `countSQL`）
- **代码**：
  ```swift
  // ActionHistorySheet.swift:126
  actions.removeAll { ids.contains($0.id) }
  // The count is left alone, and that is not an oversight.
  //
  // An undo does not remove a row from the history — the server
  // records an *undo* row for it, so the history still says what
  // Lagoon did. … The total is therefore unchanged, and decrementing
  // it here would make the footer claim fewer older entries than exist.
  ```
  ```swift
  // ActionHistorySheet.swift:216
  private var remainingCount: Int? {
      guard let totalCount else { return nil }
      return max(0, totalCount - actions.count)      // ← actions.count 刚刚少了 1
  }
  ```
  服务端侧（`AIActionStore.swift:205-219`）：`countSQL` 用 `NOT EXISTS (... u.kind = 'undo' ...)` 排除**被撤销的**行，但**保留 undo 行本身**——所以**服务端的总数确实不因一次撤销而变**。
- **触发条件**：面板有 150 条历史里的 100 条，页脚写着"还有 50 条更早的记录"。用户 ⌘Z 撤销一条 → `actions.removeAll` 删掉那一行 → `actions.count` 变成 99 → `remainingCount` 变成 `150 - 99 = 51` → 页脚现在说"**还有 51 条更早的记录**"。
  **一次会话里撤销 5 次，页脚就会比实际多报 5 条。**
- **为什么是问题**：**代码注释对"总数"是对的，对"显示出来的差值"是错的**——显示量是 `totalCount - actions.count`，而 `actions.count` 变了。页脚是一个关于服务端历史的承诺，它开始撒谎。
- **建议修法**：让计数和列表**用同一套口径**。要么撤销后重新读这一页（`guard let ids` 的早退分支**已经是这么做的**），要么单独维护一个 `unloadedRemaining`，**只在服务端告诉客户端时才调整**。
- **测试说明**：`ActionHistoryPanelPagingTests.swift:138-148`（`test_anUndoDoesNotShrinkThePanelCount`）**显式钉死了当前的 `totalCount` 处理**（断言源码里不出现 `totalCount = totalCount.map`）。**这个测试是对的**——它管的是总数。**但它不覆盖 `remainingCount` 这个派生量**，而后者正是用户读到的那个数。
- **验证方式**：撤销一条 → 断言页脚数字**不变**。
