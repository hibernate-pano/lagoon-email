## HB-01【P0】启动即死锁：无窗口、端口不监听

**现象**：`open dist/Lagoon.app` → 进程活着，但 `lsof -nP -iTCP -sTCP:LISTEN` 里
**没有 Lagoon**。App 停在"服务器启动中"，连标题栏都没有。

**实测栈**（`sample <pid> 2`）：

```
1754 main  (in Lagoon)
 + 1754 mach_msg2_trap
   + partial apply for closure #1 in AccountStore.load()  (in Lagoon)
     + static KeychainStore.load(service:)  (in Lagoon)
       + SecItemCopyMatching  (in Security)
         + SecKeychainItemCopyContent
           + Security::KeychainCore::ItemImpl::getContent(...)
             + mach_msg2_trap
```

**根因**：ad-hoc 签名 → 每次重建 cdhash 变 → 文件钥匙串条目的 ACL 不再匹配 →
macOS 要用户点"允许"，而弹窗由后台 `SecurityAgent` 承接（无可见窗口）→
`SecItemCopyMatching` 在 `mach_msg2_trap` **无限等待**。

**代码层面的结论**：当前源码**已经**修好了这一条——
`Sources/Lagoon/Models/AccountStore.swift:89` 用的是有界的 `KeychainReader.readString`
（5 秒截止 + 属性探针兜底），而 `KeychainReader.swift` 是 **10-21 那次快照才新增的**
（`git cat-file -e 24b3152^:...KeychainReader.swift` → 不存在）。

**所以：不是代码没修，是产物没重建。** 用户现在手上的 `dist/Lagoon.app` 仍然是会死的。

**分派**：
- fix-runtime：确认源码侧的修复完整（含 `EmbeddedServer.bootstrap` 的那条 await）。
- **中枢**：交付前重建 bundle 并实测（端口监听 + 截图 + 真实打开一封邮件）。

## HB-02【P0】界面在撒谎：把"这个构建读不到钥匙串"报成"授权码要过期"

**实测链路**（每一环都验过，不是推断）：

| 环节 | 证据 |
|---|---|
| 钥匙串读不到 | `security find-generic-password -s lagoon.bodyKey` → *not found*；`lagoon.tokenKey` 存在但被 ad-hoc ACL 挡住 |
| 凭据解不开 | `Sources/LagoonServer/IMAP/IMAPProvider.swift:929` → `throw MailError.notConfigured("credentials unreadable")` |
| 标签坍缩 | `MailProvider.swift:289` → `case .notConfigured: return "not-configured"` |
| 同步状态 | `sync_status = needsReconnect`，`last_sync_error = not-configured`（真实库实测） |
| 界面文案 | `RootView.swift:929` → title `healthNeedsReconnect` = **"需要重新连接 —— 重新连接后继续同步。"**，action = `l10n.reconnect` → **直接打开 QQ 授权码表单** |
| 详情文案 | `L10n.swift:656` `reasonNotConfigured` = **"邮箱设置不完整，请重新连接并补全授权信息。"** |

**真相**：授权码可能完全有效。坏的是**这个构建读不到自己的钥匙串**。
用户照着界面去重新输入授权码，**不但没用**，还可能覆盖掉原本可用的凭据。

**为什么这条重要**：README 里已经记过一次同类的谎——
"账号找不到 → 同步失败 → 告诉用户授权码过期 —— **这是个谎**"。
**同一个谎，换了个成因，又活了一次。**

**分派**：
- fix-runtime：`SyncHealth.Status` 增加一个能表达"钥匙串不可读"的状态，
  让横幅说真话、按钮不再指向"重填授权码"。
- fix-copy-i18n：文案层把"需要重新连接"与"邮箱设置不完整"拆开，
  让"内部读不到密钥"与"用户配置缺失"是两种不同的句子。

## HB-03【P0】占位密钥会被装进加密器，而"禁止用占位密钥写入"的开关是死代码

**这是本轮最危险的一条。**

**证据**：

1. `Sources/Lagoon/Services/EmbeddedServer.swift:159-168`：
   内嵌 app 启动时给 runtime 传的是**占位密钥**（全零 32 字节），并置 `usesPlaceholderKeys: true`。
2. `Sources/LagoonServer/Runtime/Runtime.swift:121-136`：
   runtime **无条件**把配置里的 key 装进加密器：
   ```swift
   AccessTokenCipher.keyProvider = { SymmetricKey(data: keyData) }
   BodyCipher.keyProvider       = { SymmetricKey(data: bodyKeyData) }
   ```
3. `usesPlaceholderKeys` **全仓只被赋值、从未被读取**：
   ```
   grep -rn "usesPlaceholderKeys" Sources/
   → EmbeddedServer.swift:167 / Runtime.swift:51,61,70（只有定义与默认值）
   ```

**后果**：钥匙串读失败、或超过 5 秒截止的窗口内，**任何写入**都会用**全零密钥**封存：
重连时封存授权码（`CredentialVault.seal`）、同步时封存正文与摘要（`BodyCipher.seal`）。
真密钥随后装上 → 那些数据**永久不可解**。

**已排除的误判**：我一度怀疑用户那 52 行正文就是用占位密钥封的（那它们还能救回来）。
**实测否定了这个假设**：

```
swift /tmp/lgprobe/dec3.swift → ZERO-KEY FAILED -> authenticationFailure
```

（用 CryptoKit 的 AES-GCM，全零 32 字节作 key，正文与摘要都解不开。）
所以那批数据当初用的是**真密钥**，真密钥已丢。**这不是侥幸，是必须补上的护栏。**

**分派**：fix-data-layer + fix-runtime 联合：
- 让"占位密钥"状态下**拒绝一切写入**（fail-closed），而不是只用来做诊断。
- `usesPlaceholderKeys` 要么被真正消费，要么删掉——**死开关比没有开关更危险**。

## HB-04【P1】历史行里的 `archiveFolder:false` 把归档门关上了

**实测**：真实库 `accounts.capabilities` =
`{"idle":false,"archiveFolder":false,"move":false,"serverSnippet":false}`

解码：`MailCapabilities.swift:110` `decodeIfPresent(Bool.self, "archiveFolder")` →
`.some(false)` → `allowsArchive`（`MailCapabilities.swift:156`）= `archiveFolder != false`
= **false** → **归档会 409 archive-unavailable**。

**README 说**："这些角色字段现在是 `Bool?`，`nil` 表示*未探测*，闸门按**放行**读。"
**类型改了，历史行没改。** 那些 `false` 不是探测出来的，是旧默认值写进去的。

**分派**：fix-data-layer：一条数据迁移（旧的显式 `false` 归一为"未探测"），
或保证重连时强制重新探测并覆盖。

## HB-06【P0】`lagoon.bodyKey` 已丢，52 行正文 + 345 条摘要 + 1 条 AI 草稿是孤儿

**实测**：
- 钥匙串里**没有** `lagoon.bodyKey`（`security find-generic-password` → not found）。
- 库里：`message_bodies` 52 行**全部**是 `lgb1:` 密文；
  `message_headers.snippet_cipher` 356 行中 **345 行**是 `lgb1:`；
  `draft_replies.variants` **1 条**是 `lgb1:`。
- **全零占位密钥解不开**（HB-03 已验证）→ 当初用的是真密钥，真密钥已丢。
- **恢复路径是真的**：事故备份
  `~/Library/Application Support/Lagoon/incidents/2026-10-20-accountid/lagoon.pre-incident.sqlite`
  里 `message_bodies` 表是**旧 schema**（`body_text` 明文列），实测 **52 行全部有明文**，
  356 行 header 齐全。台账说的"随时可执行"属实。

**但护栏还没做**：`EmbeddedServer.swift:278-288` 的 `.missing` 分支会
**生成并写入一把新 body key**。一旦写入，新封存的数据用新 key，旧的永远打不开。

**分派**：fix-data-layer —— 台账 §H 要求的护栏**必须本轮落地**：
启动时若发现库里存在 `lgb1:` 密文、而钥匙串里没有对应 key，
**不得生成新 key**，应提示"正文密钥丢失"并保持只读。

## HB-08【P0】签名身份绑 cdhash —— 每次重建都毁掉用户密钥（免费可解）

**实测**：

```
$ codesign -d -r- dist/Lagoon.app
designated => cdhash H"826d87a028057dd6418fa0bc24795e5dbbb244cf"     ← ad-hoc

$ codesign --force --deep --sign "CF9FB2183018F0D285722AA8A0E301D74DD493E6" <副本>
$ codesign -d -r- <副本>
designated => identifier "com.lagoon.email" and anchor apple generic
  and certificate leaf[subject.CN] = "Apple Development: 362472407@qq.com (8J7TT5DXWD)"
  and certificate 1[field.1.2.840.113635.100.6.2.1] /* exists */    ← 跨重建稳定
```

**含义**：旧式 file-based keychain 的条目 ACL 绑在**创建者的代码签名身份**上。
ad-hoc 的 designated requirement 是 **cdhash** → 每次重建都变 → 旧条目 ACL 永不匹配 → HB-01。
换成**本机已有的免费 "Apple Development" 证书**，requirement 变成 `identifier + 团队` → **跨重建不变**。

**所以这条根因是零成本可解的。** `scripts/build-app.sh` 里"用开发证书会被 XProtect 判为恶意软件"
那条理由需要**重新验证**（本地构建、无 quarantine 属性的 app 与下载来的 app 走的不是同一条 Gatekeeper 路径）。

> 证书消歧：这台机器上两个同名证书，必须用 SHA1 —— `CF9FB2183018F0D285722AA8A0E301D74DD493E6`
> （另一个 `F6C455813BEF9B637DE00929DEED3DB7B08BBE2B`）。用名字签会报 `ambiguous`。

**分派**：fix-keychain-trust（新建域）。

## HB-09【P0】密钥其实没丢 —— `.env` 里有全部原件，AI 现在整个是关的

**实测**：

- `lagoon.envJSON`（钥匙串里的 AI 配置）内容 = **`{}`** —— 空的。
  这就是第三轮运行时审查的 **R-04**（`migrateLegacyEnvIfNeeded` 用 `"{}"` 覆盖读不到的环境变量）
  **已经在用户机器上发生过**。
- 但 `.env` 里 `LLM_PROVIDER_PRIMARY_API_KEY` / `_BASE_URL` / `_MODEL` **都还在**（值未打印，只验存在性）。
- `LAGOON_TOKEN_KEY` 也还在，而且**能解开** `accounts.credentials`：
  中枢用 CryptoKit 实测 `DECRYPT OK`，解出 `["authCode","kind","username"]`。
  → **授权码一直都在，用户根本不需要重新输入授权码。**

**推论**：
1. 界面那句"需要重新连接 / 邮箱设置不完整，请重新连接并补全授权信息" —— **两件事都是假的**：
   授权码有效，配置也完整。
2. **AI 现在整个是关的**（密钥在 `.env`，但钥匙串副本是 `{}`，而 app 只读钥匙串）。
   → 这就是为什么中枢启动 app 时日志是 `AI gateway disabled`。
   **产品的招牌功能（AI 摘要/分类/建议）现在对用户是死的。**
3. 唯一真正丢失的是 **body key**（52 正文 + 345 摘要 + 1 草稿），
   但事故备份里 52 行正文**全是明文**，可恢复。

**分派**：fix-keychain-trust（做恢复工具，在副本上验证）。
