# v4 · 外部版本（Web 前端 + Rust 外壳）—— 理解与方案

> 状态：**待你拍板** · 2026-10-29 · 作者：lead
> 本文只做三件事：把你的想法翻译成可实现的东西、告诉你代价在哪、把需要你决定的四个问题摆出来。
> 目录名用 `v4`（当前产品是 v3.2.0，且 `docs/superpowers/specs/` 里已经有一个被废弃的 “v2 设计稿”，叫 v2 会撞车；改名是一行 git mv）。

---

## 0. 一句话

把 Lagoon 从「SwiftUI 原生外壳 + 进程内 Swift 服务端」改成
**Web 前端 + Rust 外壳（Tauri 2）+ 可替换的后端**；
过渡期由 Rust 外壳带 Swift 服务端当**边车**（sidecar），成熟后再把服务端逐模块迁到 Rust，终局是**一个 Rust 二进制、可跨平台**。

---

## 1. 我理解的你的想法

### 1.1 字面

> 「虽然当前项目计划做成 macOS 原生应用，但我考虑是否可以做一个外部版本，并通过 Rust 进行包装。」

拆成两句：

1. **换壳**：界面不再用 SwiftUI/AppKit 画，改成 Web 技术（HTML/CSS/TS）画，塞进一个原生的 WebView 窗口里 —— 这是“外部版本”的界面含义；
2. **用 Rust 包起来**：进程生命周期、窗口、托盘、通知、单实例、自动更新、安装包，由 Rust 程序负责 —— 这是“包装”的含义。

### 1.2 我的判断：这其实是**三层**改动，代价差一个数量级

| 层 | 具体做什么 | 代码量级 | 周期（1 名熟练开发） | 是不是你真正想要的 |
|---|---|---|---|---|
| **L1 换壳** | Web 前端 + Rust 外层（Tauri 2）：窗口、进程、托盘、通知、快捷键宿主、自动更新、安装包；业务后端原样复用 | Rust 壳 ~2–4k 行 + Web UI ~12–18k 行 | 4–6 周 | 大概率是 |
| **L2 换后端** | 把 20.6k 行 Swift 服务端（IMAP/SMTP/同步/存储/路由）+ 4.3k 行 LagoonKit 重写为 Rust | Rust ~15–20k 行 | 8–12 周（且要重新验证 QQ 边角） | 取决于你要不要跨平台 |
| **L3 换分发** | Developer ID 签名、公证、更新器、DMG/MSI/AppImage、CI 矩阵 | 脚本 + 配置 | 2–3 周 | 若真要对外分发，必须做 |

**分水岭是 L2。** 只做 L1，v4 依然依赖 macOS 和 Swift 工具链，只是换了个皮肤和进程边界；做了 L2，才真正兑现“Rust 版、跨平台、单二进制”。

### 1.3 一个需要先说清楚的反问

这个仓库**已经不需要 Xcode**：`scripts/build-app.sh` 用 SwiftPM 构建 + 手工打 `.app` 包，CI 跑在 `macos-15` 上。所以如果动机只是“摆脱 Xcode / 原生构建太麻烦”，那这件事大概率不值得做。

真正能支撑这次改动的理由只有三个，请你确认命中哪一个：

- **A. 跨平台**：QQ 邮箱的用户大量在 Windows；macOS 原生路线永远到不了他们。
- **B. 外部可达**：同一套前端以后能跑在浏览器里（局域网/远程/多设备），不再是“只在这台 Mac 上”。
- **C. 迭代与验证速度**：Web UI 可以用 Playwright 做自动视觉/交互回归，改样式不需要重编译整个 App，贡献门槛也更低。

如果三个都不是，那我的建议是**不换壳**，把力气花在 v3 的功能与稳定性上（我会直接说）。

## 2. 为什么这个项目**适合**这么改（不是拍脑袋）

现有代码里已经长出了一条真实的“客户端–服务端”缝，这不是我硬造的：

| 事实 | 证据 | 对 v4 的意义 |
|---|---|---|
| 客户端走 HTTP/JSON，带 Bearer token | `Sources/Lagoon/Services/APIClient.swift:1323` | Web 前端可以**原样复用**这份契约，不用碰服务端 |
| 服务端能独立进程运行 | `Sources/LagoonServerCLI/main.swift` | 边车（sidecar）模式天然成立 |
| 服务端密钥可由环境变量注入，不强制读 Keychain | `Sources/LagoonServerCLI/main.swift:21`（`LAGOON_TOKEN_KEY` / `LAGOON_BODY_KEY` / `LAGOON_API_TOKEN`） | **Rust 侧独占 Keychain，Swift 边车零 Keychain 依赖** —— 直接绕开本项目踩过的“临时签名 → Keychain 读挂起”事故 |
| 没有 SSE/WebSocket，是 30s 轮询 | `Sources/Lagoon/Models/PollClock.swift:19,34` | Web 端实现简单；以后加 SSE 是增强不是前置条件 |
| 正文封存格式自描述 | `Sources/LagoonKit/BodyCipher.swift:58`（`lgb1:` + base64(combined)） | 算法上 Rust 能解析同一份密文（§2.3 实测 PASS）；但**密钥拿不到**，所以数据仍要独立（§5.2） |
| HTML 邮件已在沙箱 WKWebView 里渲染 | `Sources/Lagoon/Views/HTMLMessageView.swift:94,147` | Web 端用 sandbox iframe + CSP 等价实现，甚至更简单 |
| 存储是单文件 SQLite（WAL） | `Sources/LagoonKit/LagoonDatabase.swift` | Rust 用 rusqlite/sqlx 直接打开；schema 可以平滑交接 |
| 53k 行测试，含大量路由/行为用例外 | `Tests/LagoonServerTests/` | 迁移的 **oracle**：同一份 golden JSON 可以既跑 Swift 也跑 Rust |

一句话：**缝已经在了，v4 要做的是把这条缝正式变成契约，而不是重新发明架构。**

界面的规模甚至比接口更小：**24 个界面（1 窗口 + 3 栏 + 2 种列表表面 + 1 阅读器 + 23 个面板）对着 57 个端点**；简报页与收件箱页本来就已经由同一个 `SidebarDestination` 派生、同时挂在 ZStack 上（`RootView.swift:143-145,512-518`），Web 端可以合成“一个页面两种模式”。反过来，v1 里**拖放 / 打印 / QuickLook / 原生 NSMenu 全仓 0 处**，这几块没有移植负担。

### 2.1 已经实测过的三件事（本机，2026-10-29）

| 实测 | 命令/证据 | 结论 |
|---|---|---|
| **Swift 服务端能当边车独立跑，且完全不碰 Keychain** | `LAGOON_DB_PATH=/tmp/… LAGOON_SERVER_PORT=18099 LAGOON_TOKEN_KEY=… LAGOON_BODY_KEY=… LAGOON_API_TOKEN=… ./.build/release/LagoonServerCLI` → `/healthz` 200、`/api/accounts` 带 Bearer 200 / 不带 401；临时库自动建出 14 张表 | Rust 壳 ↔ Swift 边车这条链路**今天就能开工**，密钥由 Rust 独占 Keychain、以 stdin/0600 文件传给子进程 |
| **端口 0 会被系统分配** | `LAGOON_SERVER_PORT=0` → 日志 `Server started and listening on 127.0.0.1:50908` | 不必固定 8080：握手先解析这行日志，M1 再给 CLI 加一行结构化握手 `{"port":…,"pid":…}` |
| **SIGTERM 优雅退出** | `kill -TERM` → 进程退出码 0 | 生命周期不需要额外协议，Rust 侧负责 kill + 超时兜底 |

> 顺带一个契约细节：`/api/briefing` 不带 `accountId` 会回 400 `{"error":"malformed-accountId"}` —— 查询参数是必填的。57 个端点的逐字契约现已落盘：`recon/server-contract.md`。

### 2.2 Rust 侧已实测（本机有个好消息）

- **没有完整 Xcode（只有 Command Line Tools）也能构建 Tauri 2 应用。** 用官方 `tauri` 2 + `tauri-build`、前端先放静态文件（不引入打包器），`cargo build` 成功，产出 27.8 MB 的 debug 二进制（`v4/spike/tauri-probe/`）。
- 版本与实证：`tauri 2.12.5` / `tauri-build 2.7.4` / `wry 0.57.1` / `tao 0.37.2`，冷编译 ≈54s；启动后 8s 存活、stderr 0 字节。
- 两个已经踩到的坑（写进 `recon/rust-spike.md`）：① `generate_context!` 硬要求 `icons/icon.png`，缺了就是 proc-macro panic，`bundle.icon=[]` 绕不过；② `externalBin` 的磁盘文件名必须带 target-triple 后缀（`lagoon-server-aarch64-apple-darwin`），而且**不能等于 crate 名**；推荐 Rust 侧直接用 `std::process::Command` 起边车，不用 shell 插件（省掉“前端可调可执行文件”的 capability）。
- 仍未验证：完整打包 / 公证 / 通用二进制（本机没有 rustup，加不了 `x86_64-apple-darwin` target）→ 已进 §6.1 风险台账。

### 2.3 AES-GCM 互通已实测通过（决定「将来能不能继承历史」）

| 用例 | 结果 |
|---|---|
| Rust 加密 → Swift CryptoKit 解密 | **PASS** |
| Swift 加密 → Rust 解密 | **PASS** |
| 中文 + emoji 正文 | **PASS** |
| 空字符串 | **PASS** |
| 篡改 1 bit → 双方都必须拒绝 | **PASS**（Rust `aead::Error` / Swift `authenticationFailure`） |
| 非 `lgb1:` 信封 → 必须拒绝 | **PASS** |

版本：`aes-gcm 0.10.3` / `aead 0.5.2` / `base64 0.22.1`。格式 = `lgb1:` + base64(12B nonce ‖ ciphertext ‖ 16B tag)，与 `Sources/LagoonKit/BodyCipher.swift` 完全一致。
**结论：算法层零风险——但“能解格式”不等于“拿得到钥匙”。** v3 的两个密钥在 data-protection keychain 里，v4 按签名身份被隔离（§5.2 实测 −25300），所以实际路线仍是“v4 重新生成密钥 + 独立数据目录”。这条实测的真正价值是：**将来若要做历史继承，只需要解决密钥交付，不需要重写加密格式。** 证据：`v4/spike/cipher-interop/interop-transcript.log`。

## 3. 四条路线，以及我为什么推荐其中一条

| | 路线 | 终局形态 | 周期 | 主要风险 | 跨平台 | 与 v3 共存 |
|---|---|---|---|---|---|---|
| **①** | **先壳后凿**（推荐）：Rust 壳 + Web UI + Swift 边车 → 再逐模块把后端迁 Rust | 单 Rust 二进制 + Web UI | 4–6 周见效，全部 3–4 个月 | 双进程期长；后端迁移是长跑 | 是（M4 之后） | 完全共存，**各自独立数据目录**（§5.2） |
| ② | 直接 Rust 重写后端 + 新 UI | 同 ①，但一步到位 | 3–4 个月才有第一个可运行版本 | 前期没有任何可用产物；QQ/IMAP 边角（GBK 解码、IDLE、UIDPLUS、归档文件夹角色、幂等发送）会重新踩一遍 | 是 | v3 冻结不动 |
| ③ | 只做 Web 前端，后端永远 Swift | macOS + 浏览器访问 | 2–3 周 | 授权模型要重做（现在 token 是 per-install + 仅 loopback 绑定）；不是“Rust 版” | 否 | 共存 |
| ④ | Electron | — | 2–4 周 | 引入第二个运行时（Node + Rust），体积/内存最差；与“用 Rust 包装”的诉求相悖 | 是 | 共存 |

**推荐 ①。** 理由不是“稳一点”这种套话，而是三条硬的：

1. **v4 第一周就能看到真实数据**：边车跑的是今天线上那份服务端，连接的是同一个邮箱、同一个库。前端做错的地方立刻暴露，而不是 3 个月后才发现契约对不上。
2. **迁移有 oracle**：Swift 服务端在 M1–M2 期间一直是“参考实现”，Rust 模块可以对着它做双跑比对（同一请求两边各发一次，diff 响应），比任何设计文档都可靠。
3. **失败可回退**：L1 完成时你已经有可用的 v4；L2 是增量替换，任何一步都可以停。② 一旦中途发现某块重写不通，前期投入全沉没。

## 5. 关键技术决策（我按“推荐”执行，除非你反对）

| 决策 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| 外壳 | **Tauri 2**（`tauri` + `tauri-build` + WRY/WKWebView） | 裸 `wry`；Electron | Tauri 提供 sidecar、托盘、通知、更新器、单实例、签名打包；系统 WebView 而非内嵌 Chromium，体积/内存可控 |
| 前端 | **Vite + React + TypeScript + 手写 CSS variables**（不用组件库） | Svelte；纯 DOM | 主题 token（`LagoonMetrics/LagoonTheme`）直接映射成 CSS 变量；不用组件库是为了保住现有视觉识别度，而不是变成“又一个后台系统” |
| 进程模型 | **短期双进程**（Rust 壳 + Swift 边车）→ **长期单进程**（Rust 壳内嵌 Rust 后端） | 一开始就单进程（需先完成 L2） | 双进程是过渡手段，不是终局；端口交给系统分配（`0`）+ stdout 握手（先解析 listening 行，M1 换成 `{"port","pid"}` 一行 JSON），不做固定 8080 |
| 后端 Rust 栈 | axum + tokio + rusqlite（bundled）+ aes-gcm + base64 + encoding_rs（GBK）+ imap/async-imap + lettre + mail-parser + reqwest + keyring/security-framework | 直接上 sqlx | 与现状一一对应；bundled SQLite 免系统依赖 |
| 数据 | **独立数据目录**（`~/Library/Application Support/Lagoon-v4/`） | 共享 v3 的库 | 实测后修正：密钥拿不到，共享库里的封存正文/草稿都解不开（§5.2）；独立目录 + 重新连一次邮箱是唯一干净路径。**规则见 §6** |
| 秘密 | **v4 自持密钥**（新服务名）；M1 开发期用 0600 文件 + 环境变量注入边车，发布期用「签名 + data-protection Keychain」 | 一次性从 v3 导入密钥 | **实测：v4 读不到 v3 的 Keychain**（`-25300`，因为 v3 用 data-protection keychain，条目按签名身份的 access group 隔离）。所以必须重新生成密钥 → 意味着 v4 要重新连一次邮箱、旧本地状态不继承（见 §6.1） |
| 通知 | Tauri notification 插件（底层仍是 UNUserNotificationCenter） | 自写 Swift 桥 | 需要**稳定签名身份**：本项目已记录“临时签名让 Keychain 访问列表失配、读取永久挂起”的事故，v4 必须一开始就用固定 Developer ID |
| 只读宪法 | Rust 侧用**无写方法的 trait** 表达同步读取面（对应 Swift 的 `MailSyncReading`）；同步路径编译期就拿不到写能力 | 靠 code review | 这是产品承诺（AI 只读）在语言层面的延续，不能因为换语言就退化成约定 |

### 5.1 边车集成的四个硬约束（来自 `recon/server-contract.md` 的实测盘点）

这四条直接改 M1 的实现方式，先写死：

1. **服务端零 CORS。** WKWebView 里直接 `fetch` `http://127.0.0.1:PORT` 会被跨源拦截。
   **方案**：所有 HTTP 请求走 Tauri 的 Rust 侧（`tauri-plugin-http` 或自写 command），前端只调 `invoke`。
   附带收益：**Bearer token 只存在 Rust 进程里，前端 JS 拿不到** —— XSS 也偷不走令牌，比现在的 v3 更安全。
2. **后端没有 HTTP-only 模式。** `LagoonRuntime.start` 无条件启动同步引擎，且同步与路由共享同一个 GRDB 连接池 → **同一个库只允许一个后端进程**。v4 启动前必须检测并拒绝 v3 同时在跑。
3. **端口没有结构化握手。** `RunningLagoonServer.port` 回显的是配置值（传 0 就回 0），日志里才有真实端口。
   **方案**：Rust 侧自己挑空闲端口 → 启动 → 轮询 `/healthz` 直到 200；失败重试换端口。**不改 v1**。若以后要更稳，再给 CLI 加一行 `{"port":…}` 握手（≤20 行，可选参数，不动现有行为）。
4. **CLI 只认环境变量传密钥**，而 `argv/env` 对同用户进程可见。
   **M1 先接受**（单机、密钥不落盘），**M2 给 CLI 加一个可选 `--keys-fd 3`**（新增分支，不改变现有调用方式），从文件描述符读两个密钥。

### 5.2 密钥边界：v4 读不到 v3 的 Keychain（实测）

- 探针在 data-protection keychain 与 login keychain 里查 4 个 `lagoon.*` 条目，全部 **`-25300`**（item not found）；而对照实验（自建 keychain、由 `security` CLI 写入、Rust 读取）能读到且不弹窗 —— 说明探针本身可用，`-25300` 是**访问组不可见**，不是“条目不存在”。
- 根因在 v1 自己的实现里：`Sources/Lagoon/Services/KeychainStore.swift:36,99` 明确使用 **data-protection keychain**（`kSecUseDataProtectionKeychain = true`）。这类条目按签名身份的 access group 隔离，**换一个 bundle id / 换一个签名就看不见，且不会弹授权框**。
- 推论（这是硬约束，不是选择）：
  1. v4 **不可能**“一次性导入 v3 的密钥”，除非 v3 主动导出（要改 v1 + 用户点一次，且与“密钥永不落盘”的产品承诺冲突）——**不建议**；
  2. 因此 v4 必须**重新生成密钥** → 旧的封存正文/摘要/草稿变不可解 → **M1 用独立数据目录、重新连一次 QQ 邮箱**是唯一干净路径；
  3. v4 自己也要面对同一套规则：**未签名的开发构建可能连 data-protection keychain 都写不进去**（`-34018` 一类），所以 M1 开发期用 `v4/.dev/keys.json`（0600、gitignore）+ 环境变量注入边车，发布期再切到“稳定签名 + Keychain”。
- 另一个好消息：**AES-GCM 本身零风险**（§2.3 双向 PASS），所以“密钥换了、老库读不了”是访问权问题，不是算法问题；将来若真要继承历史，代价是给 v3 加一个导出入口，而不是重写加密。

### 5.3 契约盘点的关键数字（供你评估工作量）

- **57 个端点**（`/api` 56 + `/healthz`），18 个域；读一封邮件 = **2 次请求**（body + read），有内联图再 +1；附件字节走独立端点，每次重解析整封。
- **无 SSE / WebSocket / 长轮询**：Web 前端只能轮询（列表/账户目录 30s、time-saved 60s）。
- **错误封装只有一种**：`{"error":"<code>"}`；「不知道」不靠状态码表达，而是**字段缺省**（`MailCapabilities` 门控字段是 `Bool?`，`totalCount`/`hasMore`/`bodyScanSkipped` 可为 `nil`）；409 表示能力闸门（`archive-unavailable` 等）。Web 端必须照这个语义实现六态，否则会把「不知道」画成「失败」。
- **12 张表、迁移链 v1→v10**；4 个封存列；日期 TEXT UTC。
- **界面：24 个（1 窗口 + 3 栏 + 2 种列表表面 + 1 阅读器 + 23 面板）**；35 个键位（26 行快捷键字典 + 5 个未入表）；Web 端**必须做全局键盘层**，且浏览器会抢 ⌘N/⌘T/⌘W/⌘Q，要在外壳层拦截。
- **最难的三处**：HTML 邮件渲染（v3 用 719 行处理 WKWebView 禁 JS + 内容规则屏蔽全网 + cid→dataURL）、三栏宽度求解器（自研橡皮筋）、通知/角标/深链（平台 + 签名身份）。

## 6. 数据、密钥、进程的规则（这几条现在写死，避免以后发电）

1. **同一时刻只允许一个后端在跑。** 数据目录分开后不再是“抢同一个文件”，而是“抢同一个邮箱”：两个后端各开一条 IMAP 会对同一批 UID 做重复写（归档/删除互相打架）。v4 启动前检测 v3 是否在跑（锁文件 + `pgrep`），在跑就明确提示“先退出 Lagoon”，而不是让两个同步引擎同时动邮件。
2. **M1–M2 期间 schema 迁移主权属于 Swift 边车。** v4 用的是自己的新库，边车打开它会跑 v1→v10 迁移；v4 外壳**不写任何 DDL、也不“顺手升级”**。M3 交接时以 `recon/server-contract.md` §7 的 DDL 为准，Rust 版必须能通过同一套迁移版本断言。
3. **密钥只由 Rust 壳持有**，边车通过 stdin/临时 0600 文件传参（比 `argv` 安全，`argv` 在 `ps` 里可见）；不用 `ps` 可读的环境变量传密钥。
4. **失败要会说话**：边车起不来、端口没握上手、密钥没解出来 —— 每种都要有独立的、真实的状态文案（这正是 v3 的 P3“不撒谎”承诺；Web 端实现时照抄那份六态约定）。
5. **密钥不可共享**：v4 生成自己的 `tokenKey`/`bodyKey`；不要为了“继承历史”去读 v3 的 Keychain（读不到），也不要为了“省一次授权码”把 v3 的密钥导出到磁盘（与“密钥永不落盘”的承诺冲突）。

### 6.1 风险台账（含本轮实测新增的）

| 风险 | 细节 / 证据 | 应对 | 阶段 |
|---|---|---|---|
| 未签名/换签名的构建写不进 Keychain | data-protection keychain 需要签名身份；开发期可能 `-34018` | 开发期用 `v4/.dev/keys.json`（0600、gitignore）；M1 内验证一次“稳定签名下 Keychain 可写” | M1 |
| 无 rustup、无 Xcode | 加不了 `x86_64-apple-darwin` target；公证 / 通用二进制未验证 | M4 前补 rustup；M1 只跑 arm64 本地构建 | M4 |
| Tauri `generate_context!` 硬要 `icons/icon.png` | 缺图标会 proc-macro panic，`bundle.icon=[]` 绕不过 | 把 `Support/Lagoon.icns` 转成 `shell/icons/` 一套 | M1 |
| `aes-gcm` 0.11 API 已变 | spike 用 0.10.3 通过；0.11 是另一套 API | v4 钉死 0.10.3 并写进 `Cargo.lock` | M1 |

| 双进程崩溃恢复 | 边车死掉、端口被占、残留子进程 | 父进程 with kill-on-drop 语义 + 健康检查 + 超时重启 + 退出时清理 | M1 |
| SwiftUI 的“原生质感”损失 | 列表滚动、菜单栏、快捷键、拖放、Dock、Spotlight | 逐条对照 `recon/client-surface.md`；先做键盘层（命令面板 + 快捷键），接受部分能力降级并写进 ADR | M1–M2 |
| App Store 不可用 | 边车 + 非沙箱 | 明确“官网下载 / DMG 分发”路线，不承诺上架 | M4 |
| 字体/系统色没有权威数值 | v3 只有语义字号（`LagoonTypography`），仓内无 pt 记录；系统色是 sRGB 动态色，暗色下需实测采样 | M0 实机采样并冻结成 `tokens.css`，用 PB 截图做视觉基线 | M0 |

| 三栏布局是自研求解器 | 橡皮筋宽度、最小宽、窗口缩放回弹的行为约定在 v3 代码里 | M1 先做固定比例 + 可拖拽分隔条，接受第一版降级并写 ADR | M1 |

## 8. 边界：这次改动的「不做」清单

- 不改 AI 只读宪法；不因为换语言就让 AI 能写邮箱。
- 不改 v1 代码（不重构、不格式化、不顺手修 bug）——v4 是并行子树，v1 保持可构建、测试全绿。
- 不做移动端、不做云托管、不加第二个邮箱服务商。
- 不为了“跨平台漂亮”牺牲 QQ 特有正确性（GBK/GB18030 解码、UIDPLUS 撤销语义、归档文件夹角色创建、发送幂等）——这些是 v3 用事故换来的，Rust 版必须逐条有测试。
- **不承诺**“Rust 包装 = 更小的包”。Tauri + 系统 WebView 的体积与内存要实测后再对外说。

## 9. 待你拍板的四个问题

**Q1 · 「外部版本」到底指什么？**
- (a) 同机换壳：Web UI + Rust 外壳，仍只在这台 Mac 上跑
- (b) 跨平台：在 (a) 之上，最终能构建 Windows / Linux 版本 ← **我推荐**
- (c) 外部可达：前端还能从浏览器 / 其他设备访问（需要重做鉴权与绑定策略，单独一期）
- (d) 其他（请说明）

**Q2 · 后端怎么走？**
- (a) 先 Rust 壳 + Swift 边车，再逐模块迁 Rust ← **我推荐**（最快看到东西、有参考实现、可回退）
- (b) 直接 Rust 重写后端（3–4 个月才出第一个可运行版本）
- (c) 只做 Web 前端，后端永远 Swift（最快，但就不是“Rust 版”了）

**Q3 · v4 首发范围？**
- (a) 只读浏览（连接 / 简报 / 列表 / 阅读 / 搜索 / AI 摘要）
- (b) 核心闭环（(a) + 归档 / 废纸篓 / 回复 / 撤销 / 置顶）← **我推荐**，日常可用
- (c) 全功能对齐 v3.2（规则、提醒、备份、用量面板……）

**Q4 · 数据与密钥？**（实测后修正了推荐）
- (a) 共享 v3 的库与密钥 —— **技术上不成立**：v4 读不到 v3 的 data-protection Keychain 条目（−25300），密钥拿不到，封存正文就解不开；要成立必须先给 v3 加“导出密钥”入口（改 v1 + 密钥临时落盘，与产品承诺冲突）
- (b) **独立数据目录 + 新密钥**（v4 重新连一次 QQ 邮箱，完全隔离）← **我推荐**；旧本地状态（置顶/规则/审计/草稿）不继承；正文本来就能从服务器重新拉回来

## 10. v4 自己的验收标准

1. **契约可执行**：`v4/tests/contract/` 的 golden JSON，同一份既跑 Swift 服务端也跑 Rust 服务端，全绿才算“一致”。
2. **只读宪法机器可验**：Rust 侧同步路径拿不到写方法（类型层面），并有测试断言。
3. **六态不撒谎**：每个会等待数据的界面显式处理 v3 定义的六态与三个“不知道”。
4. **可回退**：任一里程碑都能退回 v3 继续用；v3 的 `bash scripts/run-all-tests.sh` 始终全绿。
5. **可分发**：M4 之后，干净机器（无 Swift 工具链）安装即用。
