## 二、问题清单（按严重度）

### 🔴 P0-1 · `/api/delete-bulk` 丢弃 `sent` 轴 → 在「已发送」里批量删除会**误删收件箱**

**三级独立确认**：产品经理发现 → 工程师独立复现 → 主理人逐行核验。

| 环节 | 事实 | 位置 |
|---|---|---|
| 客户端**会**发 `sent` | `DeleteBulkRequest` 有 `let sent: Bool?`，`init(allMatchingIn:)` 从 `LensScope.sent` 取值 | `Sources/LagoonKit/Stacks.swift:70, 89, 106` |
| 服务端**丢弃** `sent` | `deleteBulkHandler` 的局部 `Req` 只有 `remoteIds / allMatching / archived / deleted / stackId` | `Sources/LagoonServer/Routes/ActionsRoutes.swift:750-757` |
| 两次查询也不传 | `MessageStore.remoteIds(...)` / `count(...)` 均未传 `sent` | `Sources/LagoonServer/Routes/ActionsRoutes.swift:808-824` |
| 存储层默认 `false` | `sent: Bool = false` → 落回收件箱分支 `is_deleted=FALSE AND is_archived=FALSE AND is_sent=FALSE` | `MessageStore.swift:285, 564, 903` + `filterSQL:242-251` |
| UI 可达 | 批量条「删除」按钮**无透镜门控**（只有归档受 `canArchive` 限制）；「选择服务器上的全部 N 封」链接亦无门控 | `Views/BulkActionBar.swift:103`、`Views/MessageListView.swift:764-767, 930, 1556` |
| **守卫恰好漏掉** | `test_lensScope_coversEverySidebarDestination` 枚举为 `[.briefing, .allMessages, .unread, .pinned, .archived, .deleted]` —— **没有 `.sent`**；`DeleteBulkTests` 亦无 sent 用例 | `Tests/LagoonTests/TwoStageSelectTests.swift:35-37` |

**后果**：在「已发送」里点「选择服务器上的全部 N 封」再删除，服务端按**收件箱**口径解析，把收件箱最新最多 500 封移入废纸篓（软删除、可恢复，但仍是一次严重的错误批量操作 + 500 条审计行）。

**讽刺点**：`Sidebar.swift:187-194` 的注释正是为防此事故而写（"a new sidebar row without a mapping here would silently fall back to `.inbox` … a wrong one is an incident"）。客户端映射做全了，**服务端把字段切掉了**。

**修法（约 4 行）**：`Req` 增 `let sent: Bool?` 并传给两处 `MessageStore` 调用（`filterSQL` 已完整支持该轴，存储层无需改）；补两个守卫：`DeleteBulkTests` 加 sent-scope 用例、`TwoStageSelectTests` 枚举补 `.sent`。

**已排除的相邻风险**：批量**归档**不受影响 —— `archiveBulk(remoteIds:accountId:)`（`APIClient.swift:535`）只接受显式 id 列表，**没有 `allMatching` 路径**，缺陷仅限 delete-bulk 的全选分支。

### 🟠 P1-3 · 永久删除漏删依赖表 → 孤儿数据

`MessageStore.hardDeleteSync`（`MessageStore.swift:835-859`）只删 `message_pins / advice / message_bodies / message_headers` 四张表。schema 中还有两张按 `(account_id, remote_id)` 关联的表被漏掉：

| 表 | 外键指向 | 会被级联吗 | 当前处置 |
|---|---|---|---|
| `message_bodies` | → `message_headers` | ✅ 会 | 显式删（冗余但安全） |
| `advice` | → `message_headers` | ✅ 会 | 显式删（冗余但安全） |
| `message_pins` | → `accounts` | ❌ 不会 | 显式删（**必要**） |
| **`draft_replies`** | → `accounts` | ❌ 不会 | **漏删** ❌ |
| **`ai_overrides`** | → `accounts` | ❌ 不会 | **漏删** ❌ |
| `ai_actions` | 按 `actionId` 索引 | — | **刻意保留**（审计日志，正确） |

**影响**：永久删除后留下孤儿行。当前无读路径会展示（`overridesBySender` 会 JOIN `message_headers` 过滤掉），但违背"永久删除抹净全部痕迹"的承诺，且任何将来的账号级草稿列表都会把它们翻出来。**修法**：在同一事务补两条 `DELETE`，并让 `PurgeRoutesTests.dependentCounts` 一并断言。

### 🟡 P2-4 · `senderRanking` 漏 `is_sent = FALSE` → 「发件人排行」把用户本人列为高量发件人

`MessageStore.swift:713` 的谓词只有 `account_id = ? AND is_deleted = FALSE`。R1 之后，打开过一次「已发送」就会把 Sent 邮件 upsert 进 `message_headers`（`from_address` = 本人地址）。该面板主题是"谁在给我写信"，现在会把你自己的地址计入、甚至可能置顶（体积优先排序）。**修法**：谓词加 `AND is_sent = FALSE`（与 `unreadCount`/`pinnedCount` 同口径）。

### 🟡 P2-5 · `StackStore.messageCount` 与规则列表/清扫口径不一致

| 口径 | 谓词 | 位置 |
|---|---|---|
| 规则**徽章计数** | `is_deleted = FALSE AND <匹配>` —— **含归档 + 含已发送** | `StackStore.swift:107, 113` |
| 规则**列表** | `filterSQL` → `is_archived = FALSE AND is_sent = FALSE` —— 排除归档与已发送 | `StackSheets.swift:314` → `SyncRoutes.swift:48` |
| 规则**清扫**（allMatching） | `count/remoteIds(archived: false, sent: false)` | `ActionsRoutes.swift:808-824` |

**后果**：徽章数字 ≠ 列表行数，差额 = 归档数 + 已发送数。这正是项目自己反复称之为"徽章的数字和它标注的列表对不上"的缺陷类别。**修法**：徽章计数改道与列表同源的 `filterSQL`（见 §三 架构建议）。

### 🟡 P2-6 · `MessageStore.find()` SELECT 漏 `is_sent` → 单条查询丢 sent 标志

`find()`（`MessageStore.swift:333-343`）的 SELECT 列表含 `is_read, is_archived, is_deleted` 但**没有 `is_sent`**（而 `recent()` :304 有）。`decode` 对 nil 容错为 `false` → 单条查询会把已发送邮件标成非已发送。**修法**：补 `is_sent` 进 SELECT。

### 🟡 P2-7 · 外键开关的仓库内自相矛盾 + 测试假保证

仓库里对同一个事实有**两种相反说法**：

| 出处 | 说法 |
|---|---|
| `Sources/LagoonKit/LagoonDatabase.swift:172` | `configuration.foreignKeysEnabled = true`（注释："GRDB 7 enables foreign keys by default; stated explicitly because the schema leans on ON DELETE CASCADE"）→ **FK 是 ON** |
| `README.md:71` | "foreign keys ON" → **ON** ✅ |
| `Sources/LagoonServer/Storage/MessageStore.swift:813` | "this connection runs with `PRAGMA foreign_keys = OFF`（verified against the live database）" → **错** |
| `Tests/LagoonServerTests/PurgeRoutesTests.swift:29-31` | 同上 → **错** |
| `MVP第二步实施记录-永久删除与全选.md §2.2` | "实测这个连接的外键开关是关的" → **错** |

**（1）真相是 FK = ON。** 架构师在 `/tmp` 用与 App 完全相同的 `Configuration` 建独立验证程序实测：
- GRDB 连接 `PRAGMA foreign_keys` = **1（ON）**；删父行后子行剩余 = **0（CASCADE 触发）**
- `foreignKeysEnabled = false` 的连接 = 0
- `sqlite3` CLI 查**同一文件** = **0（OFF）** ← **假象来源**

即开发者当初几乎可以确定是**用 `sqlite3` 命令行查的**（CLI 是新连接、per-connection pragma 默认 OFF，永远报 0），把 CLI 行为当成了 App 连接行为。

**（2）由此产生的系统性风险**：
- `PurgeRoutesTests` 里"body / advice 已删净"的断言由 CASCADE 兜底 → **即使把 `hardDeleteSync` 退化成裸删 `message_headers`，该测试仍然绿**。它提供的是**假保证**，无法拦截回归。
- `AccountStore.delete`（`AccountStore.swift:214-219`）注释称依赖 FK 级联删 messages/pins/drafts —— 这条**是对的**（FK 真 ON），但它的正确性与 `hardDeleteSync` 的假设**方向相反**，两个注释并存会让后来者彻底迷失。
- `MessageStore.deleteAll`（UIDVALIDITY 重置，:352-355）裸删 `message_headers` 会级联清 bodies/advice，但**不清 pins**（pins 的 FK 指向 accounts）—— 属有意为之，但语义依赖 FK 行为，须知情。

**修法**：修正 3 处注释/文档为 "FK ON"；让测试**先断言 FK 状态**（或改断言 `message_pins`/`draft_replies` 这类**无 FK** 的表被删净），使 cascade 无法替它兜底。

### 🟡 P2-8 · 「彻底删除 / 清空废纸篓」在 IMAP 层零真实路径测试（不可逆 + 安全护栏）

`permanentlyDelete`（`IMAPProvider.swift:974`）与 `emptyTrash`（`:997`）是产品中**唯一不可逆**的操作，其安全语义是：

```swift
guard try await client.capability().contains("UIDPLUS") else {
    throw MailError.protocolError("UIDPLUS not supported")   // 宁可不删，也不退化成整 folder EXPUNGE
}
```

**没有任何测试**驱动真实的 `UID EXPUNGE` 路径，也**没有测试**断言这条降级拒绝分支。`PurgeRoutesTests` 测的是路由层（`StubMailProvider.permanentlyDelete` 永远成功），覆盖不到 IMAP 行为。**修法**：`IMAPProviderTests` 补 3 个用例（有 UIDPLUS 时发出单 uid `UID EXPUNGE`；无 UIDPLUS 时抛错且**不发出任何 expunge**；`emptyTrash` 整批行为 + 空废纸篓不发 expunge）。

## 三、架构健康度评估

### 评分

| 维度 | 结论 | 关键证据 |
|---|---|---|
| 分层清晰度 | **良** | `Package.swift` 依赖 DAG 无环：`Kit ← AI ← Server ← {Lagoon, CLI}`；LagoonKit 21 文件最长 375 行，未被污染成垃圾桶 |
| **宪法执行强度** | **强（编译期真强制）** | 逐行核验 `MailSyncReading`（`MailProvider.swift:238-251`）**只有 3 个方法**：`capabilities` / `pullChanges` / `shutdown`，**无任何写方法**；`SyncEngine` 全链路持有 `any MailSyncReading`。本轮新增的 `unarchive`/`restoreFromTrash`/`move`/`permanentlyDelete` 均已正确隔离在 `MailProvider`（用户触发路由），引擎够不到 |
| 数据一致性风险 | **中高（🔴侧滑）** | 见下 |
| 可演进性 | **中** | 巨型文件：`MessageListView.swift` **1889 行**（单类型约 1700 行 / 35 func / 20 `@State`）、`ActionsRoutes.swift` 1733、`IMAPProvider.swift` 1437、`MessageRoutes.swift` 1006 |
| 技术债密度 | **中** | 死 guardrail 规则、R2 死能力、FK 文档矛盾、迁移数文档陈旧 |

### ★ 核心结构性断层：多轴筛选的「双轨制」

项目有**两套**筛选谓词来源，且已咬过一次：

1. **共享 `filterSQL`**（`MessageStore.swift:206-277`）—— 被 `recent()`/`count()`/`remoteIds()` 复用，是"列表与计数同源"的正解。
2. **手写 WHERE 的计数/查询**（不走 `filterSQL`）：`unreadCount`(:582)、`pinnedCount`(:614)、`sentCount`(:652)、`deletedCount`(:666)、**`senderRanking`(:700)**、`oldestReceivedAt`(:764)、`trashedRemoteIds`(:866)、`listUnsubscribeIds`(:471)。

**已经发生过的漂移**：加 `is_sent`（第三轴）时漏进了 `unreadCount`/`pinnedCount`，代码注释自认 *"this query predates `filterSQL` and hand-rolls its own predicate, so adding a third axis to the shared clause did not reach it"*（`MessageStore.swift:586-593`）—— **靠轮末人工体检发现，不是靠测试**。

**本轮体检新增发现**：同一模式**仍有活体** —— `senderRanking`（P2-4）、`StackStore.messageCount`（P2-5）、`find()`（P2-6）三处漏加新轴。**路线文档 §"已知失败模式"最后一行标记的"两个筛选条件各写一套，开始漂移"，没有被防住。**

**侧边栏把两套口径混用**：`FolderCountsRoutes.swift:76-86` 里 `live`/`archived` 走 `count()`→`filterSQL`，而 `unread`/`pinned`/`sent`/`deleted` 走手写计数 —— **同一个侧边栏，两套语义**。

### 对第 4 个轴（R2 的 folder）的架构判断

**当前结构能撑 3 个布尔轴，撑不住第 4 个非布尔轴。** `folder` 是任意文件夹名（非布尔），直接塞进布尔模型必然重现"一封邮件同时在两个列表"的旧病。

- **最小改动**：加一列 `custom_folder TEXT NULL` + `filterSQL` 增加 `folder` 谓词分支，并**把 4 个手写计数全部改道**为基于 `filterSQL` 的单一 `count(kind:)`（即消灭双轨制）。这样第 4 轴只落在**一处**。
- **更彻底**：用**单一 `place` 列**（枚举 `inbox` / `archive` / `trash` / `sent` / `folder:<path>`）替换三个互斥布尔。现在的布尔组合能表达"不可能状态"（三者同真），而"邮件在哪"本质是**单值**属性。
- **明确否决**：**不要**把自定义文件夹复用进 `is_archived` —— 档案柜是独立面，复用会让邮件同时出现在「已归档」。
