## 0. 一句话结论

**这个 app 有一份写得很好的设计系统文档，但文档里的 token 大部分是死代码，界面上真正生效的是散落在 40 多个文件里的字面量——所以现在同一个语义有两到三套值，而且最刺眼的四处（未读标记、次级文字层级、emoji 分组图标、时间戳格式）在主界面上肉眼可见。**

具体到四个最伤 professionalism 的点：

1. **未读标记在主界面根本不存在。** 简报行（默认密度）没有任何未读点/色条，只靠主题是否加粗区分；而文档里 `LagoonTheme.unreadMarker`（深青）和 `LagoonMetrics.unreadStripeWidth`（2pt 色条）两个 token **引用数为 0**——它们描述的是一个从未被实现的设计。
2. **app 的次级文字层级在 macOS 上根本不存在。** 整个 app 用 `.caption`（10pt）当"发件人"、`.caption2`（**也是 10pt**）当"摘要"——**macOS 上这两者逐像素同号**（实测渲染行高都是 13.0）。而这两行的**颜色也相同**（都是 `.secondary`）。也就是说：简报行里的发件人和摘要，**在中文内容下几乎无法区分**。61 处 `.caption2` 建立起来的层级是一个幻觉。
3. **分组头用 emoji 当图标**（🔴 需要回复 / 🟢 可归档 / 🆕 订阅噪音 / 📌 置顶 / ⏳ 待回复）。🔴 与 🟢 正好撞上 app 的严重度色板（红=错误、绿=成功）——同一个窗口里"需要回复"和"需要重新连接"是同一个红。
4. **品牌青绿只到达了一半控件。** `.tint(LagoonTheme.brand)` 写在 `LagoonApp.swift:101`，侧边栏图标实测是青绿 `#2B859B`，但**链接按钮实测 `#418FF8`（系统蓝）、sheet 里的"完成"主按钮实测 `#4091F8`（系统蓝）**——而 `LagoonApp.swift:97-100` 的注释明说"so every accent (toggles, links, picker segments, selection highlight) reads as 'Lagoon teal', not 'system blue'"。这句注释被像素采样证伪。

**核心判断**：这不是"风格不统一"的审美问题，是**"token 存在但没有被强制"**的工程问题。第三节的收敛方案第 1+2 步（约 10 处改动）可以一次性关掉 12 条发现的主要根因。

### VZ-01 · 主界面没有未读标记：整个 triage 工具的信号只剩"加粗"

- **现象**：简报行（compact/舒适密度）**没有任何未读标记**——没有点、没有色条、没有颜色。只有主题的 `.bold(!isRead)`。原始邮件列表有一个 `.tint` 的小圆点，简报的**紧凑密度**行有 6pt 的点，但**默认的"简报"界面一个都没有**。同时，`LagoonTheme.unreadMarker`（注释写"unread row's leading stripe and dot"）和 `LagoonMetrics.unreadStripeWidth`（注释写"2pt. The accent stripe down the leading edge of an unread row"）**引用数都是 0**——文档描述的色条在整个 app 里不存在（`grep -rni stripe Sources/Lagoon/Views/` → 0 命中）。
- **证据**：
  - `Sources/Lagoon/Views/BriefingFeedView.swift:2171-2244`（`regularRow`）——整行只有 avatar + 主题 + 发件人 + 理由，**没有未读点**。
  - `Sources/Lagoon/Views/BriefingFeedView.swift:2150-2154`（`denseRow`）才有：`Circle().fill(.tint).frame(width: 6, height: 6)`。
  - `Sources/Lagoon/Views/MessageListView.swift:1276-1279` / `1549-1552`：`Circle().fill(.tint).frame(width: 7, height: 7)`。
  - `Sources/Lagoon/Theme/LagoonTheme.swift:101-106`：`static let unreadMarker = deepTeal` —— 0 引用。
  - `Sources/Lagoon/Theme/LagoonMetrics.swift:57-70`：`unreadDotSize = 7`、`unreadStripeWidth = 2` —— 0 引用。
- **为什么不对**：这个 app 的全部产品承诺是"打开两次、十分钟清零"。清零的第一件事就是**分清哪些还没处理**。现在唯一的信号是字重——对 CJK 主题（"需要你回复"）加粗几乎看不出差别，对低视力用户更看不出。而 Apple Mail.app / Outlook 的每一行未读都有**蓝色圆点 + 蓝色主题**，因为未读是这个产品最核心的一等信息。实测截图里那行"Windows quality: an…"的加粗确实是这个 app 里最弱的层级信号。Apple HIG《Typography》也明确指出纯字重差是**最弱**的语义区分手段。
- **建议怎么修**：
  1. 在 `BriefingFeedView.regularRow` 的 `HStack` 首位加一个未读指示，与 `MessageListView` 同款；
  2. 点尺寸统一成 `LagoonMetrics.unreadDotSize`（7），颜色改成 `LagoonTheme.unreadMarker`（`deepTeal`）——**不要用 `.tint`**，`LagoonTheme.swift:34-39` 已经写清楚了理由（`.tint` 跟随系统 accent，暗色下浅蓝点在深色行上几乎看不见）；
  3. 顺手实现 `unreadStripeWidth = 2` 的前缘色条，或者把这两个死 token 删掉——**留着不实现的 token 比没有 token 更糟**，它会让人以为色条已经在了。

### VZ-02 · "同步降级"在两个界面是两种颜色，而文档说这个 bug 已经修好了

- **现象**：同一个 `SyncHealth.Status.degraded`，账号菜单画**黄**，设置窗口画**橙**。而且账号菜单把 `error` 也画成黄——**同一个界面上，"出错了"和"降级了"是同一个颜色**。
- **证据**：
  - `Sources/Lagoon/Views/RootView.swift:1112-1119`：
    ```swift
    private func statusColor(for account: ConnectedAccount?) -> Color {
        switch account.syncHealth.status {
        case .ok: return .green
        case .degraded, .error: return .yellow      // ← degraded 和 error 同色
        case .needsReconnect, .accountMissing: return .red
    ```
  - `Sources/Lagoon/Views/SettingsView.swift:204`：`return LagoonTheme.syncStatusColor(account.syncHealth.status)` → degraded = `Severity.warning.color` = `.orange`，error = `.red`。
  - `Sources/Lagoon/Theme/LagoonTheme.swift:116-123` 的注释原文：
    > "One mapping, used by every surface that shows the dot — the toolbar's account menu and the Settings window. **The two used to disagree: the toolbar drew 'degraded' yellow while Settings drew it orange**, so a user had to learn two colours for one state…"
  - 实测截图 `04-启动裸spinner无文案.png` 同一窗口里横幅是红色（error），而账号菜单圆点是黄色（degraded）。
- **为什么不对**：这不是"两个地方不一样"，是**文档在撒谎**。`LagoonTheme` 的注释把这件事描述成已修复，CI 绿灯也盖住了它——但代码里那行 `.yellow` 从没被删。更糟的是 `RootView.swift:1116` 把 degraded 和 error 合并成一个黄色，而 `LagoonTheme.swift:128` 把 error 映射成红色——**同一个状态在同一个 app 里有两种颜色，而且每个界面内部自己也不自洽**。
- **建议怎么修**：删掉 `RootView.statusColor(for:)` 这个私有方法（`RootView.swift:1112-1119`），`RootView.swift:1057` 改成 `LagoonTheme.syncStatusColor(account.syncHealth.status)`。**一行改动**，同时让 `LagoonTheme.swift:116-123` 那段注释变成真的。

### VZ-03 · 分组头用 emoji 当图标，而且红色=错误色、绿色=成功色

- **现象**：简报的五个分组头用 emoji 文字当图标：`🔴 需要回复`、`🟢 可归档`、`🆕 订阅噪音`、`📌 置顶`、`⏳ 待回复`。实测像素：🔴 = `#D94E3B`，🟢 = `#5DB940`。而 app 的严重度色板里 **error = `.red`、success = `.green`**——同一个窗口里，"需要回复"这个**好事**是红的，"需要重新连接"这个**坏事**也是红的。
- **证据**：
  - `Sources/LagoonKit/Briefing.swift:17-26`：
    ```swift
    public var emoji: String {
        switch self {
        case .needsReply: "🔴"
        case .awaitingReply: "⏳"
        case .safeToArchive: "🟢"
        case .subscriptionNoise: "🆕"
        case .pinned: "📌"
        }
    }
    ```
  - `Sources/Lagoon/Views/BriefingFeedView.swift:669`：`Text("\(group.emoji) \(l10n.groupTitle(group))").font(.headline)`
  - 同一行的 chevron 是 `Image(systemName: "chevron.down").font(.caption2)`（`BriefingFeedView.swift:667-668`）——**同一行里混了 emoji 字形和 SF Symbol**。
  - 截图证据：`04…/02-简报分组头-emoji当图标.png`（🔴 直径约 18pt，比 `.headline` 标题还高）。
- **为什么不对**：三个层次的问题。
  1. **视觉**：emoji 的光学尺寸不受字号控制，这个 🔴 明显比旁边的标题大一号，整行视觉重心偏左（见截图）。
  2. **语义**：红/绿是 app 已经分配的严重度语义（`LagoonTheme.Severity`）。用 emoji 抢占红绿，等于在同一个视觉通道里放了两套互不相干的含义——用户看到红色圆点必须先想"这是分组还是出错了"。
  3. **平台**：macOS 应用里出现 🔴🟢 这种 iOS/Slack 风格的彩色 emoji 当导航图标，在任何截图里都会显得像原型而不是产品。Apple HIG《Symbols》明确要求用 SF Symbols，并规定符号要与文本共享同一套"图形语言"（同样的线宽、比例、视觉重量）。
  4. `🆕` 更糟——它渲染成一个蓝底白字的 "NEW" **徽章**，视觉上像系统 UI 控件，和相邻的 🔴🟢 完全不是一套东西（截图可见）。
- **建议怎么修**：删掉 `Briefing.swift:17-26` 的 `emoji` 属性；在 `BriefingFeedView.swift:664-686` 的 `groupHeader` 里改成 `Image(systemName:)`，用**中性** SF Symbol（`bubble.left.and.exclamationmark.bubble.right` / `clock` / `tray` / `newspaper` / `pin`），**不要用红绿**；分组身份交给 `.headline` 文字本身。顺带把 `BriefingFeedView.swift:668` 的 `.caption2` chevron 提到 `.caption`，让整行是 2 个尺寸而不是 3 个。

### VZ-04 · 品牌青绿只到达一半控件：链接按钮和 sheet 主按钮仍是系统蓝

- **现象**：`.tint(LagoonTheme.brand)` 写在窗口级，但实测**侧边栏图标是青绿、链接按钮是系统蓝、sheet 里的主按钮是系统蓝、分段控件是中性灰**。一屏之内三种强调色。
- **证据**：
  - 意图：`Sources/Lagoon/LagoonApp.swift:97-101`：
    ```swift
    // Brand tint: matches the icon palette so every accent
    // (toggles, links, picker segments, selection highlight)
    // reads as "Lagoon teal", not "system blue".
    .tint(LagoonTheme.brand)
    ```
  - 实测像素（对运行中的实例采样）：
    - 侧边栏"收件箱"托盘图标 = **`#2B859B`**（色相 191.8°，与 `brand` 的 193.5° 一致 → 青绿 ✓）
    - 行内"建议归档"链接（`.buttonStyle(.link)`，`RowAdviceStrip.swift:174`）= **`#418FF8`**（色相 214.4° → 系统蓝 ✗）
    - 快捷键表 sheet 的"完成"按钮（`.borderedProminent`，`ShortcutsSheet.swift:136`）= **`#4091F8`** → 系统蓝 ✗
    - 工具栏分段 Picker（`RootView.swift:1221-1229`）= 中性灰 `#5C5A5A` / `#ECE9E9`（未着色 ✗）
  - 截图证据：`04…/01-快捷键表-sheet-完成按钮是系统蓝.png`
- **为什么不对**：
  1. **注释被自己的实现证伪**。上面那段注释逐个点名了 "links, picker segments"，而这两个恰好是**没被 tint 到**的。
  2. 原因在 SwiftUI on macOS：`.tint()` 只作用于 SwiftUI 自己绘制的控件；`.buttonStyle(.link)` 走 AppKit `NSButton` 的 `NSColor.linkColor`（跟随 `NSApp.accentColor`），`.sheet` 内容在**另一个 NSWindow** 里，窗口级 `.tint` 不会传进去。
  3. 用户看到的不是一个"稍微蓝一点"的细节，而是**同一个窗口里侧边栏是青的、行里的链接是蓝的、弹窗里的按钮又是蓝的**——这正是 `LagoonTheme.swift:11-19` 自己描述的"two accent languages on one screen"，只不过这次不是 `.blue`/`.green`/`.orange`/`.yellow`，是 teal/blue。
- **建议怎么修**：**改 `NSApp.accentColor`，不要只改 SwiftUI 的 `.tint`**——这是唯一能让 SwiftUI 控件、AppKit 控件和 sheet 窗口一起变青的做法：
  ```swift
  // LagoonApp.swift，App init 里
  NSApp.accentColor = NSColor(LagoonTheme.brand)
  ```
  保留 `.tint(LagoonTheme.brand)` 作为 SwiftUI 侧的兜底；sheet 内部（`ShortcutsSheet` 等）各自再补一次 `.tint(LagoonTheme.brand)`。改完后 VZ-04 与 `LagoonTheme.swift:11-19` 的那段叙述才成立。

### VZ-05 · 时间戳比主题还长；统一日期格式的 token 是死代码

- **现象**：简报的**正常行**用 `date: .abbreviated`，中文环境下渲染成 **`2026 年 8 月 11 日 13:16`**——占掉列表列宽的近三分之一，把主题挤成 `Windows quality: an…`。而**同一份代码里的紧凑行**和**原始邮件列表**都用 `date: .omitted`（只有 `13:16`）。**同一个 app、三套日期习惯。**
- **证据**：
  - `Sources/Lagoon/Views/BriefingFeedView.swift:2194`（正常行）：`Text(item.message.receivedAt.formatted(date: .abbreviated, time: .shortened))`
  - `Sources/Lagoon/Views/BriefingFeedView.swift:2164`（紧凑行）：`Text(item.message.receivedAt.formatted(date: .omitted, time: .shortened))`
  - `Sources/Lagoon/Views/MessageListView.swift:1305` 和 `1317`（原始列表）：同样 `date: .omitted`
  - `Sources/Lagoon/Theme/LagoonTypography.swift:74-84`：`rowTimestamp(_:now:)` —— **0 引用**。它的注释原文：
    > "The Briefing showed '10月20日 14:30' and the raw list showed '14:30' — the same mailbox, two date conventions… One function, one rule, two surfaces."
  - 截图证据：`04…/03-简报行-时间戳比主题长.png`（时间戳宽度 ≈ 主题的 3/4）
- **为什么不对**：在邮件客户端里，**时间是列的标尺，主题是内容**。一个 11 点的邮件和 3 个月前的 11 点邮件，扫一眼应该看得出区别——`date: .omitted` 恰恰把这个区别抹掉了（`14:30` 不告诉你是今天还是去年），这正是 `rowTimestamp` 注释里写的担忧。而简报正常行那个超长日期又走向另一个极端：**用 16 个字符去表达一个"3 个月前"**。
  行业做法（Mail.app / Outlook / Gmail）：今天→ `14:30`；本周→ `周二`；更早→ `10月13日`。**三档，绝不出现年份，除非跨年。**
