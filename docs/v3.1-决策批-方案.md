### 1.2 四个断点（每个都能指到行）

**断点 1 —— 建议队列没有出口。**
`advice` 表有 `decision`/`decided_at` 两列（`migrations.rs:206-222`），但 `store/advice.rs` 只有
`list` / `accepted_stats` / `has_advice` / `upsert_ai` 四个函数，**没有任何写 decision 的函数**。
`web/src/ui/AdviceStrip.tsx:44-49` 两个按钮是 `disabled`，tooltip 写着「M2 开放」。
`docs/api-contract.md:237` **已经声明**了 `POST /api/advice/:id/decision`，Rust 侧 `http/mod.rs` 没有注册。
→ AI 说「建议归档」，用户唯一的办法是自己再去找那封邮件点归档。

**断点 2 —— 历史邮件从没被分诊。**
分诊只在 `sync/mod.rs:294` 的 `triage()` 里跑，且 `TRIAGE_PER_ROUND = 3`（`sync/mod.rs:131`）、
`TRIAGE_BACKLOG_LIMIT = 200`（`:133`）。队列是内存里的 `VecDeque`，进程重启即丢失。
→ 430 封历史邮件，除非逐轮同步触发，永远不会进 advice。

**断点 3 —— 退订是空壳。**
`provider/lagoon_mail.rs:110` 硬编码 `unsubscribe_links: "[]"`。
`imap/provider.rs:1093` 只把 `List-Unsubscribe` 转成一个 bool（`decoded(...).is_some()`），链接从未解析。
`DEFAULT_HEADER_FIELDS`（`imap/client.rs:68-76`）确实抓了 `LIST-UNSUBSCRIBE`，但抓完就丢了。
分类器会输出 `action:"unsubscribe"`（`ai/classify.rs:22`），下游无任何执行路径。

**断点 4 —— 批量动作的粒度错了。**
`/api/archive-bulk`、`/api/delete-bulk` 已经存在且测透（`routes_r5.rs:611-840`），
但前端只能操作"当前选中的行"（`web/src/ui/BulkBar.tsx`）。
→ 想清掉那 80 封，得手动滚 80 行去多选。

## 2. 什么叫 AI native（本方案的设计公理）

**不是聊天框。** 聊天框是把"读 430 封"换成"跟 AI 聊 430 封"，成本没降，还多了一层猜谜。

三条公理，本方案每条设计都要能对得上：

**A1 · AI 的输出必须能变成动作。**
一条建议如果只能看不能执行，它就不是"AI 帮你处理邮件"，是"AI 给你写评语"。

**A2 · 动作的粒度必须是「批」，不是「封」。**
人的确认成本必须与**决定数**成正比，不是与**邮件数**成正比。
430 封 → 8 张卡 → 3 次点击。这个比例是本产品的全部价值。

**A3 · 确认权不可让渡，但确认成本可以压缩。**
沿用既有宪法（`docs/superpowers/specs/2026-10-02-advisory-only-ai-constitution-design.md`）：
AI 永不写邮箱、永不发信。人点才算数。
但"人点"不等于"人点 430 次"——一次点击可以覆盖 80 封，只要它可撤销、且批次内容对用户可见。

**A4 · 每个数字都要有出处（沿用项目 P3「不撒谎」）。**
分诊进度、置信度、花了多少钱、被跳过了多少、批里到底有哪几封——界面上出现的数字必须能回答"这个数从哪来"。
答不出来就显示"不知道"，不显示 0。

### 反面清单（明确不做，防止跑偏）

- ❌ 聊天式邮件助手（"帮我清一下收件箱"）
- ❌ AI 自动归档/自动退订/自动标已读（宪法 §5 非目标）
- ❌ 自动规则引擎（"以后这个发件人都归档"）——宪法 §2 规则 5 明确禁止
- ❌ 语义搜索（搜索不是本轮痛点）
- ❌ 换 UI 主题/重做视觉（价值为零）

## 4. S1 · 分诊批处理

### 4.1 为什么是后台 worker，不是加个循环

三种做法的取舍：

| 做法 | 问题 |
|---|---|
| 复用 sync 的 `triage()` | 队列是内存 `VecDeque`，只吃 upsert，重启即丢；`TRIAGE_PER_ROUND=3` 是给"增量"设计的 |
| 前端循环调 430 次单封接口 | 430 个 HTTP 请求；界面卡在请求上；没法显示"还剩多少" |
| **后台 worker + 进度轮询**（选它） | 关掉界面不中断；进度可查；可取消；成本闸门天然生效 |

### 4.2 分层分诊：先用免费的，再花钱（★本轮最重要的成本设计）

**原方案是 430 封全喂 AI。真实数据推翻了这个做法。**

| 事实 | 数字 |
|---|---|
| 总邮件 | 430 |
| `snippet` 为 NULL（正文没抓过） | **430（100%）** |
| 正文已缓存 | **3** |
| 带 `List-Unsubscribe` | 185 |
| 订阅类发件人（`noreply`/`newsletter`/`marketing`/…，规则已有） | 137（与上条不重叠部分） |
| **两者合计可免费判掉** | **322（74.9%）** |
| **真正需要 AI 判断** | **108** |

这意味着两件事：

1. **分诊输入是"发件人 + 主题"，没有正文。** 主题是明文（`message_headers.subject`，契约 §6 明确不加密），
   质量不差：`电子报销凭证（美团）`、`昇腾社区电子邮箱验证`、`有人提起黑色星期五？`。
   但**必须诚实地告诉用户**：AI 只看了发件人和主题。
2. **不该为 322 封明显的订阅邮件付钱。** 既有启发式（`briefing.rs:92-116`）已经能判它们，
   且 `advice.source` 的合法值本来就是 `heuristic|ai`（`store/advice.rs:60`）——
   schema 早就为"两种来源"准备好了，只是从来没人填过 `heuristic`。

**所以：L1 启发式（免费，全量）→ L2 AI（付费，只处理剩下的）。**

```
430 封
  ├─ L1 启发式（本地，0 成本，毫秒级）
  │    ├─ 带 List-Unsubscribe        → 建议 archive / unsubscribe
  │    ├─ 订阅类发件人                → 建议 archive / unsubscribe
  │    ├─ 自己发的（From == 账号）    → 建议 nothing（不进卡片）
  │    └─ 其余标记为「待 AI 判断」
  └─ L2 AI（108 封，≈ $0.03）→ 覆盖 L1 的待判项
```

L1 写 `source='heuristic'`、`confidence='medium'`（**不冒充高置信度**）。
L2 写 `source='ai'`，置信度用模型给的。

成本：**$0.11 → 约 $0.028**（108 封 × ≈$0.00026）。少花 75%，而且第一批卡片秒出——
用户不用等 2 分钟才看到东西。这是产品体验和成本的双赢，不是妥协。

**为什么 L1 不直接复用 `/api/briefing` 的分组结果**：简报的分组是"给收件箱分层"，
它的 `needsReply` 是默认桶（"剩下的都需要回复"），不是判断。
把它直接当建议会让 108 封全部变成 `reply`——那是假建议。L1 只取**能明确判定的那几条规则**：
`list_unsubscribe`、`matches_subscription_sender`、`from == account_email`。其余一律留白给 AI。

### 4.3 数据来源：SQL 是唯一真相

不新增表。**"还没分诊的邮件"是查询结果，不是状态字段。**

```sql
-- L1：免费的，全量
SELECT h.remote_id, h.from_address, h.from_name, h.subject,
       h.list_unsubscribe, h.received_at, h.message_id_header
FROM message_headers h
LEFT JOIN advice a ON a.account_id = h.account_id AND a.remote_id = h.remote_id
WHERE h.account_id = ?1
  AND h.is_deleted = 0 AND h.is_sent = 0
  AND a.id IS NULL
ORDER BY h.received_at DESC

-- L2：只取 L1 判不了的（L1 跑完后 a.id IS NULL 的剩余）
--   同一查询 + 正文缓存 LEFT JOIN（有就用前 300 字，没有就只用主题）
```

- `a.id IS NULL` 就是"从未分诊"，天然幂等：跑两遍不会重复收费或重复写行。
- `ORDER BY received_at DESC`：**先分最近的**。用户要处理的是当下的压力；
  2025-05 那批早没人看了。第一批卡出得越早，产品越有说服力。
- 正文增强：`message_bodies` 有缓存就用前 300 字（现在只有 3 封，将来会变多）；
  没有就只用发件人+主题。**界面如实标注分诊依据。**

### 4.4 成本与并发

- 复用 `classify::classify(&ai, targets)`（`ai/classify.rs:79`），一次喂 **3 个 target**。
  保持**一封一个模型调用**，不做批量 prompt：批量 prompt 要改输出 schema（数组），
  部分解析失败会静默丢建议——那是"看起来在工作"的失败模式，本项目最不能接受。
- 3 路并发（`tokio::task::JoinSet`），`classify` 内部是串行的，所以一次 3 个 future 并行 = 3 个 POST。
- 每条成功建议必须写 `store::usage::record`（对齐 `sync/mod.rs:537-552`），
  否则预算闸门看不见花费 —— 这是宪法级要求，不是可选项。**L1 不记账（零成本调用）。**
- 每次循环前查 `ai.status()`：`configured == false` 立刻停，状态写 `stopped-unconfigured`。
  注意：**未配置时 L1 仍应能跑**——启发式不需要 key。这让产品在没配 AI 时也有价值。
- `AiError::BudgetExceeded` → 停，状态 `stopped-budget`，**并把这个事实告诉用户**（不是静默截断）。

**成本口径**：MiniMax M3 按 `config/providers.json` 的保守价
（$0.0006/1k prompt、$0.0024/1k completion），单封 prompt ≈ 120 token、completion ≈ 80 token
→ ≈ **$0.00026/封**。108 封 ≈ **$0.03**。方案里不写死这个数，界面显示 `usage_log` 的真实累计。

### 4.5 状态机

```
idle ──run──▶ running ──┬── 队列空 ──────▶ done
                        ├── 预算用尽 ────▶ stopped-budget
                        ├── 未配置 key ──▶ stopped-unconfigured（L1 已完成才停）
                        ├── 连续失败 ≥5 ─▶ stopped-error
                        └── cancel ─────▶ cancelled
```

`running` 期间再次 `run` → **不启动第二个**，返回当前状态（202 + 同一份 run）。
理由：两个 worker 同时跑同一账号会撞 `upsert_ai` 并重复计费。

进程重启 → 内存状态丢失 → `idle`。这不是 bug：`done` 的真值来自 SQL（advice 行数），
重启后 `unsuggested` 会自动变小，用户再点一次就接着跑。

9. `a_user_decision_is_never_overwritten_by_either_layer` —— 先接受建议，再跑 worker，
   `decision` 仍为 `accepted`（钉住 `upsert_ai` 的 `WHERE advice.decision='pending'`）。
10. **`the_model_never_sees_a_mail_the_heuristic_already_decided`** —— 断言 L2 的 prompt 里
    不出现 L1 已判邮件。这是成本的真正来源，也是"两层不打架"的证明。

## 5. S2 · 建议决策出口

### 5.1 形状：决策与执行分离

契约已经声明 `POST /api/advice/:id/decision`（§4.8 p.237），**照它实现**，不发明"accept 即执行"的合并端点。

理由：
- 契约是唯一对账面（项目纪律 §8「改协议先改契约」）。契约里已经写好的形状，没有理由绕开。
- 执行走 `archive/delete` 那些**已经测到牙齿**的路由（`r3_actions.rs` 四条撤销用例），
  合并端点等于造第二条无人验证的写路径。
- 顺序由前端控制：**先执行，成功后才记 decision**。执行失败 → decision 保持 pending。
  这样账本永远不撒谎（不会出现"已接受"但邮件还在收件箱）。

### 5.2 契约（新增）

```
POST /api/advice/decisions-bulk?accountId=<uuid>
  body {"ids": [1,2,3], "decision": "accepted"|"dismissed"}
  → 200 {"items":[{"id":1,"ok":true}],"decided":3}
```

单个沿用契约已有的 `POST /api/advice/:id/decision`。

约束：
- `decision` 只接受 `accepted`/`dismissed`；`pending` → 400 `invalid-decision`。
- 已决策的行再决策 → **幂等**（`decided_at` 只在首次落），返回 ok。
  理由：前端批量重试不该变成 409。
- `ids` 为空 → 400 `empty-ids`；>500 → 400 `too-many-ids`（与 bulk 端点同口径）。
- 不属于本账号的 id → 逐条 `{"ok":false,"errorCode":"unknown-advice"}`，不整体失败。

### 5.3 顺手修一个账本 bug：动作要消费建议

用户手动归档一封有 pending 建议的邮件后，那条建议还挂在队列里 —— 下次打开又出现，且计数虚高。

修：**写动作成功后，把该邮件的 pending 建议置为 `accepted`**。
位置：`routes_r5.rs` 的 `run_message_action` / `run_bulk`，在 `local()` 成功之后、同一个连接内。
只动 `decision='pending'` 的行，绝不覆盖已有的 accepted/dismissed。

`accepted_stats`（`store/advice.rs:121`）随之变成"真的被采纳过的统计"，而不是"模型自说自话"。

## 6. S3 · 决策台（本轮的产品主戏）

### 6.1 为什么是独立视图，不是塞进简报

简报（`BriefingFeed.tsx`）是"分组的收件箱"——还是 430 行。用户得先扫一遍才知道该干什么。
决策台是"待你拍板的事"——8 张卡。**首屏必须是后者**，否则用户仍然在读 430 封信。

侧边栏 SMART 段最上方加入 `决定`，作为默认落地页。简报保留（它按发件人/线程分组仍有价值）。

### 6.2 卡片的两种类型

**A · 动作批**：按 `(action, category)` 聚合，只聚合**可执行**的 action：`archive`、`delete`。
`reply / wait / remind / unsubscribe / nothing` 是建议性的，不生成卡（见 6.6）。

**B · 发件人批**：同一发件人 ≥ 10 封。这是断点 4 的正解，也是 77 封那种情况的唯一合理粒度。

⚠️ **不能直接用 `/api/senders` 的 `totalCount`。**
`store/senders.rs:26-40` 的 WHERE 是 `is_deleted=FALSE AND is_sent=FALSE` —— 注释明说
"archived mail is included (that is where finished mail lives)"。
但决策卡的语义是"待处理"，已归档的不该算进来。直接复用会让卡片显示 80 而实际只有 3 封待处理。

→ 新查询（`store/senders.rs` 加 `pending_ranking()`），WHERE 增加 `AND is_archived = FALSE`。
`/api/senders` 本身**不动**（它服务的是"发件人排行"，口径不同且正确）。

排序：可执行的按邮件数降序；展示前 6 张，其余折进「其他小批（N 封）」一张。

### 6.3 「这一屏是谁判的」—— 分层必须可见

卡片角标写来源：`规则` / `AI`。两种来源混在同一张卡里时，写 `规则 9 · AI 3`。

理由：用户有权知道"这条建议是我写死的规则给的，还是模型看了内容判的"。
混在一起当成一个东西，就是在隐去模型没参与的部分。这是 P3 的直接应用。

同时：分诊进度条分两段显示「规则已判 322 / AI 已判 40 / 剩余 68」，
用户看见免费那层秒完，也知道钱花在哪。

### 6.4 卡片上必须有什么（少一样都不合格）

```
┌──────────────────────────────────────────────────────────┐
│ 📥 归档 · 营销邮件                       12 封 · 高 9/中 3 │
│                                                          │
│  Shopee 双十一预售 · shopee@...                          │
│  Supabase 11 月更新 · noreply@supabase.com               │
│  Steam 周末特惠 · noreply@steampowered.com               │
│  …查看全部 12 封                                          │
│                                                          │
│  AI 为什么这么判：批量发送 + 带退订链接 + 你从未回复过      │
│                                                          │
│  [ 归档这 12 封 ]  [ 忽略 ]                               │
└──────────────────────────────────────────────────────────┘
```

硬要求：

1. **数量与置信度分布**一起显示。置信度混合时不许写成一个统一的手势（"9 高 / 3 中"）。
2. **至少 3 条样本**（主题 + 发件人），可展开全部。用户必须能看见自己批了什么。
3. **理由**（`advice.rationale`）必须显示。这是信任的唯一来源。
4. `delete` 卡的主按钮走确认框，文案写明"移到废纸篓，可撤销"。`purge` 不在此界面出现。
5. 执行中 `busy`，执行完 toast + **撤销按钮**（走 `undo-bulk`，`routes_r5.rs:913`）。
6. 空态三分支：无账号 / AI 未配置（给出「去配置」的说明，不假装有建议）/ 真的没有待办。
7. **不撒谎**：`unsuggested > 0` 时页面顶部常驻一行「还有 310 封没被 AI 看过（开始分诊）」。

### 6.5 执行路径（前端编排，两次调用）

```
点「归档这 12 封」
  → POST /api/archive-bulk {remoteIds:[...]}        // 已有，测透
  → 全成功 → POST /api/advice/decisions-bulk {ids, decision:"accepted"}
  → 部分失败 → 只对成功的 remoteId 记 decision；失败的保留 pending 并在卡上标红
```

顺序不可颠倒（先执行后记账，见 5.1）。

### 6.6 建议性 action 怎么处理

`reply` / `wait` / `remind` 不生成卡，但也不能丢。做法：决策台底部一个「需要你亲自处理（N）」列表，
每行是邮件主题 + 建议动作 + 理由，点开就是阅读器（回复/转发已有界面）。
这批**不可批量执行**——因为"回复"这件事 AI 替不了，假装能批量才是欺骗。

## 8. S5 · 退订：只解析、只呈现、不代发

### 8.1 为什么不做服务端一键退订（重要决策）

`List-Unsubscribe` 的值来自**邮件正文**，也就是**攻击者完全可控的输入**。
在服务端对它发 HTTP，等于给任何能给你发信的人一个向你的内网发请求的通道（SSRF）。
要做对，需要：DNS 解析后校验 IP、禁私网/环回/链路本地、禁重定向、限时、限响应体、
禁凭据、RFC 8058 的 `List-Unsubscribe-Post` 语义区分——这是一整个安全项目。

而且本仓库**刚刚自己做过这个决定**：`568dfe3 feat(shell): 邮件里的链接交给系统浏览器，不再在应用窗口里导航`。
服务端代发退订请求，与那条决策的精神相反。

所以本轮：**解析出来、显示出来、让系统浏览器去打开**。风险为零，价值仍然成立
（用户从"找不到退订入口"变成"一眼看到、一点就走"）。

### 8.2 做什么

1. `crates/lagoon-mail/src/mime/unsubscribe.rs`（新建）：
   `parse_list_unsubscribe(raw: &str) -> UnsubscribeLinks`
   - 支持 `<https://...>`、`<mailto:...>`、逗号分隔、大小写不敏感
   - 同时解析 `List-Unsubscribe-Post: List-Unsubscribe=One-Click` → `oneClick: true`
   - 畸形输入不 panic，丢弃该段，返回已解析部分
2. `imap/provider.rs:1089-1095` 用新解析器填 `unsubscribe_links`（SEF 序列化成 JSON 数组），
   `list_unsubscribe` 布尔仍保留（简报分组在用）。
3. `provider/lagoon_mail.rs:110` 删掉硬编码 `"[]"`。
4. 契约：`MessageBody` 增加**可选**字段 `unsubscribeLinks: [{url, kind:"https"|"mailto", oneClick}]`
   （§8 允许"新增可选响应字段"，向后兼容）。
5. 阅读器：发件人下方一行「此发件人提供退订」+ 域名 + 按钮 → `openExternal`（已有能力）。

### 8.3 安全要求（必须写进测试）

- 只呈现 `https:` 和 `mailto:`。`http:`/`javascript:`/`data:` → 丢弃并不显示。
- 显示完整**主机名**，不只显示"退订"两个字（用户要知道自己在点什么）。
- 不在应用窗口内导航，走既有系统浏览器通道。

### 8.4 验收

```bash
cargo test -p lagoon-mail unsubscribe
cargo test -p lagoon-api --test r6_unsubscribe
```

1. `<https://a.example/u?id=1>, <mailto:u@a.example>` → 两条，kind 正确。
2. 带空白、大小写混用、缺尖括号 → 仍能解出。
3. `javascript:alert(1)` / `http://plain` → 不出现在结果里。
4. 空值 / 畸形 → 空数组，不 panic。
5. `List-Unsubscribe-Post: List-Unsubscribe=One-Click` → `oneClick=true`。
6. 端到端：sync 一封带退订头的信 → body 响应里有 `unsubscribeLinks`。

## 10. 自审记录（三轮，逐轮记录改了什么）

### 第 1 轮 · 正确性（对照宪法 + 契约 + 现有测试）

发现并修正：

1. **原方案打算加 `POST /api/advice/{id}/accept` 做"接受并执行"。**
   → 改为：契约已声明的 `decision` 端点 + 复用 `archive-bulk`/`delete-bulk`。
   理由：契约 §4.8 p.237 早就写了 decision；再造一个合并端点等于绕过"契约先行"纪律。
2. **原方案打算把分诊塞进 `sync::triage`。**
   → 改：独立 worker + SQL 真相。`sync` 的 backlog 是 `VecDeque`（`sync/mod.rs:127`），
   进程内、只吃 upsert、重启即丢，430 封历史永远进不去。
3. **原方案打算用批量 prompt 省成本。**
   → 改：一封一次调用。`classify` 的解析路径（`ai/classify.rs`）是单对象 JSON，
   改数组要重写解析，且部分失败会静默丢建议 —— 与本项目 P3 冲突。
4. **发现遗漏**：手动归档后 pending 建议不会消失。补 §5.3。
5. **发现遗漏**：`/api/senders` 的计数口径未核实，可能把已归档算进去。补 §7 第 2 条为**必查项**。

### 第 2 轮 · 风险与安全

发现并修正：

1. **退订：从"服务端一键 POST"降级为"解析 + 系统浏览器"。** 见 D2。
   这是我这一轮砍掉的最大功能，也是最正确的一刀：安全边界不是一个"待优化项"。
2. **删除卡不能和归档卡同一个手势。** 补 §6.4 第 4 条：删除走确认框并写明"可撤销"；
   `purge`（真删）不在此界面出现。
3. **并发分诊必须幂等启动。** 补 §4.4：`running` 时再 `run` 返回同一份状态，
   否则两个 worker 撞 `upsert_ai` 并重复计费。测试 6 专门钉这条。
4. **预算耗尽必须说出来。** 补 §4.3：`stopped-budget` 是可见状态，不是静默截断。
5. **决策只允许 accepted/dismissed。** `pending` 作为入参会让"撤销决策"变成可能，
   但那会破坏 `upsert_ai` 的 `WHERE decision='pending'` 语义。不许。
6. **`decided_at` 幂等**：重复决策保留首次时间戳，前端批量重试不产生脏数据。

### 第 3 轮 · 产品（这真的是 AI native 吗？）

发现并修正：

1. **原方案把决策卡放在简报页顶部。** → 改为独立首屏。
   理由：首屏还是列表，用户就还在读 430 行；卡片是装饰不是入口。这是本轮最重要的一次改动。
2. **加了"理由"字段的强制要求**（§6.4 第 3 条）。没有理由卡片的批量按钮是黑箱，
   用户第一次按下去心惊胆战、第二次就不敢按了 —— 产品的信任是一次性消耗品。
3. **加了顶部常驻的"还有 N 封没被 AI 看过"**（§6.4 第 7 条）。
   这是本项目 P3 的直接应用：不显示 0，也不假装全覆盖。
4. **砍掉"聊天式助手"。** 它是最廉价的 AI-native 模仿，对 430→8 的压缩毫无贡献。
5. **加了"需要你亲自处理（N）"清单**（§6.6）。否则 reply/wait 的建议会凭空消失 ——
   这比不做更糟：用户会以为 AI 看过了、没事。
6. **确认执行后必须给撤销**（§6.4 第 5 条）。P2 说"撤销是真的"，卡片批量执行是新路径，
   必须接进既有的 `undo-bulk`，否则是在新功能上开一个违反 P2 的口子。

### 第 4 轮 · 真实数据（写完之后去查真实库，推翻了一个核心设计）

**这是我写方案时最该先做、却最后才做的一步。教训记在这里。**

原设计：430 封全部喂给 AI，成本 ≈ $0.11。

去查真实库之后，三个事实推翻了它：

1. **`snippet` 430/430 是 NULL，正文只缓存了 3 封。**
   → 原来以为"至少能用正文开头做上下文"是错的。真实输入只有**发件人 + 主题**。
   主题是明文且质量不差（`电子报销凭证（美团）`、`有人提起黑色星期五？`），
   但方案必须如实写成"只看发件人和主题"，不能暗示看过正文。

2. **185 封带 `List-Unsubscribe`，137 封是订阅类发件人 → 322/430（74.9%）是免费可判的。**
   → 为这 322 封付钱是纯浪费。改为**分层**：L1 启发式（免费，全量）→ L2 AI（只处理剩下的 108 封）。
   成本从 $0.11 降到 ≈$0.03，且第一批卡片秒出（不必等模型）。
   这不是妥协，是**更好的产品**：用户不用盯着进度条等两分钟。

3. **`advice.source` 的合法值本来就是 `heuristic|ai`**（`store/advice.rs:60`）。
   → schema 早就为两层设计好了，只是从来没人填过 `heuristic`。这说明分层不是我的发明，
   是原设计里存在但没实现的东西。

连带修正：

- 加了测试 2 `the_heuristic_layer_never_calls_the_model`（零请求、零记账）——
  这是分层的地基，不钉死就会在某次重构里退回"全量付费"。
- 加了测试 3 `an_unconfigured_gateway_still_runs_the_free_layer`——
  **没配 AI 也要能用**。这改变了产品的降级行为，是更好的默认。
- 加了测试 10 `the_model_never_sees_a_mail_the_heuristic_already_decided`——
  证明两层真的不打架，而不是"我以为它们不打架"。

### 我仍然不满意、但本轮不做的

- **分诊输入只有发件人+主题**（正文有缓存时才补 300 字，现在只有 3 封有）。
  这是本轮质量的硬上限。做全文分诊要给 430 封抓正文，IMAP 往返成本远高于模型成本
  （参考 `docs/V1.0` P4：单封正文 1.2s）。留作下一轮的"按需深读"。
- **没有"以后这个发件人都归档"**。宪法禁止自动规则。但我认为这是产品的真实缺口：
  77 封同一个发件人，用户明年还会再清一次。值得和 owner 讨论
  **"规则只生成建议、仍逐批确认"** 是否在宪法允许范围内（我倾向于认为允许，因为它不自动执行）。
- **S5 只到"看得见"**。真正的一键退订需要独立的安全设计（DNS 校验、私网拒绝、重定向策略、
  RFC 8058 语义），是一个独立项目，不能顺手做。

**一处走错又改回的路（写下来防止重犯）。**
中途我把发件人卡改成"优先抢占邮件"，理由是"77 封同一发件人更该按发件人杀"。
真实数据一量：322 封本来只压成 **2 张**动作卡；发件人卡抢走后变成 **7+ 张**——决策数变多，方向反了。
改回"发件人卡只收动作组没覆盖的邮件"，并把这个真实形状写成了测试
`does not split a group that already covers the mail just to show a sender`。

**教训**：分组的价值是**减少决策数**，不是让每个维度都有卡。任何分组改动都要先量，再改。
