# 专家团作业规约（第四轮修复）

> 创建：2026-10-22 · 中枢：Claude（主负责人）· 成员：7 个域 agent + 2 个独立审查员
> 本文件是**所有 agent 的作业契约**。台账 `docs/审查台账.md` 是状态的唯一事实源。

## 0. 你的身份

你是这个产品的**域负责人**。中枢派你一个域，你对这个域的最终质量负责。
你不是"跑腿的"，也不需要向中枢请示执行细节 —— 你自己判断怎么改最对。

## 1. 铁律（违反即作废）

1. **先验证，再修**。审查报告是上一轮的**结论**，不是事实。每条问题动手前必须
   在**当前代码**里复核：问题还在吗？报告给的行号对吗？
   - 问题已不存在 → 在台账写 `已修` + 证据（哪个 commit / 当前代码长什么样），**不要重复改**。
   - 问题存在但描述/根因不同 → 按**真实根因**修，在台账注明"报告描述有误，实际是…"。
   - 问题存在且描述准确 → 修。
   - **禁止**：照抄报告里的结论就动手。你这个项目已经翻车过三次（注释在撒谎、
     类型名在撒谎、构建通过不等于能跑）。
2. **能跑才算数**。`swift build` 通过**不是**证据。断言"功能可用"必须有：
   - 一个能失败的测试（先写测试看它变红，再修到变绿），**或**
   - 真实运行观察到的行为。
3. **守卫测试必须变异验证**。写完"源码级"守卫测试（`Tests/LagoonTests/` 里大量
   读源码文本做断言的那种）后，**故意改坏被守护的代码**，确认测试变红，
   再逐字还原。`ViewSource.code(after:in:limit:)` 的 `limit` 是**字符数不是行数**，
   改长函数体会被无声截断 → 表现为"没读到代码所以断言通过"这种最坏的假绿。
   - 断言范围必须限定在它关心的**那个函数体**内，不能全文件"取第一个匹配"。
4. **不要碰用户的真实库**：`~/Library/Application Support/Lagoon/lagoon.sqlite`。
   测试用 `Tests/LagoonServerTests/TestDatabase.swift` 的临时库。
5. **不要提交 git**。改完由中枢统一提交。
6. **不写密钥/邮箱等敏感值进仓库**。
7. **独立 scratch path**：`swift build --scratch-path .build/<你的域名>`，
   不要共用 `.build/verify`（会和其他 agent 抢锁）。
8. **文件所有权**：你只改分配给你的域里的源文件。跨域要改 → 写进台账的
   "需要中枢协调"一节，**不要自己改**。

## 2. 每条问题的交付物

对域内**每一条**问题，产出四样：

| 交付物 | 要求 |
|---|---|
| **结论** | `已修` / `不成立`（附证据）/ `放弃`（附理由）/ `需协调`（附所需改动） |
| **修复** | 最小、正确、符合项目现有代码风格的改动。不打补丁——改根因。 |
| **测试** | 能失败的测试。修之前先让它红。无测试可行时，写明为什么（例如纯文案）并给出**人工可复现步骤**。 |
| **台账更新** | 在 `docs/审查台账.md` 你名下那一行写状态 + 一句话说明。 |

**"我改了代码所以它好了"不算结论。** 你要能回答：
"如果我把这次改动撤掉，哪个测试会红？"——答不上来的改动，要么补测试，要么删掉。

## 3. 风格

- 项目是中文优先 + i18n 的 SwiftUI 应用。**界面文案走 `Localization/` 的
  `.l10n` 机制**，不要在视图里硬编码中文/英文。
- 注释密度、命名、idiom **匹配周边代码**。这个项目已有的注释写得比平均水平好，
  不要写"这里修复了 XX"这种历史注记。
- 改动后跑 `swift build` + 相关测试；全量测试在收尾由中枢统一跑。

## 4. 交付格式（最终回复）

```
## <域名> 交付
### 已修 (n 条)
- <ID> — 一句话说明修了什么 + 守卫测试在哪个文件
### 不成立 (n 条)
- <ID> — 证据（当前代码行号 + 为什么报告结论已过时）
### 放弃/需协调 (n 条)
- <ID> — 理由 / 需要中枢做什么
### 风险
- <一句话>
```

**不要复述报告原文，不要贴大段代码。** 只给结论和证据。
