## 〇、先纠正任务书里的一条前提

任务书给的两条"硬事实"里，**第一条在本 SDK 上是错的**，这直接决定了本轮最重要的一节结论。

> **前提一（任务书原话）**：*SwiftUI 的 `.disabled(_:)` 覆盖环境值而不是与之组合。两处叠加的 `.disabled()` 会静默丢掉第一个。*

实测结论：**`.disabled()` 是组合语义（AND），不是覆盖语义。** 三路独立证据：

**① SDK 源码**（`SwiftUICore.swiftinterface` 第 210–213 行）：

```swift
@inlinable nonisolated public func disabled(_ disabled: Swift::Bool) -> some SwiftUICore::View {
  return modifier(_EnvironmentKeyTransformModifier(
    keyPath: \.isEnabled, transform: { $0 = $0 && !disabled }))
}
```

变换函数是 `$0 && !disabled`——**读取已有环境值再与新条件求与**。整个 SDK 里不存在 `_DisabledEffect` 这类"覆盖型"实现。`EnvironmentValues.isEnabled` 标注 `@available(macOS 10.15+)` + `@_originallyDefinedIn(module: "SwiftUI", macOS 15.0)`，即 macOS 14 部署目标走的是回移植实现，与 macOS 15+ 行为一致。

**② 目标三元组下的 SIL**（`swiftc -target arm64-apple-macosx14.0 -emit-sil`）：产出 `_EnvironmentKeyTransformModifier<Bool>`，即组合实现，回移植路径与新系统同构。

**③ 运行期探针**（`/tmp/discheck/probe2.swift`，读 `@Environment(\.isEnabled)`）：

| 链 | 结果 |
|---|---|
| `disabled(true).disabled(false)` | `false` |
| `disabled(false).disabled(true)` | `false` |
| `disabled(true).disabled(true)` | `false` |
| `disabled(false).disabled(false)` | `true` |
| `disabled(true).disabled(false).disabled(true)` | `false` |

没有任何一种组合会让"第一个条件被丢掉"。

**对本项目的影响**：任务书要求"猎杀叠放的 `.disabled()`"。我用链感知扫描器（逐个 `.disabled(` 调用向后回溯，直到撞上新表达式的起点，遇到另一个 `.disabled(` 才算叠放）扫了 `Sources/**/*.swift` 全部 **65 处** `.disabled(` 调用点——**真正的叠放调用为 0 处**。

唯一的"疑似"是 `RootView.swift:321` 与 `:341`：

```swift
.opacity(surface == .briefing ? 1 : 0)
.disabled(surface != .briefing)          // :321
...
.opacity(surface == .allMessages ? 1 : 0)
.disabled(surface != .allMessages)       // :341
```

这是**两个不同 surface 的两条独立修饰链**（`briefingSurface` 与 `messagesSurface` 各自一个 `@ViewBuilder` 属性），不是叠放。扫描器的误报来自"两个 `.disabled(` 之间没有出现新的 `Button(`/`Text(` 之类表达式起点"这一启发式。

> **前提二（任务书原话）**：*源码级守则测试必须把范围限定到它针对的那个函数。全文件"首次匹配"搜索会比对到错误的出现位置。*
>
> 这条**成立**，而且本项目确实有此类假绿风险。见第五节 S3-05 / S3-06。

## 一、结论摘要

| 严重度 | 数量 | 说明 |
|---|---|---|
| **P0 崩溃 / 数据丢失** | **0** | 未发现可证实的崩溃或数据丢失缺陷 |
| **P1 用户可见的错误行为** | **3** | 简报页 ⌘N 跳组后 j/k 走不到新展开的行；建议面板"打开邮件"在刷新进行中静默失效；刷新门在本地变更打断轮询后不安排补跑 |
| **P2 健壮性 / 性能** | **1** | 「全部邮件」批量标已读逐封重建索引，O(k·n) |
| **P3 整洁性** | **1** | 三处注释把 `.background` 说成"兄弟图层"，与 SwiftUI 实际语义相反 |

**本轮最有价值的产出不是这 5 条缺陷，而是下面这条**：

代码里三处注释（`BriefingFeedView.swift:807-811`、`BriefingFeedView.swift:855-858`、`MessageListView.swift:791-794`）断言：

> *".background 是兄弟图层，RootView 给整个界面加的 `.disabled()` 到不了这里——没有这道门，隐藏的简报页仍然会响应 ⌘A。"*

**这句话是错的。** 探针（`/tmp/bgprobe`，`NSHostingController` + `NSEvent.performKeyEquivalent`）实测：

| 形状 | 父层 `.disabled(true)` 能否抑制 `.background` 层的 ⌘ 快捷键 |
|---|---|
| A：父层对**子视图整体**（子视图自己拥有 `.background`）施加 `.disabled` | **能**（`A-disabled` 未触发，`A-control` 触发） |
| B：`.disabled` 施加在**包含**该 `.background` 的容器上 | **能**（`B-disabled` 未触发，`B-control` 触发） |

两种形状都抑制。而 Lagoon 的结构恰好是形状 A：`RootView.briefingSurface` 对 `BriefingFeedView` 的结果施加 `.disabled(surface != .briefing)`（`RootView.swift:321`），而 `BriefingFeedView` 自己的 `.background { groupJumpShortcuts; keyboardNavigationShortcuts }`（`BriefingFeedView.swift:207-210`）。

**结论：那些 `!isVisible` 门不是承重结构，是冗余的。** 代码是安全的（双保险），但**理由是错的**，而且这个错误前提被原样抄进了两个测试文件的文档注释里（见 S3-05）。留着它，下一个按注释推理的人会得出错误的结论——比如"既然父层的 `.disabled()` 到不了这里，那就必须在这里再写一次"，从而写出更绕的代码。

## 二、P1 — 用户可见的错误行为

### S3-01 · 简报页 ⌘1–⌘5 跳组后，j/k 再也走不到刚展开的那批行

| 项 | 内容 |
|---|---|
| **文件:行** | `Sources/Lagoon/Views/BriefingFeedView.swift:877-883`（`jump(to:)`）<br>对照 `Sources/Lagoon/Views/BriefingFeedView.swift:1006-1017`（`toggle(_:)`） |
| **严重度** | P1（用户可见的功能缺陷） |

**问题**

`toggle(_:)` 折叠/展开一个分组后调用了 `rebuildIndex()`，注释写明了原因：

```swift
// Sources/Lagoon/Views/BriefingFeedView.swift:1006
private func toggle(_ group: BriefingGroup) {
    withAnimation(.spring(response: 0.32, dampingRatio: 0.85)) {
        if collapsedGroups.contains(group) { collapsedGroups.remove(group) } else { collapsedGroups.insert(group) }
    }
    // The reachable rows changed with the collapsed set, so the cached
    // walk order has to follow — otherwise j/k would keep offering a row
    // the user can no longer see.
    rebuildIndex()          // :1016
}
```

但 `jump(to:)` 做了同一件事——`collapsedGroups.remove(group)`——却**没有** `rebuildIndex()`：

```swift
// Sources/Lagoon/Views/BriefingFeedView.swift:877
private func jump(to group: BriefingGroup) {

    collapsedGroups.remove(group)

    withAnimation { scrollProxy?.scrollTo(group, anchor: .top) }

}
```

**触发条件**

1. 打开简报页。「订阅噪音」组默认折叠（`BriefingGroup.collapsedByDefault` 只有 `subscriptionNoise` 为 true，`Sources/LagoonKit/Briefing.swift:29`；`BriefingFeedView.swift:28` 据此初始化 `collapsedGroups`）。
2. 按 **⌘4**（`groupJumpShortcuts` 把 `BriefingGroup.allCases` 按顺序绑到 ⌘1…⌘5，`BriefingFeedView.swift:801-805`；`BriefingGroup` 的声明顺序是 needsReply / awaitingReply / safeToArchive / subscriptionNoise / pinned，所以 ⌘4 = 订阅噪音）。
3. 该组展开、行可见了。
4. 按 **j**。

**为什么是问题**

`j`/`k` 的行走顺序来自缓存 `index.visibleIds`（`BriefingFeedView.swift:719-721`）：

```swift
rebuilt.visibleIds = items
    .filter { !collapsedGroups.contains($0.group) }
    .map(\.message.remoteId)
```

这个缓存只在 `rebuildIndex()` 里刷新，而 `rebuildIndex()` 的调用点只有两处：`setItems()`（`:697`）和 `toggle(_:)`（`:1016`）。

⌘4 展开订阅噪音组之后，`index.visibleIds` **仍然是折叠状态下的那份**——订阅噪音的行不在里面。于是 `moveSelection(.down)`（`:758-781`）在 `visibleIds` 里遍历，永远到不了订阅噪音组的任何一行：用户看到那些行就在屏幕上，却用键盘选不中。

更糟的是，`destination(for:)`（`:928-938`）用 `visibleIds` 计算阅读面板的"上一篇/下一篇"兄弟列表：

```swift
let visible = visibleIds
let siblings = visible.contains(remoteId)
    ? visible.map { MessageRef(accountId: accountId, remoteId: $0) }
    : nil
```

所以 ⌘4 展开订阅噪音组后，从阅读面板按"下一封"也会跳过整个订阅噪音组。

**规模**：订阅噪音组恰恰是简报页**行数最多**的一组（它装的是所有订阅/推广邮件）。这不是"少走一行"，是"整整一组到不了"。

**建议修法**

`jump(to:)` 里补上 `rebuildIndex()`，与 `toggle(_:)` 对齐：

```swift
private func jump(to group: BriefingGroup) {
    collapsedGroups.remove(group)
    // The collapsed set changed, so the cached walk order has to follow —
    // otherwise j/k (and the reader pane's sibling list) still believe the
    // group's rows are unreachable.
    rebuildIndex()
    withAnimation { scrollProxy?.scrollTo(group, anchor: .top) }
}
```

更进一步（防同类回归）：`collapsedGroups` 是唯一的折叠状态来源，但**没有任何 `onChange` 兜底**。建议把 `rebuildIndex()` 的触发收敛成一条路径——要么在 `collapsedGroups` 上加 `.onChange(of: collapsedGroups) { rebuildIndex() }`，要么把 `collapsedGroups` 藏进一个只暴露 `expand/collapse/toggle` 方法的私有类型里，让"改了折叠集合就必须重建索引"成为类型层面的约束。后者更彻底：现在 `toggle` 和 `jump` 两条路径都得记得手动调 `rebuildIndex()`，这正是漏掉的原因。

**验证方式**

- 单元测试（源码级）：断言 `BriefingFeedView.swift` 里 `jump(to:)` 的方法体内出现 `rebuildIndex()`。注意**不要**用全文件首次匹配——本文件里 `rebuildIndex()` 出现在 `:697`、`:708`、`:1016`，必须先定位到 `private func jump(to group: BriefingGroup) {` 之后的那一段。
- 更好的测试：把 `collapsedGroups` 与 `visibleIds` 的推导抽成一个纯函数（`static func visibleIds(items:collapsed:)`），然后直接测"折叠集合里移除一组 → visibleIds 变长"。这样测试的是行为而不是文本。
- 手工：⌘4 展开订阅噪音组 → 按 j，看高亮能否进入该组。

### S3-02 · 建议面板的「打开邮件」在刷新进行中静默失效

| 项 | 内容 |
|---|---|
| **文件:行** | `Sources/Lagoon/Views/BriefingFeedView.swift:1923-1939`（`reveal(_:)`）<br>关联 `Sources/Lagoon/Views/BriefingFeedView.swift:1853`（`refresh()` 的 `claim()` 早退） |
| **严重度** | P1（用户可见的功能缺陷） |

**问题**

```swift
// Sources/Lagoon/Views/BriefingFeedView.swift:1923
private func reveal(_ remoteId: String) async {
    if !items.contains(where: { $0.message.remoteId == remoteId }) {
        await refresh()
    }
    guard !isLoading else { return }          // :1927  ← 问题在这
    guard items.contains(where: { $0.message.remoteId == remoteId }) else {
        errorBanner = ErrorBanner(
            severity: .warning,
            title: l10n.adviceMessageGoneTitle,
            detail: l10n.adviceMessageGoneDetail
        )
        return
    }
    withAnimation {
        selection = [remoteId]
    }
}
```

**触发条件**

1. 简报页上有一条 AI 建议（`RowAdviceStrip` 的「打开邮件」按钮 → `BriefingFeedView.swift:466` / `:2173` 的 `onOpenAdvice` → `Task { await reveal(remoteId) }`）。
2. 点击的瞬间，**恰好有一轮刷新/轮询在途**。刷新每 30 秒一次（`Self.refreshInterval`，`poll()` 在 `:345-362`），此外每次 `⌘Z`（`.lagoonDidUndo`）和数据变更通知（`.lagoonDidChangeData`）也会触发 `refresh()`（`:283-288`）。命中窗口约等于"刷新耗时 / 30 秒"，实测在带 LLM 分类的简报接口上可以是数百毫秒到数秒。
3. 目标邮件不在当前快照里（建议指向的是刚到的新邮件）→ `reveal` 调 `await refresh()`。

**为什么是问题**

`refresh()` 的第一行是一个**协作式**早退：

```swift
// Sources/Lagoon/Views/BriefingFeedView.swift:1845
private func refresh() async {
    guard let accountId = accounts.accountId else { return }

    // `claim` is nil while a refresh is in flight. ...
    guard let generation = refreshGate.claim() else { return }   // :1853

    isLoading = true
    ...
}
```

于是 `reveal` 的执行路径变成：

1. `await refresh()` → `claim()` 返回 `nil`（已有刷新在途）→ **立即返回**，新邮件**没有**被拉进来。
2. `guard !isLoading else { return }` → 在途刷新把 `isLoading` 置为 `true` → **早退**。
3. 用户看到的是：**什么都没发生**。没有提示、没有错误横幅、阅读面板不动。

这个 `guard` 是在做一件它做不到的事：`isLoading` 表达的是"当前有刷新在途"，而不是"当前不能选中"。而刷新在途时**恰恰是最需要能选中的时刻**——因为要选的往往就是刚到、还没进快照的那一封。

`MessageListView` 里没有对应的 `guard`，因为它没有"按 id 打开一封可能尚未加载的邮件"这个需求。`reveal` 是简报页独有的路径。

**建议修法**

把"等这一轮刷新结束"和"刷新被拒"分开处理。可选：

**方案 A（推荐）——让 `refresh()` 可等待。** 把 `claim()` 失败时的早退改成"记录待办并让调用方等到本轮结束"，即返回本轮刷新的 `Task`，而不是 `nil`：

```swift
// 概念上的改法
private func refresh() async {
    guard let generation = refreshGate.claim() else {
        await refreshGate.waitForCurrentRun()   // 等在途那轮跑完
        return
    }
    ...
}
```

`RefreshGate` 已经是"两个列表面共用的簿记"，把它从"布尔 + 整数"升级成能提供 `waitForCurrentRun()` 的类型，是自然的下一步。

**方案 B（局部、侵入更小）——在 `reveal` 里改用"刷新后重试"。**

```swift
private func reveal(_ remoteId: String) async {
    if !items.contains(where: { $0.message.remoteId == remoteId }) {
        await refresh()
        // A refresh may have been turned away because one was already in
        // flight; that run's payload is at least as fresh as ours, so wait
        // for it before deciding the message is gone.
        guard !isLoading else {
            try? await Task.sleep(for: .milliseconds(120))
            return await reveal(remoteId)   // 重入一次
        }
    }
    ...
}
```

方案 A 更干净；方案 B 可以立刻止血，但带一个轮询延迟。

**方案 C（最省事，但语义最弱）——去掉 `guard !isLoading` 的早退，改成"在途时排一次刷新"。** 即 `reveal` 在 `isLoading` 时记一个 `pendingReveal = remoteId`，由当前刷新在 `defer` 里消费。这条路能work，但它把 `reveal` 的语义从"打开"变成"排队打开"，用户会以为点击没生效。

**验证方式**

- 注入一个可控的慢刷新（例如测试里让 `api.fetchBriefing` sleep 2 秒），在刷新在途时调用 `reveal`，断言最终 `selection` 包含目标 `remoteId`。
- 断言在目标邮件确实不在快照里时，`errorBanner` 是 `adviceMessageGoneTitle`（而不是"什么都没有"）。
- 源码级守则测试：断言 `reveal` 的方法体里**不**存在裸的 `guard !isLoading else { return }`。这一条要小心作用域——必须先定位 `private func reveal(` 再取其方法体，不能全文件首次匹配（`isLoading` 在 `:418`、`:427`、`:436`、`:1855`、`:1862` 都出现）。

### S3-03 · 本地变更打断轮询后，刷新门不安排补跑，列表停留在旧快照

| 项 | 内容 |
|---|---|
| **文件:行** | `Sources/Lagoon/Models/RefreshGate.swift:32-45`（`finish()`）<br>调用点 `Sources/Lagoon/Views/BriefingFeedView.swift:1861-1866`、`Sources/Lagoon/Views/MessageListView.swift:1112-1117` |
| **严重度** | P1（用户可见的错误行为） |

**问题**

`RefreshGate` 的整个设计意图在注释里写得很清楚（`RefreshGate.swift:20-23`）：

```swift
/// Release the claim. True when a caller was turned away and is owed a
/// run — the caller is expected to start one.
mutating func finish() -> Bool {
    isRunning = false
    defer { isPending = false }
    return isPending
}
```

`isPending` 只在 `claim()` 被拒时置位（`RefreshGate.swift:28-31`）：

```swift
mutating func claim() -> Int? {
    guard !isRunning else {
        isPending = true        // ← 只有"被拒的调用方"会置位
        return nil
    }
    ...
}
```

但 `invalidate()`（`:36-38`）**不会**置 `isPending`：

```swift
mutating func invalidate() {
    generation += 1
}
```

**触发条件**

1. 轮询刷新在途（`isRunning == true`）。
2. 用户在此时做了一个本地变更——归档、删除、退订、标已读。简报页的 `unsubscribeFrom`（`:1173`）、`archiveAndUndo(byId:)`（`:1210`）、`deleteOne`（`:1777`）、`dropItem`（`:1050`）、`deleteBulk`（`:1457`）都调 `invalidatePendingRefresh()`；列表页的 `removeRow`（`:1983`）、`archive`（`:1654`）、`restoreFromTrash`（`:1947`）同样。
3. 在途刷新返回，`generation` 已被 `invalidate()` 推高 → `guard generation == refreshGate.generation else { return }`（`BriefingFeedView.swift:1875`、`:1888`；`MessageListView.swift:1136`、`:1147`、`:1175`、`:1186`）拦住它 → **这一轮的载荷被丢弃**。
4. `defer` 里 `refreshGate.finish()` 返回 `false` → **不安排补跑**。

**为什么是问题**

`RefreshGateTests.swift` 的文档注释（`:5-10`）写着这个类型存在的两个原因：

> *"...a refresh raised while another was in flight was dropped instead of queued, so the user sat on a stale snapshot until the next 30s tick."*

`finish()` 修好了"刷新请求被丢弃"这一半，但**没修"载荷被丢弃"这一半**。这两半是同一个用户症状的两个来源：

- 请求被丢弃 → 靠 `isPending` 补跑。✅ 已修。
- **载荷被丢弃**（本地变更使在途响应作废）→ 靠 `isPending` 补跑。❌ 没修。

我用一份与 `RefreshGate.swift` 逐行等价的 Python 模型模拟了两条路径：

```
claim/claim/finish        (在途期间来了第二个调用方) → 补跑 = True   ← 门当初修的那条
claim/invalidate/finish   (在途期间落了本地变更)     → 补跑 = False  ← 没修的那条
```

所以：**只要用户在一个 30 秒轮询窗口里归档/删除/退订过一次，那一轮的服务器最新状态就被丢掉，列表会一直停在上一个快照，直到下一次 30 秒 tick 撞上同样的运气。**

对"归档"这种操作，用户会看到自己刚归档的邮件**又出现在列表里**（服务器已经归档了，但客户端的快照里还有它，直到下一轮）。这恰恰是 `RefreshGate` 这个类型被写出来要防的那个症状——只不过触发路径换了一条。

**建议修法**

`invalidate()` 也应当记一笔"欠一次刷新"，因为它使在途响应作废、而这个作废本身就需要一次新载荷来纠正状态：

```swift
/// Retire whatever is in flight: a local mutation of the list means
/// the running call's payload predates it.
///
/// The running call's payload is therefore *discarded* — so this run owes
/// the caller a fresh one. Marking it pending here is what makes the
/// mutation's effect reach the screen without waiting for the next tick.
mutating func invalidate() {
    generation += 1
    if isRunning {
        isPending = true
    }
}
```

`isRunning` 的判断是必要的：只在有在途刷新时记欠账；`invalidate()` 也被 `markAllRead`（`:1948`）等在**没有**在途刷新的路径上调用过，那时不该凭空排一次刷新。

**连带需要检查的一处**：改完之后，`finish()` 返回 `true` → `Task { await refresh() }`（`BriefingFeedView.swift:1864`）。这个 `Task` 是在 `defer` 里创建的 unstructured task，它本身是"补跑"机制的唯一载体。现在它会在**每一次本地变更 + 在途轮询**的组合下被触发，频率比之前高。需要确认它不会造成刷新风暴——`RefreshGate.claim()` 的"同时只有一轮"的语义保证了不会并发；`finish()` 返回 `true` 后 `isPending` 被清空，也保证了不会自激。**但请在改完后用真机验证一次"归档 50 封"的场景**，确认不会打成 50 轮刷新。

**验证方式**

在 `RefreshGateTests.swift` 里补一条与现有 `test_aRefreshRaisedDuringAnInFlightOneIsNotLost` 对称的用例：

```swift
func test_aMutationDuringAnInFlightRefreshAlsoOwesARun() throws {
    var gate = RefreshGate()
    _ = gate.claim()          // 一轮刷新在途
    gate.invalidate()         // 本地变更作废了这一轮的载荷
    XCTAssertTrue(
        gate.finish(),
        "the invalidated run's payload is discarded; a fresh one is owed"
    )
}
```

**注意**：现有的 `test_invalidateRetiresTheInFlightResponse`（`:14-25`）只断言 `claimed != gate.generation`，**不**断言 `finish()` 的返回值——所以这条缺陷在现有测试下是全绿的。这正是任务书说的"源码级守则测试的盲区"的一个实例。

## 三、P2 — 健壮性 / 性能

### S3-04 · 「全部邮件」批量标已读逐封重建索引，O(k·n) 主线程开销

| 项 | 内容 |
|---|---|
| **文件:行** | `Sources/Lagoon/Views/MessageListView.swift:1730-1742`（`markSelected`）→ `:1756-1775`（`markReadOne`）→ `:1079-1088`（`setRead`）→ `:1478-1488`（`setMessages`/`mutateMessages`）→ `:1496-1508`（`rebuildIndex`） |
| **严重度** | P2（性能） |

**问题**

批量标已读的每个成功项都会走一遍完整的索引重建：

```swift
// MessageListView.swift:1756
@MainActor
private func markReadOne(_ m: MessageHeader, isRead: Bool) async {
    do {
        _ = try await api.markRead(remoteId: m.remoteId, accountId: m.accountId, isRead: isRead)
        setRead(remoteId: m.remoteId, isRead: isRead)   // → mutateMessages → setMessages → rebuildIndex
    } catch { ... }
}
```

`setRead`（`:1079`）→ `mutateMessages`（`:1484`）→ `setMessages`（`:1478`）→ `rebuildIndex()`（`:1496`）：

```swift
private func rebuildIndex() {
    index.byRemoteId = Dictionary(messages.map { ($0.remoteId, $0) }, uniquingKeysWith: { first, _ in first })
    index.sections = Self.groupSections(displayMessages, mode: groupingMode)   // ← 昂贵的那一半
    index.mode = groupingMode
    index.unreadOnly = unreadOnlyEffective
    index.rowTags = Self.rowTags(index.sections, expanded: expandedThreads)
}
```

`groupSections` → `ConversationGrouper.group` → `groupByThread`（`Sources/Lagoon/Models/Conversation.swift:91-134`），其成本是：

1. **对每一封邮件跑一次正则**做主题规范化（`SubjectNormalizer.normalize`，`Conversation.swift:56-58`：`replacingOccurrences(of: #"\s+"#, with: " ", options: .regularExpression)`），外加一个 `while changed` 循环反复剥前缀。
2. 一遍并查集（union-find）合并线程。
3. 按根分组 + 排序。

**触发条件**

用户在「全部邮件」页 ⌘A 全选（或框选）N 封，按「标为已读」。`markSelected`（`:1730`）把 N 封交给 `runBulk`（`:1802`，并发上限 8），每封成功后各触发一次完整的 `rebuildIndex()`。

**实测**

我按 `Conversation.swift` 的逻辑做了一份等价的 Swift 基准（`/tmp/lagoon-bench/bench.swift`，500 封、120 个线程、40 个发件人）：

| 构型 | 单次 regroup | 批量标已读 N 封的主线程总开销 |
|---|---|---|
| release (`-O`) | 3.16 ms | N=10 → **31.6 ms**<br>N=50 → **158 ms**<br>N=200 → **632 ms**<br>N=500 → **1580 ms** |
| debug | 6.90 ms | N=50 → **345 ms**<br>N=500 → **3451 ms** |

即：**选中 500 封标已读，主线程上有约 1.6 秒（release）/ 3.5 秒（debug）的纯分组计算**，全部发生在 `markReadOne` 里的 `setRead` 同步段——也就是每封请求返回时的那一瞬间。列表会在这个过程中反复重建分组、反复跳动。

**为什么是问题**

1. 这不是理论上的 O(n²)：上表是实测数字。简报页的服务器窗口是 500 条（`BriefingFeedView.swift:841` 的注释：「服务器一次最多回 500 条」），所以 500 封全选是**用户能达到的正常操作规模**。
2. 同一份代码库里已经有正确写法。`BriefingFeedView.markBulk`（`:1522-1606`）在批量标已读时是**一次** `mutateItems`：

   ```swift
   // Sources/Lagoon/Views/BriefingFeedView.swift:1563
   // One mutation for the whole batch: flipping the rows one at a time
   // would rebuild the cached lookups once per row — a quadratic sweep
   // over a 500-row feed for a change the user sees in one frame.
   // The same reason `markAllRead` does it this way.
   let succeededSet = Set(succeeded)
   if !succeededSet.isEmpty {
       mutateItems { rows in
           for i in rows.indices where succeededSet.contains(rows[i].message.remoteId) {
               rows[i] = rows[i].withRead(isRead)
           }
       }
   }
   ```

   简报页的 `markAllRead`（`:1960-1964`）也是同样的一次性 `mutateItems`。

   **同一个产品里的同一个动词，两处实现的复杂度差了 k 倍。** 列表页是漏改的。

**建议修法**

在 `MessageListView` 里把批量路径改成"一次 mutation"，与 `BriefingFeedView.markBulk` 对齐。`runBulk` 的 `body` 闭包需要能汇报结果，而不是就地改列表：

```swift
private func markSelected(isRead: Bool) {
    guard !selection.isEmpty else { return }
    guard !isBulkBusy else { return }
    let ids = selection
    let targets = messages.filter { ids.contains($0.remoteId) }
    selection.removeAll()
    isBulkBusy = true
    Task {
        let succeeded = await runBulkCollecting(targets) { m in
            await self.markReadOne(m, isRead: isRead)
        }
        // One mutation for the whole batch — see BriefingFeedView.markBulk.
        let succeededSet = Set(succeeded)
        if !succeededSet.isEmpty {
            mutateMessages { rows in
                for i in rows.indices where succeededSet.contains(rows[i].remoteId) {
                    rows[i] = rows[i].withRead(isRead)
                }
            }
        }
    }
}
```

`markReadOne` 需要改成"只写服务器、返回成功与否"，本地写入交给批量收尾那一次。

**另一条更省事的路（可选，但值得评估）**：`rebuildIndex()` 里的分组（`groupSections`）**不依赖**已读状态——它只按线程/发件人/日期分桶，已读只影响 `unreadOnly` 过滤和 `displayMessages` 的内容。所以：

- 标已读/未读**不改变分组结构**，只改变 `displayMessages` 的成员。
- 若 `unreadOnly` 为 false，标已读甚至**完全不改变 `displayMessages`**。

也就是说 `rebuildIndex()` 里唯一需要重算的分组结果，在"标已读"这个动作下是**恒等的**。一个更精确的修法是给 `rebuildIndex()` 拆出"哪部分输入变了"的判定（像 `rebuildSections()` 已经做的那样，`:1517-1525`），标已读只走"内容变了但分组没变"的那条路。

**验证方式**

- 性能测试（`swift test --enable-performance-testing`）：构造 500 封的列表，调用批量标已读，断言总主线程分组耗时 < 50 ms。或者更简单也更稳：断言 `rebuildIndex()`（或 `groupSections`）在批量路径上**被调用了一次**，而不是 N 次——这可以通过给 `groupSections` 加一个注入计数器来实现。
- 源码级守则测试：断言 `MessageListView.swift` 里 `markReadOne` 内部**没有**调用 `setRead`/`mutateMessages`。注意 `setRead`（`:1079`）还被别的路径用（`onReadStateChange` 回调，`:1021`），所以不能断言"`setRead` 不存在"，只能断言"`markReadOne` 的方法体内没有 `setRead(`"——**必须先定位 `private func markReadOne(` 再取其方法体**。

## 四、P3 — 整洁性

### S3-05 · 三处注释把 `.background` 说成"兄弟图层"，与 SwiftUI 实际语义相反

| 项 | 内容 |
|---|---|
| **文件:行** | `Sources/Lagoon/Views/BriefingFeedView.swift:807-811`<br>`Sources/Lagoon/Views/BriefingFeedView.swift:855-858`<br>`Sources/Lagoon/Views/MessageListView.swift:791-794` |
| **严重度** | P3（整洁性；错误前提会误导后续改动） |

**问题**

三处注释的核心断言都是："`.background` 是兄弟图层，RootView 给整个界面加的 `.disabled()` 到不了这里"。

第一节的实测结论已经给出答案：**父层的 `.disabled(true)` 会传到 `.background` 层，并且会抑制那里的 `.keyboardShortcut`。** 探针（`/tmp/bgprobe`）的两种形状都是如此：

```
LOG: ["A-control-fired", "B-control-fired"]
  A-disabled   fired? NO      ← 父层 .disabled(true) 抑制了 .background 层的 ⌘A
  A-control    fired? YES
  B-disabled   fired? NO
  B-control    fired? YES
```

**为什么是问题**

代码本身是**安全的**——`!isVisible` 门是冗余的双保险，不是承重结构。所以这不是功能缺陷，是**注释在陈述一个假事实**。

但它的代价是实打实的：

1. **误导后续改动。** 下一个人按注释推理："既然父层的 `.disabled()` 到不了 `.background`，那我在这里加一个新的 `.disabled()` 也到不了子视图"——于是写出无法生效的门。这个推理链已经在本项目里发生过一次（`SurfaceShortcutOwnershipTests` 的注释说"两处 `.disabled()` 会丢掉第一个"，而实际上 `.disabled()` 是组合语义，所以"必须写成一次"这个约束是虚构的）。
2. **误导测试。** 同一句错误前提被抄进了 `Tests/LagoonTests/SurfaceShortcutOwnershipTests.swift:44-49` 和 `Tests/LagoonTests/BriefingMultiSelectTests.swift:490-496` 的文档注释（见第六节）。
3. **错误的注释比没有注释更贵**，因为读代码的人会**信它**并跳过验证。

**建议修法**

改成陈述实测事实：

```swift
// The parent surface's `.disabled(surface != .briefing)` does reach this
// `.background` layer — SwiftUI's `.disabled` writes `isEnabled` into the
// environment, and `.background` inherits the environment (verified with a
// PreferenceKey probe + NSEvent.performKeyEquivalent). This gate is
// therefore redundant, not load-bearing. It stays because it makes the
// intent explicit at the point of the binding, and because it keeps the
// shortcut inert even if the surface is ever hosted somewhere that does
// NOT disable the parent.
```

**建议同时做的一件事**：把这个实测结论写进 `docs/` 的一份共享笔记（或 `.memory/`），避免下一轮审查再次从"惯例"出发重新推导一遍——这正是本轮开头那条"前提一"被误信的原因。

**验证方式**

- 无需测试（这是注释修正）。
- 但**必须同步修正两个测试文件的文档注释**（见 S3-07），否则错误前提会继续在测试里存活。

### S3-07 · 两个测试文件的文档注释写入了**事实错误的** `.disabled()` 前提

| 项 | 内容 |
|---|---|
| **文件:行** | `Tests/LagoonTests/SurfaceShortcutOwnershipTests.swift:44-49`<br>`Tests/LagoonTests/BriefingMultiSelectTests.swift:490-496` |
| **类型** | 假绿风险（错误前提会导向错误的后续改动） |

**问题**

两处注释内容完全一致：

> *"The gate is matched on *containing* `!isVisible`, not on being exactly `.disabled(!isVisible)`: a shortcut may carry a second condition (the delete shortcut is also gated on the account having a trash folder), and the two must be **one** `.disabled` call — SwiftUI's `.disabled` overwrites the environment value rather than composing with it, so two stacked calls would silently drop the first."*

**这句话的后半段是事实错误**（见第〇节的三路实测证据）：

- `.disabled()` **是组合语义**（`$0 && !disabled`），不是覆盖语义。
- 所以"两处叠加的 `.disabled()` 会丢掉第一个"**不成立**。
- 所以"必须写成**一次** `.disabled(a || b)`"这个约束**是虚构的**。

**为什么是问题**

这个错误前提会产生三个具体后果：

1. **它让"写成一次"看起来是硬约束。** 但既然 `.disabled()` 组合，把两个条件写成两次 `.disabled(a)` + `.disabled(b)` 在语义上是**等价的**。测试的注释却宣称这会出错——于是未来有人看到两处 `.disabled()` 时会以为有 bug 而去"修"它，或者反过来，把合法的两处写法误当成 bug 报出来。
2. **它会诱导出错误的架构判断。** 结合 `BriefingFeedView.swift:807-811` 那个同样错误的"`.background` 是兄弟图层"前提，读者会推断："SwiftUI 的环境传播在 `.background` 处断开、在 `.disabled` 处覆盖"——**这两个前提都是反的**。正确的事实是：`.background` **继承**环境，`.disabled` **组合**环境。
3. **它把一个无法验证的前提写成了测试的依据。** 测试真正的意图（"每个共享快捷键必须有自己的可见性门"）是好的、是对的；错的只是它给出的**理由**。

**建议修法**

保留意图，替换理由：

```swift
/// The gate is matched on *containing* `!isVisible`, not on being exactly
/// `.disabled(!isVisible)`: a shortcut may carry a second condition (the
/// delete shortcut is also gated on the account having a trash folder).
///
/// Note: SwiftUI's `.disabled(_:)` *composes* — it writes
```

### S3-08 · `CapabilityGatingTests` 用固定**字符数**窗口界定函数体，边界可能跨到下一个声明

| 项 | 内容 |
|---|---|
| **文件:行** | `Tests/LagoonTests/CapabilityGatingTests.swift:40-55`、`:62-73`、`:80-91`、`:97-108`（300 字符窗口）<br>`Tests/LagoonTests/CapabilityGatingTests.swift:117-143`（6000 字符窗口）<br>`Tests/LagoonTests/CapabilityGatingTests.swift:149-160`（400 字符窗口） |
| **类型** | 假绿风险（边界依赖格式，而非依赖语义） |

**问题**

`ViewSource.code(after:in:limit:)`（`Tests/LagoonTests/RowChromeAndBannerTests.swift:297-306`）的实现是：

```swift
static func code<S: StringProtocol>(
    after index: S.Index,
    in source: S,
    limit: Int
) -> String {
    source[index...].prefix(limit)          // ← 字符数，不是行数，不是声明边界
        .components(separatedBy: "\n")
        .filter { !$0.trimmingCharacters(in: .whitespaces).hasPrefix("//") }
        .joined(separator: "\n")
}
```

`limit` 是**字符数**。所以"这个窗口覆盖的是哪个声明"完全取决于那个声明恰好有多长、以及文件里后面接着什么。

**逐条核对当前的实际边界**（我按 Swift 的 `prefix(limit)` 语义重算了一遍）：

| 测试 | 锚点 | 窗口实际覆盖到 | 结论 |
|---|---|---|---|
| `test_theListGatesDeleteOnTheTrashFolder` | `MessageListView` 的 `private var canDelete: Bool` | 刚好是 `canDelete` 这个 computed property 的完整函数体 | ✅ 边界正确，但**只差几个字符**就会溢出到下面的 `canPurge` |
| `test_theListGatesPurgeOnUIDPlus` | `MessageListView` 的 `private var canPurge: Bool` | `canPurge` 函数体 + 后面约 200 字符 | ✅ 当前正确 |
| `test_theDetailViewGatesDeleteOnTheTrashFolder` | `MessageDetailView` 的 `canDelete` | 刚好是函数体 | ✅ |
| `test_theBriefingFeedGatesDeleteOnTheTrashFolder` | `BriefingFeedView` 的 `canDelete` | 刚好是函数体 | ✅ |
| `test_theRowMenuDisablesDeleteAndPurge` | `private struct RowChrome` | 6000 字符 = **118 行**，从 L2359 到 **L2476**（全文 2535 行） | ⚠️ 见下 |
| `test_theBulkBarDisablesDelete` | `BulkActionBar` 的 `Button(role: .destructive, action: onDelete)` | 400 字符 | ✅ |

**具体风险点**

1. **`canDelete` 的 300 字符窗口只差一点点就溢到 `canPurge`。** 第一个测试断言 `body.contains("allowsDelete")` **且** `!body.contains("allowsPurge")`。当前窗口恰好在 `canPurge` 之前截断（`canDelete` 的函数体是 4 行 ≈ 130 字符，加上前后空白约 140 字符，距 300 还有余量）。但只要有人在 `canDelete` 和 `canPurge` 之间插一段注释或另一个声明（比如加一个 `canArchive`），`allowsPurge` 就会落进窗口，测试**变红**——而这**不是缺陷**，是窗口太宽。反过来，如果有人把 `canDelete` 的实现从 `allowsDelete` 改成别的（比如 `capabilities.canTrash`），测试**会变红**（正确）。

   **这里的风险是"假红"而不是"假绿"**，但方向同样重要：一个因为格式变化而变红的测试，会被下一个人"修"成更宽的窗口，然后假绿就来了。

2. **`RowChrome` 的 6000 字符窗口覆盖了整个 `RowChrome` 类型（到 L2473 结束），但 `RowChrome` 之后还有 60 行的 `Identifiable` 包装类型。** 当前 `.disabled(!canDelete)`（L2468）、`.disabled(!canPurge)`（L2441）、`l10n.deleteUnavailable`（L2469）、`l10n.purgeUnavailable`（L2442）确实都在窗口内，所以测试是绿的。但这四个断言是**"某个 6000 字符的窗口里存在这些字符串"**，而不是"**这个按钮**上有这个门"。窗口里还有另外两个 `.disabled(...)` 吗？我核对了：`RowChrome` 内只有这两处 delete/purge 相关的 `.disabled`。所以当前**内容**是对的，但**边界**是脆的——把 `RowChrome` 的菜单再写长 1000 字符（比如加一个「转发」按钮），或者把 `RowChrome` 挪到文件更早的位置，窗口边界就会漂移。

3. **同类的"全文件首次匹配"还有 106 处**（`grep -rn "range(of:\|firstIndex(where:\|occurrences(of:" Tests/LagoonTests/*.swift | wc -l` → 106）。其中相当一部分是**唯一锚点**（比如 `source.range(of: "private func performAcceptedAdvice(")`），这类是安全的：锚点字符串在文件里唯一，首次匹配 = 唯一匹配。**真正危险的只有锚点字符串在目标文件里出现多次的那些**，以及像 `CapabilityGatingTests` 这样"锚点唯一但窗口是固定字符数"的。

**建议修法**

把 `ViewSource.code(after:in:limit:)` 补一个**按声明边界**截断的变体，并让能力门测试改用它：

```swift
/// The body of the declaration that starts at `index`, up to the
/// matching closing brace — not a fixed character count.
static func declarationBody<S: StringProtocol>(
    after index: S.Index,
    in source: S
) -> String { ... }
```

这样"这个门读的是 `allowsDelete` 还是 `allowsPurge`"就由**语法边界**决定，而不是由 `canDelete` 恰好有多短决定。

同时：对锚点字符串在目标文件里出现多次的情况，**遍历所有出现位置逐个断言**，而不是取第一个。

**验证方式**

给 `ViewSource` 的新 helper 喂合成源（沿用 `RefreshGateTests.test_theMatcherSeesEveryShapeItClaimsTo` 的模式，`:249-284`）：构造一个"目标声明后面紧跟着另一个含相反关键字的声明"的源，断言 helper **不会**把后者的内容吸进来。

## 六、经核实不成立

以下候选都经过追查，**不构成缺陷**。逐条给出证据与理由，避免下一轮重复劳动。

### 1. 叠放的 `.disabled()` 调用 —— 任务书指定的主攻方向，本项目 **0 处**

- **全仓 `.disabled(` 调用点：65 处**（`Sources/**/*.swift`）。

- 而且——**即使有叠放也不会丢条件**：`.disabled()` 是组合语义（第〇节三路实测）。
- 唯一"形似"的 `BriefingFeedView.swift:823` / `:826` 是**同一个 `VStack` 里两个不同 `Button` 的各自的门**，不是同一个按钮上的两次 `.disabled()`。

**结论**：任务书的前提一在本 SDK 上不成立，且本项目也没有这个 bug 类。

### 2. `.background` 不继承父层 `.disabled()` —— 前提反了，实测相反

- 探针 `/tmp/bgprobe`：`A-disabled` / `B-disabled` 两种形状的 ⌘ 快捷键**都**被父层 `.disabled(true)` 抑制，控制组都触发。

- 反过来说，**如果**前提成立，那些门就是承重结构、绝不能删。二者必居其一——实测站在"冗余"这一边，所以**删除它们是安全的**，但保留也无害。

### 3. `SearchSheet` 逐字符触发网络请求 —— 不存在

### 5. `ObservableObject` 在每次渲染时重建 —— 不存在

- **结论**：没有"struct 持有 class 实例作为普通属性导致每次更新重建"的情况。

### 6. `@Published` 在主 actor 之外被改 —— 不存在

### 7. `View.body` 里的 `await` —— 不存在

### 9. `noticeBanner` 自动消失的竞态 —— 不存在

- `NoticeBannerModifier`（`Sources/Lagoon/Views/NoticeBanner.swift:200-209`）：

  ```swift
  dismissTask?.cancel()

  dismissTask = Task { @MainActor in ... }
  ```

  `cancel()` 在 `guard` **之前**，所以旧任务一定先被取消再决定是否排新任务——不存在"旧任务在新 banner 到位后才醒来把新 banner 清掉"的竞态。

### 10. `MessageListView.hoverTask` 在视图消失时不取消 —— 已经修了

- `.onDisappear { hoverTask?.cancel(); hoverTask = nil }`（`MessageListView.swift:888-891`），注释也写明了原因。
- `hover(_:)`（`:237-253`）本身每次都先 `hoverTask?.cancel()`，且 Task 体内有 `guard !Task.isCancelled else { return }`。
- **结论**：干净。上一轮审查报告（`docs/审查-SwiftUI代码-2026-10-20.md` P1-07）报的这条，**当前代码里已经不存在**。

### 11. `HTMLMessageView` 的延迟加载会覆盖新文档 —— 已排除

初看 `updateNSView`（`HTMLMessageView.swift:556-565`）的未受控 `Task` 像个竞态：两次 `updateNSView` 各自 spawn 一个 Task，两者都 `await Self.ruleListReady()`，后恢复的那个把先恢复的覆盖掉。`await Task.value` 的等待者确实是 **LIFO** 恢复（我实测 5/5 次都是 `["B-load-v2", "A-load-v1"]`），所以"后写的文档先加载"。

但按真实时序跑完整个流程后**不构成缺陷**：

- 实测 `WKContentRuleListStore.compileContentRuleList` 冷启动 **0.5–3.1 ms**（`/tmp/ruletime`）。
- 因此 `blocksRemoteContent` 在第一封邮件的 `updateNSView` 之前几乎必然已经为真 → 走**同步**加载路径 → 根本不存在两个延迟 Task。
- 即使在延迟路径下，我用等价模型跑完"延迟优先"和"同步优先"两种变体（`/tmp/htmlprobe`），**最终显示的都是带 inline image 的新文档**——因为延迟路径里的 Task 在 `await ruleListReady()` 之后才追加自己的文档，而同步路径的文档追加得更晚。

**结论**：这是一个**代码气味**（未受控的 Task、理论上可能活过视图），但**没有可证实的错误行为**。不列为缺陷。若要加固，把那个 Task 存进 `Coordinator` 并在 `dismantleNSView` 里取消即可（`Coordinator` 已有 `measureTask` / `fallbackTask` 的取消模式，`:292-297`）。

### 12. `MessageDetailView.sentNoticeDismiss` 未在视图消失时取消 —— 危害为零

- `sentNoticeDismiss`（`MessageDetailView.swift:89-90`、`:1371-1379`）是一个 6 秒后把 `sentNotice` 置 `nil` 的 Task。
- 视图消失后它醒来写的是一个 `@State`——SwiftUI 会把它丢弃，**不会崩溃、不会污染别的视图**（`sentNotice` 是这个 view 私有的 `@State`，不是 `@EnvironmentObject`）。
- **结论**：无用户可见影响，不构成缺陷。

### 13. 视图层的 122 个 unstructured `Task {}` 未在消失时取消 —— 逐个核对后无一处构成缺陷

Views 层共 122 处 `Task { }`（不含 `Task.detached` / `Task { @MainActor`）。逐类核对：

| 类别 | 判定 |

**结论**：没有"一个 Task 无限循环且强持有 self"、没有"一个 Task 在模型层活得比它的主人久"、没有"两个并发写同一个 `@Published`"。

### 14. `RefreshGate` 的"代次/epoch 计数器用在了正确的位置吗" —— 用对了，但漏了一条路径

- `guard generation == refreshGate.generation else { return }` 出现在 `BriefingFeedView.swift:1875`、`:1888` 和 `MessageListView.swift:1136`、`:1147`、`:1175`、`:1186`——**每个可能提交载荷的分支之前**。
