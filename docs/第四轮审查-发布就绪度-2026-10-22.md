## 0. 一句话结论：这东西现在能不能拿出去给人看？

**不能。**

不是因为功能不够，而是因为**交付链是断的**：仓库是公开的，但**没有任何一个别人能拿到的产物**——没有 Release、没有下载链接、CI 不产出安装包、`dist/` 被 gitignore；而 `dist/` 里现存的 `Lagoon.app` 是 **10 月 20 日的旧构建**，它**缺了「邮件」整条菜单**（文档里白纸黑字写着这条菜单）、**缺了 `lagoon://` 深链接注册**，打开后第一屏还会被 macOS 的**钥匙串密码弹窗**顶死。

更要命的是，就算把包递到别人手上，**对方第一次双击它就会看到一个要求输入「登录」钥匙串密码的系统弹窗**，整个 App 卡在启动画面动弹不得——而这件事只写在 `scripts/build-app.sh` 的一行代码注释里，用户的 runbook（《启动说明》《使用说明》）里一个字都没有。

一句话：**这是一个"自己能跑、但还不能给别人看"的项目。** 核心代码和守卫体系（1451 个测试全绿）质量不错，但**发布面几乎是空白**，而且**已经推上 GitHub 的那个 `main` 恰好还没红**——因为触发守卫误报的两个新文件还没入库。**这批工作一提交，CI 就转红；这批工作一交付，别人就会撞上钥匙串弹窗。**

（补充一条边界：以上结论全部基于**发布与交付面**。功能是否够用、交互是否顺手、存储是否可靠，不在本报告范围内——那些由功能/UX/数据层负责。）

#### RR-01　**没有任何一个别人能拿到的产物**

**现象**
GitHub 仓库是**公开**的（`hibernate-pano/lagoon-email`，`visibility: PUBLIC`），但：

- `gh release list` → **空**，一个 Release 都没有；
- `dist/` 在 `.gitignore:15`，所以 `Lagoon.app` / `.dmg` **不在仓库里**；
- `.github/workflows/ci.yml` 只跑 `run-all-tests.sh`，**不构建 app、不构建 dmg、不上传产物、不监听 tag**；
- 没有 `LICENSE`、没有 `CHANGELOG`；
- README 里**没有一张截图**，仓库 description **是空字符串**。

结果：一个人打开这个公开仓库，读完 15KB 的 README，**找不到任何可以下载或运行的东西**。

**证据**
```
$ gh repo view hibernate-pano/lagoon-email --json visibility,isPrivate,description
{"description":"","isPrivate":false,"visibility":"PUBLIC"}
$ gh release list -R hibernate-pano/lagoon-email
(空)
$ git check-ignore -v dist/Lagoon.app dist/Lagoon-v3.0.1.dmg
.gitignore:15:dist/    dist/Lagoon.app
$ ls LICENSE* CHANGELOG*
(无)
$ grep -nE '!\[|<img|\.png' README.md
(无)
```
`.github/workflows/ci.yml:11-26`（整个 workflow 只有 26 行，唯一的 step 是 `bash scripts/run-all-tests.sh`）

**为什么这会让人看出不成熟**
一个"成熟产品"的最低交付形态是：**一个能下载、能拖进 /Applications、能双击起来的文件**。现在连"能下载"这一格都是空的。一个公开仓库对陌生人说"看，这是我的邮件客户端"，对方点进去只看到一堆文字和一行 `bash scripts/build-app.sh`——那不是产品，那是源码。

**怎么修**
1. `.github/workflows/ci.yml` 追加一个 `release` job：`on: push: tags: v*` → 跑 `scripts/build-app.sh` + `scripts/build-dmg.sh` → `gh release create` 上传 `.dmg`（附 sha256）。
2. `README.md` 顶部加一段「下载」小节 + **一张首屏截图**（用 `docs/release-evidence/04-钥匙串授权页-新构建.png` 换一张正常的收件箱截图更好）。
3. `gh repo edit --description "Lagoon —— macOS 上的 AI 分诊邮件客户端"`。
4. 加 `LICENSE`（MIT）与 `CHANGELOG.md`（从 34 个 tag 里回填 v3.2.0 一节即可）。

#### RR-02　**`dist/Lagoon.app` 是旧构建，缺了「邮件」整条菜单和 `lagoon://` 深链接**

**现象**
`dist/` 现存的 `Lagoon.app` 是 **2026-10-20 07:29** 的构建，`CFBundleVersion = "1"`。当前 HEAD 是 `359498a`（2026-10-21 12:06）。

`Sources/Lagoon/Platform/LagoonAppCommands.swift`（整个应用菜单所在文件）是在 **10-21 的 commit `24b3152`** 才加进来的 —— **旧 bundle 里根本没有这个文件对应的代码**。实测确认：

| | 旧 `dist/Lagoon.app`（10-20） | 现树新构建 |

| 菜单栏 | 文件 / 编辑 / 显示 / 窗口 / 帮助 | 文件 / 编辑 / 显示 / **邮件** / 窗口 / 帮助 |

**为什么这会让人看出不成熟**
这正是"版本号对得上、功能对不上"的最阴险形态——**版本号写着 3.2.0，看起来是最新的**。一个懂行的人打开 bundle 看 Info.plist，会发现 `CFBundleVersion = "1"`；一个不懂行的人双击它，会发现 ⌘F 搜不了、⌘K 调不出命令面板、`lagoon://` 链接点了没反应。**每一个"文档里写了但用不了"的项，都是在替产品说话。**

**怎么修**
1. 立即：`bash scripts/build-app.sh` 重建 `dist/Lagoon.app`（已验证 exit 0）。
2. 根治：**让 `dist/` 不可漂移**。二选一——
   - (a) 把 `dist/` **从 `.gitignore` 移出**，只提交 `dist/Lagoon.app`（41MB，git 能扛）或只提交 `dist/Lagoon-<版本>.dmg`；
   - (b) 更干净：`ci.yml` 的 release job **在 tag 上构建并发布**，本地 `dist/` 明确降级为"临时产物"，并在 `README.md` / `docs/启动说明.md:5` 里写清"官方安装包从 GitHub Releases 下载，仓库里的 dist/ 只是你自己构建的产物"。
3. 加一条守卫：在 `scripts/check-version.sh` 里加一条 **`CFBundleVersion` 必须是 7+ 位 git hash** 的检查（现在 `"1"` 能蒙混过关），或者在 `build-app.sh` 之后跑 `codesign -dvvv` 断言 cdhash 与上次不同（防止误用旧 bundle）。

#### RR-03　**ad-hoc 签名 → 首次启动被 macOS 钥匙串密码弹窗顶死，而这件事用户文档里一个字都没有**

**现象**
这是本次审查**最重要的一条**，且是实拍复现的。

Lagoon 用 ad-hoc 签名（`Signature=adhoc`，`TeamIdentifier=not set`）。每次重建 bundle，**cdhash 都会变**，旧 build 写进钥匙串的 `lagoon.*` 条目的 ACL 就对不上了。下一次启动，系统会弹出一个**模态**对话框：

> Lagoon想要使用你储存在钥匙串的 "lagoon.accountId" 中的机密信息。
> 若要给予许可，请输入"登录"钥匙串的密码。
> `密码: [____]`　`始终允许`　`拒绝`　`允许`

**而这个弹窗会挡住整个 App。** 实测：新构建启动后连着弹出 5 次这样的对话框（`lagoon.accountId` / `lagoon.tokenKey` / `lagoon.bodyKey` / `lagoon.apiTokenSecret` / 通用密码项），每次都要处理；在弹窗存在期间，**App 连「关于 Lagoon」都打不开**。

更糟的是：App 自己的 5 秒超时设计（`KeychainReader.swift:55,113-125`）只能让**Swift 代码**不卡住，**挡不住系统弹窗本身**——弹窗是 `SecurityAgent` 独立拥有的模态窗口，App 无权关闭它。

而 `docs/启动说明.md` 的「四、故障速查」表（47-53 行）里**没有这一行**；`docs/使用说明.md` 里也没有。用户视角就是：**双击 → 白屏 → 一个要密码的框 → 输了密码还是不动**。

**证据**
```
$ codesign -dvvv dist/Lagoon.app | grep -E 'CDHash|Signature'
CDHash=c941fd2851f50c42986e7ae83d46c4467d2f8a58
Signature=adhoc
$ # 重建前后 cdhash 变了：
旧 bundle:  CDHash=826d87a028057dd6418fa0bc24795e5dbbb244cf
新 bundle:  CDHash=c941fd2851f50c42986e7ae83d46c4467d2f8a58
```
实拍截图（存于 `docs/release-evidence/`）：
- `03-钥匙串弹窗挡住首启-新构建.png` —— 全新构建启动 10 秒后的实况：系统密码框 + 背后的空白启动窗；
- `01-钥匙串弹窗挡住首启-旧构建.png` —— 旧 bundle 的同一现象；
- `04-钥匙串授权页-新构建.png` —— 拒掉全部弹窗后，App 自己的「钥匙串需要你的授权」页；
- `02-首屏红字钥匙串错误-旧构建.png` —— 旧构建更进一步：连授权页都没走到，**首屏直接是「连接 QQ 邮箱」表单 + 一行红字**「读取已保存账号失败：钥匙串错误：用户已取消操作。(-128)」——**用户第一次看到一个新产品，第一眼就是一行红色的系统错误码**。

代码侧证据：`scripts/build-app.sh:52-59` 的注释**准确描述了这件事**（"every rebuild mints a new cdhash… the first launch after a rebuild may pop Keychain consent dialogs… an unanswered dialog looks like a blank hang"）——**但这段知识只存在于源码注释里，用户和运维都读不到**。

**为什么这会让人看出不成熟**
「双击一个 App，它先要我的登录钥匙串密码」——这在 2026 年的 macOS 上是**最典型的"自己家做的软件"信号**。普通用户看到密码框的第一反应是"这软件有病毒吗"，第二反应是删掉。而 App 自己的文案还写着「系统弹出的授权窗口**可能没有显示**」（`KeychainAuthorizationView`）——在 ad-hoc 签名下，这个窗口**从来都会显示**，文案在骗人。

**怎么修（按依赖顺序）**
1. **文档先行（当天可做，零风险）**：
   - `docs/启动说明.md`「四、故障速查」表**新增一行**：「打开后卡在空白窗口 + 弹『输入登录钥匙串密码』→ 点「允许」（一次性）或输入登录密码点「始终允许」；这是临时签名的已知行为，不是坏了」；
   - `docs/使用说明.md`「一、你需要准备什么」表**新增一行**：macOS 14+、**首次启动需要授权钥匙串**；
   - 在 `docs/启动说明.md:76`「安全须知」里，把「ad-hoc → 每次重建都要重新授权」的后果写进去（现在只写了"仅限本机使用"）。
2. **修文案**：`Sources/Lagoon/Views/KeychainAuthorizationView.swift` 里「系统弹出的授权窗口可能没有显示」→ 改成「**你的钥匙串里已经存着上一版 Lagoon 留下的密钥；因为当前是临时签名，系统会要求你重新授权一次。点『允许』即可。**」

#### RR-04　**`ci-guardrails.sh` 当前是红的，两条误报把整条 CI 拦死**

**现象**
```

Sources/Lagoon/Localization/L10n+Compose.swift:211: sql-interpolation
Tests/LagoonTests/ComposeSheetHonestyTests.swift:406: sql-interpolation

`scripts/run-all-tests.sh:57` 是 `bash scripts/ci-guardrails.sh`（`set -euo pipefail`），**它在第 2 步就中止**，后面的 1451 个测试根本不会跑。而 `.github/workflows/ci.yml:25-26` 跑的就是这个脚本。

804:  done < <(find Sources Tests -type f 2>/dev/null | sort)
$ sed -n '208,213p' Sources/Lagoon/Localization/L10n+Compose.swift

$ sed -n '404,407p' Tests/LagoonTests/ComposeSheetHonestyTests.swift
                "\(view) checks each file but not the total — the server's limit is on the total"

#### RR-05　**没有 Developer ID 签名路径、没有 hardened runtime、没有公证脚本 —— 按现有指引走公证必然被拒**

TeamIdentifier=not set
（无 entitlements 段）
$ grep -n "notarytool\|stapler" scripts/build-dmg.sh
81:echo "     xcrun notarytool submit \"$DMG\" --keychain-profile \"lagoon\" --wait"
83:echo "     xcrun stapler staple \"$DMG\""
```
`docs/启动说明.md:76` 与 `docs/使用说明.md:281` 都写着「分发需要 Developer ID 签名 + 公证」——**但仓库里没有一条能走通这句话的路径**。

**为什么这会让人看出不成熟**
「分发需要公证」这句话在 README / 使用说明 / 启动说明里出现了 **3 次**，但**一次都没做成过**。对懂行的人，这等于"我们还没发过"。而 Gatekeeper 未公证的双击体验（"无法验证开发者"）是外行第一次遇到时的第一道劝退墙。

**怎么修**
1. `scripts/build-app.sh` 加签名分支（新增 `scripts/sign-release.sh` 更干净）：

   # scripts/sign-release.sh —— 需要 Developer ID Application 证书

            --sign "$DEV_ID" --entitlements Support/Lagoon.entitlements \

3. 新增 `scripts/notarize.sh`：
   ```bash
   xcrun notarytool submit "$DMG" --keychain-profile "$PROFILE" --wait
   xcrun stapler staple "$DMG"
   xcrun stapler validate "$DMG"
   ```
   并让 `build-dmg.sh` 在签名完成后**自动调用**它（而不是 `echo` 提示）。
4. 在 `docs/启动说明.md:76` 把"分发需要 Developer ID 签名 + 公证"改成"**分发流程见 `scripts/release.sh`**"，并把 `--keychain-profile` 的创建命令（`xcrun notarytool store-credentials "lagoon" ...`）写进文档。

"成熟产品"的交付面有一个隐含标准：**有一个确定的、可以指着说"就是这一版"的东西**（一个 tag / 一个 Release / 一个 checksum）。现在**没有**。任何人（包括你自己）问"现在线上跑的是哪个版本"，答案只能是"工作树里那些还没提交的东西"。

**怎么修**
1. 交付前：`git checkout -b release/3.3.0` → 全量跑一遍 `bash scripts/run-all-tests.sh`（先修 RR-04 让它能跑完）→ 提交 → 打 tag。
2. `scripts/check-version.sh` 扩展：校验 `Support/VERSION` 与**最新 tag** 一致（或至少提示落后）。
3. CI 增加 `on: pull_request` 之外的一个 **`on: push: branches: main` 的构建 job**，保证主干随时有一个可产出的 bundle。
