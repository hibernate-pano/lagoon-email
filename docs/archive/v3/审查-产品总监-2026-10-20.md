## 0. 结论先行

**产品实际兑现了什么**

| 承诺 | 兑现程度 | 依据 |
|---|---|---|
| 每天开两次、10 分钟清零 | **部分兑现** | 简报分组 + 行内归档 + ⌘E 归档并下一封 + ⌘Z 撤销，这条闭环是真的（`BriefingFeedView.swift:790`、`MessageDetailView.swift:341`、`UndoController.swift:129`）。但见 P0-02：简报页没有批量操作、没有多选，一次只能清一封。 |
| AI 分诊 | **兑现了约 60%** | 分组 ✅、建议 ✅、理由 ✅、置信度 ✅、搜索可召回 AI 判断 ✅（`DraftRoutes.swift:341-342`）。但"清零"最关键的一步——**批量接受建议**——不存在（P0-02 / P1-08）。AI 也**不读正文**做分类（见 P1-03，注意这是**有意的设计**，不是疏漏）。 |
| 本地优先、数据不出本机 | **兑现（有一处例外）** | SQLite 内嵌、Keychain 存密钥、AES-GCM 密封凭据（`AccessTokenCipher.swift:20`）。**但邮件正文是明文落库**（P0-01）。 |
| 多账号 | **只兑现了一半** | 账号能加、能切、能并发同步（`Runtime.swift:141-147`），但 UI 无法删除账号（P2-01）、搜索/简报只对当前 active 账号生效（P1-11）。 |
| "AI Inbox Operating System" | **名不副实** | 这是一个**单账号、单服务商（QQ）、纯文本、无附件发送**的邮件客户端，AI 是分类器 + 摘要 + 草稿生成器三件事的集合，不是"操作系统"。 |

**最严重的三件事**

1. **P0-01 邮件正文以明文存进 SQLite** —— 这是本地优先产品的**信任底线**问题，且与项目自己的规范（2026-09-09 总设计 §6.6 rule 5）直接冲突，而 README 和使用说明里对"加密"的表述会让用户以为正文也是加密的。
2. **P0-02 简报页没有批量操作** —— 与产品核心承诺直接冲突。"10 分钟清零"意味着一次处理几十封，而简报页一次只能归档一封。全部邮件页有 `BulkActionBar`（`MessageListView.swift:633`），简报页没有。这是**唯一一处**用户每天做两次的主界面缺少批量能力。
3. **P0-03 侧边栏的计数和聚合规则永远是空的** —— `RootView.refreshSidebarData()` **从来没有被调用过**（它在 2026-10-06 的三栏重写 `13551b2` 中被连同 `.task(id: accountId)` 一起删掉，函数体留了下来）。用户看不到任何未读数、已归档数，也看不到自己建的聚合规则。

## 1. 问题清单

- **P1** — 显著削弱核心价值，或关键旅程断裂

### P0-01 · 邮件正文以明文存进 SQLite，与项目自己的安全规范冲突

| | |
|---|---|
| **严重度** | P0 |
| **问题** | `message_bodies` 表的 `body_text` / `body_html` 是**明文 TEXT**（`LagoonDatabase.swift:320-332`），写入路径 `BodyStore.put` 直接把 `body.text` 绑进 SQL（`BodyStore.swift:96-100`）。全项目**只有凭据**被 AES-GCM 加密（`AccessTokenCipher.swift:20`，用于 `accounts.credentials`），正文没有任何加密层（`grep -rn "sqlcipher\|pragma key\|encrypt" Sources/LagoonKit/LagoonDatabase.swift Sources/LagoonServer/Storage/BodyStore.swift` → 0 命中）。 |
| **证据** | 规范要求：`docs/superpowers/specs/2026-09-09-lagoon-email-design.md:204` —— "Message bodies never leave the client unencrypted. Server stores ciphertext + metadata only… unit test that asserts no plaintext body field exists in any server-side table"。实际：`Sources/LagoonKit/LagoonDatabase.swift:320-332`（`body_text TEXT NOT NULL DEFAULT ''`）、`Sources/LagoonServer/Storage/BodyStore.swift:76-100`（明文写入）。规范要求的**那条单测也不存在**（`grep -rn "plaintext" Tests/` → 只命中 `AccessTokenCipherTests.swift`，无正文加密断言）。<br>**说明:** V2 设计（`2026-09-23-v2-inbox-os-final-design.md:24`）明确推翻了"正文不落库"、改为"body 全量落库 + 全文索引"，但**没有同时推翻 §6.6 rule 5 的加密要求**。README:132 也只说"Message bodies are stored in the local SQLite store"，没说是否加密。 |
| **建议动作** | 二选一，**不能拖**：(A) **实现加密** —— 复用现成的 `AccessTokenCipher`（同一把 Keychain 密钥），在 `BodyStore.put/get` 里对 `body_text`/`body_html` 做 seal/open；数据库里存 base64 密文。代价极小（两个函数 + 一次迁移），因为加解密设施已经存在。(B) **改规范并改文案** —— 如果正文明文落库是有意决策（全文搜索需要明文 LIKE），就修改 `2026-09-09-lagoon-email-design.md:204` 的 rule 5，在 README 和使用说明里**明说**"邮件正文以明文存在本地数据库中，磁盘上的文件不需要密码即可读出"，并把该文件纳入"备份"章节的风险提示。**当前状态是第三种、最坏的一种：规范说加密，规范的实现没做，文案没说清，用户以为加密了。** |
| **预期收益** | 这是"本地优先"这个卖点的**兑现前提**。用户信任"数据在你机器上"的前提是知道机器上的数据长什么样。任何一份对外的分发材料（官网、商店页）如果暗示"加密存储"，而实际是明文 SQLite，那是**可被指出的失实陈述**。 |

| | |
|---|---|

### P1-03 · 分类不读正文是**有意的设计**，但它的代价没有被产品化

| | |
|---|---|
| **严重度** | P1 |
| **问题** | 分类 prompt 只喂 `id / from / read / ageDays / subject / snippet`（`AIGateway.swift:248-258`），**没有正文**。这**不是疏漏** —— 代码注释明确写着 "Only headers/snippet/age — never a body (spec §6.6 rule 5)"（`:247`），即"正文不入 AI 请求"是一条既定规范。**但这个取舍的代价从未被摆到台面上**：分类的准确率上限因此是"标题 + 首行采样"，而产品叙事说的是"AI 帮你分诊"。用户不会知道 AI 其实只看了标题。 |
| **证据** | `Sources/LagoonAI/AIGateway.swift:247`（规范引用）、`:248-258`（payload 构造）、`:270-280`（prompt）；对照 summary/draft 的 prompt 明确带 `Body:`（`:321-323`、`:375-377`），各取 12000 字符 |
| **建议动作** | **不建议**直接把正文塞进批量分类（成本会翻十倍，且违反 §6.6 rule 5 的隐私意图）。建议改成"分级处理 + 诚实披露"：(1) 对**启发式无法定论**的邮件（即 `BriefingReason.needsReply` 兜底分支，`Heuristics.swift:124`）单独走一次带正文的 LLM 调用，正文截断到 2000 字——这批量很小，token 可控；(2) 在"AI 设置"面板里明确说明"分类只看标题和摘要（不发正文）；生成摘要和草稿时会发送正文（最多 12000 字）"，并标注每种能力的调用次数。 |
| **预期收益** | 让"AI 分诊"的实际能力边界变得可信。当前既没兑现更强的分类，也没告诉用户它做不到什么——两头不占。而且 §6.6 rule 5 是隐私承诺，把它保留下来反而是产品资产，只要说清楚。 |

### P1-05 · 撤销只回退一步，且三条批量路径的撤销行为不一致

| | |
|---|---|
| **严重度** | P1 |
| **问题** | ⌘Z 走 `UndoController.undoLatest()`（`UndoController.swift:140-170`）：**有活跃 toast 时**走 `undo()`，会带上 `extraIds` 整批回退（`UndoController.swift:129-136`），这部分是对的；**没有 toast 时**（6 秒自动消失后，或用户按了 ×），fallback 到服务端取**最新的**一条可撤销动作 —— 一次批量操作产生的多条审计行时间戳几乎相同，`actions.first(where:)` 只取到其中任意一条，**其余 N-1 封留在原地**。<br>更严重的是**三条批量路径行为不一致**：`SenderSheet` 的批量归档/删除**正确**收集了 `extraIds`（`SenderSheet.swift:403-409`、`:327-334`）；但 `MessageListView.deleteAllMatching`（`:1661-1700`，"选择服务器上的全部 N 封"）和 `StackSheets.sweep`（`:356-384`，聚合规则一键清扫）**根本不弹撤销 toast**，只报一个 `ErrorCenter` 信息提示 —— 而使用说明第 53 行写着"每个动作都可 ⌘Z 撤销"。 |

| 6 | **签名** | 不存在 | 所有客户端 | ★★★★☆ 每次发信都要手打，直接影响迁移意愿 | P1-10 |
| 7 | **密送 / 多收件人（新建邮件）** | 新建只能单收件人 | 所有客户端 | ★★★☆☆ | P1-10 |
| 8 | **跨账号搜索** | 做不到 | 所有客户端 | ★★★☆☆ | P1-11, P1-06 |
| 9 | **线程视图**（在阅读窗里看整个会话） | 只有列表折叠，没有线程阅读 | Gmail / Outlook / Apple Mail | ★★★☆☆ 当前只能一封封看 | — |

| 11 | **重要标记 / 星标**（区别于"置顶"） | 只有置顶 | 所有客户端 | ★★★☆☆ | — |
| 12 | **规则（条件 + 动作）** | 被宪法明确否决 | Gmail / Outlook | ★★☆☆☆ **不做是对的** | — |
| 13 | **黑名单 / 拒收发件人** | 不存在 | QQ邮箱 / 网易邮箱大师 | ★★☆☆☆ | — |
| 14 | **阅读回执** | 不存在 | Outlook | ★☆☆☆☆ 隐私争议大 | — |
| 15 | **邮件优先级 / 重要文件夹** | 不存在 | Outlook | ★☆☆☆☆ | — |

## 3. 信息架构审查

### 3.1 导航模型：三层结构基本成立，但有一处断裂

当前模型（`Sidebar.swift:108-134`）：

```
智能视图          简报 / 全部邮件 / 未读 / 置顶
位置              已归档 / 已发送 / 废纸篓
自定义聚合        (用户规则)
```

**问题 1 — "自定义聚合"分区永远不渲染**（P0-03）。这是最严重的一条 IA 问题：**导航里有一个分区，但它的数据永远为空**，用户既看不到自己建的规则，也没有创建入口（唯一的创建入口在全部邮件页工具栏的 `rectangle.stack` 图标，`MessageListView.swift:383-388`）。

**问题 2 — 缺少"收件箱"**（P2-04）。"全部邮件"实际是收件箱。

**问题 3 — 规则行的标题错误**（P2-05）。`MessageListView.surfaceTitle` 对 `.rule` 返回"自定义聚合"而不是规则名。

**问题 4 — 侧边栏没有写动词，这是对的**（`Sidebar.swift:95-97`："It has no write verbs… A navigation column that could empty a folder on its own is a different product"）。这条设计判断值得保留。

### 3.2 概念矩阵：文件夹 / 分类 / 标签 / 规则 四者重叠

Lagoon 里有四个"把邮件归到一起"的概念：

| 概念 | 实现 | 用户可见名 | 谁能改 | 问题 |
|---|---|---|---|---|
| **简报分组** | `BriefingGroup` 枚举 | 简报的 5 个 Section | AI 分类 + 用户"改分组" | 分类是**判定的**，用户改的是**覆盖值** |
| **聚合规则** | `stack_rules` 表 | 自定义聚合 | 只能新建/删除 | 命名像"规则"但实际是过滤器（P1-12） |
| **改分组** | `ai_overrides` 表 | 改分组为… | 详情页 ⋯ 菜单 | 按**发件人**生效，但 UI 没说是按发件人生效（P2-13） |
| **置顶** | `message_pins` 表 | 置顶 | 列表/详情 | 是 flag 不是分类 |

**核心问题:** "改分组"在详情页是对**这一封信**操作的，但服务端存的是**按发件人**的，效果是**这个发件人的所有邮件**都变成那个分组。界面没说明（P2-13）。同时它和 `stack_rules` 语义重叠，存在两张表、两个 UI 名字。

### 3.3 命名一致性

| 位置 | 名称 | 问题 |
|---|---|---|
| `L10n.swift:94` | 全部邮件 | 实际是收件箱（P2-04） |
| `L10n.swift:841` | 自定义聚合 / `stackRulesHeader` | 同时是**分区标题**和（错误的）**规则行标题**（P2-05） |
| `L10n.swift:838` | 已归档（档案柜） | "档案柜"是个比喻，跟邮件客户端通用语汇不符；Gmail/Outlook/Apple Mail 都叫"归档" |
| `L10n.swift:615` | 建议提醒 | 对应的是一个不存在的能力（P1-02） |
| `Sidebar.swift:116` | 位置 | Gmail 叫"标签"，Apple Mail 叫"邮箱"，Outlook 叫"文件夹"。"位置"是新造的词，但内部一致，可接受 |

### 3.4 两个平行的"表面"（Briefing vs 全部邮件）边界模糊

README 说"Briefing Feed as the default surface"（README:185-187），V2 终态设计明确说过"**双 surface + 9 个 sheet** —— Briefing vs All 不该是平行世界，而是一个漏斗的不同切片"（`2026-09-23-v2-inbox-os-final-design.md:26`）。**这个目标没有达成**：两者是两套独立的列表实现（`BriefingFeedView` 1282 行 / `MessageListView` 1996 行），各有各的行组件、各自的选中模型、各自的快捷键。V2 设计里说的"⌘1-5 是 filter 切换，不是页面跳转"（`:34`）也没有实现 —— ⌘1–⌘5 在简报里是**跳转到分组并展开它**（`BriefingFeedView.swift:522-536`、`:566` 里的 `collapsedGroups.remove(group)`），不是切 filter。

实际后果：一个用户从简报点"归档"和从全部邮件点"归档"，走的是两条代码路径（`BriefingFeedView.archiveAndUndo` vs `MessageListView.archive`），UI 反馈不同（简报有滑动动画、全部邮件没有），撤销 toast 的文案也不同。这是 P0-02（简报没有批量）的根因。

## 4. 用户旅程断点分析

### 旅程 A：全新用户 → 第一次清零

| 步骤 | 现状 | 断点 | 严重度 |
|---|---|---|---|
| 1. 打开 App | 显示"正在启动服务器"→ ConnectView 表单 | 无产品说明，用户不知道这是什么 | P1-01 |
| 2. 填 QQ 邮箱 + 授权码 | 两段灰色小字指引，用户多半要去 QQ 网页版 | 指引重复且是 tertiary 灰色 | P2-08 |
| 3. 点"连接" | 1-3 秒探测 IMAP，成功后直接进简报 | **没有"你现在有 400 封邮件正在被分类"的过渡说明**，只有一个转圈（`BriefingFeedView.swift:440-457`） | 低 |
| 4. 看到简报 | 5 个分组，第一屏是"需要回复" | 分组是 AI 的判定，但**没有一行解释这个分组怎么来的**（`reasonText` 只在特定密度下显示） | 中 |
| 5. 看侧边栏 | **所有计数徽章都不显示，自定义聚合分区不渲染** | **P0-03** | **P0** |

| 7. 归档一封 | ⌫ 或 ⌘E，撤销 toast 出现 | 顺利 | — |
| 8. 清完 40 封 | **一封一封按** | **简报页无批量（P0-02）** | **P0** |

### 旅程 B：收到一封需要回复的邮件 → 回复

| 步骤 | 现状 | 断点 |
|---|---|---|
| 1. 发现新邮件 | **没有任何通知**（P1-09），只能自己打开 | 用户可能整天不知道 |
| 2. 找到它 | 简报"需要回复"分组 / 未读筛选 / 搜索 | 简报只覆盖 30 天窗口（P2-02）；搜索只搜当前账号（P1-11） |
| 3. 读 | 分栏阅读窗，j/k 走读，1 秒停留自动标已读 | 良好 |
| 4. 看 AI 建议 | 行内建议条，展开有理由 + 置信度 | 良好，但**没有"照做"按钮**（P1-08） |

| 6. 回复全部 | ⇧⌘R，Cc 来自原邮件的 To/Cc | 良好。但**无法加新的 Cc**（`replyCcRecipients` 只能从原信推导，`:507-515`） |
| 7. 发送 | ⌘↩，走 SMTP 465 | 顺利。**不能带附件**（P1-10） |

### 旅程 C：处理订阅噪音 → 退订

| 步骤 | 现状 | 断点 |
|---|---|---|
| 1. 找到噪音 | 简报"订阅噪音"分组（**默认折叠**，`Briefing.swift:29` `collapsedByDefault`） | 折叠时分组头**仍显示计数**（`BriefingFeedView.swift:414-436` 的 `groupHeader` 里 `Text("\(count)")` 无条件渲染），这点没问题；但整个 Section 不可滚动到达 |
| 2. 逐封退订 | 右键"一键退订" | **没有批量退订**。发件人排行面板是天然入口，但它明确拒绝批量操作（`SenderRankingSheet.swift:14-22`："No bulk archive, no bulk unsubscribe, no auto-rule"）—— 这是宪法原则的有意坚持 |
| 3. 退订生效 | 服务端执行 RFC 8058 或手动 | 顺利 |

> **这一段的断点:** "订阅噪音"这个分组本身就是为了批量清理而设计的，但它默认折叠、且只能逐封退订。**这里应该是全产品批量能力最强的地方，实际却最弱**（P0-02）。

### 旅程 D：搜索一封旧邮件

## 5. 商业与信任审查

### 5.1 做得好的地方（应保留）

- **密钥分层清晰**：AES-GCM 主密钥 + API token 在 Keychain（`EmbeddedServer.swift:26-52`），AI provider key 在 `lagoon.envJSON` Keychain 项（`AISettingsSheet.swift:201-205`），磁盘上没有明文密钥文件。
- **凭据密封**：`AccessTokenCipher` 加密 QQ 授权码存进 `accounts.credentials`，`GET /api/accounts` 不返回凭据（README:121-123）。
- **AI 密钥文案诚实**：`L10n.swift:954-958` 明确说"仅存于本机钥匙串，不会离开这台 Mac（**调用时随邮件文本发给模型服务商**）"。这个括号里的补充很重要，很多产品会藏起来。
- **预算封顶 + 披露**：`UsageBudget` 每月美元上限，超了明确报 `ai-budget-exceeded`；`aiSettingsBudgetHelp` 说"设为 0 表示不限制"。
- **远程图片不加载**：`HTMLMessageView.swift:407` 明确把"不加载远程资源"当作读回执防护，隐私立场正确。
- **不可逆动作有二次确认**：`pendingPurge` 用 `.alert` 而非 sheet（`MessageListView.swift:576-607`），且确认文案带上主题名。
- **两段式全选的克制**：`docs/使用说明.md:68` 说明 ⌘A 只选已加载邮件，要全选匹配条件下的全部需再点一次链接。这是为了避免"⌘A 然后 ⌘⌫"清空整个邮箱。**这是好设计，应当保留**（P0-02 加简报批量时必须继承这个约束）。
- **宪法原则落到了类型层**：同步引擎只持有 `MailSyncReading`（无 archive/setRead/trash/send），编译期禁止。这是这个项目最好的部分。

### 5.2 问题

**P0-01（正文明文落库）已在上面列出**，这是最需要补的信任缺口。补充三点：

- **README 的措辞会让人误以为整体加密。** README:116 写的是"No secrets on disk in plaintext: the AES-GCM key… and the per-install API token live in the Keychain"，紧接着 121-123 讲"Credentials encrypted at rest"——**两处都只讲密钥和凭据**，没有一个字提到正文是明文。用户读到的是"加密"这个词，而它修饰的是别的东西。
- **没有"AI 会读哪些内容"的可见性。** `AIGateway.classificationPrompt` 只喂 header/snippet（`AIGateway.swift:247`），而 `summarize`/`draft` 会喂**最多 12000 字符的正文**（`:311`、`:363`）。用户在"AI 设置"里看到的是"调用时随邮件文本发给模型服务商"—— 诚实的，但**没有区分"分类（不发正文）"和"摘要/草稿（发正文）"**。用户以为分类时正文也走了。实际上分类不发正文 —— 这是好事（P1-03），但没讲出来。
- **没有隐私政策/数据处理的说明页。** `AboutSheet` 只有版本号、tagline、反馈邮箱、官网链接（`AboutSheet.swift:30-79`）。对一个宣称"数据只落在你这台 Mac 上"的产品（`docs/使用说明.md:7`）来说，缺一个明确的"我们怎么处理你的数据"页面。分布式交付时这是必需的。

## 6. 差异化是否成立

**问题：AI 分诊的承诺，代码里兑现了多少？**

### 兑现的部分（可信）

| 承诺 | 证据 | 兑现度 |
|---|---|---|
| AI 读信并分类 | `AIGateway.classify` 一次调用同时产出分组 + 建议 + 理由 + 置信度 + 截止日期（`AIGateway.swift:270-280`） | ✅ 扎实 |
| AI 解释为什么 | `Advice.rationale` + `dueText`，行内展开可见（`RowAdviceStrip.swift:107-129`） | ✅ 扎实 |
| AI 只建议不执行 | 宪法 §2 的 6 条规则在代码里都有对应的类型级/路由级保证 | ✅ 非常扎实，是这个项目最好的部分 |
| 搜索能召回 AI 的判断 | 搜索 SQL 左连 `advice` 表匹配 `category`/`action`（`DraftRoutes.swift:341-342`），且 UI 有一行说明为什么（`SearchSheet.swift:44-49`） | ✅ 超出同类产品的诚实度 |
| 发件人排行 | `GET /api/senders`，SQL 聚合（`SenderRoutes.swift:40`） | ✅ 扎实 |

### 没兑现的部分

| 承诺 | 现状 | 证据 |
|---|---|---|
| "AI 分诊"= AI 决定你该做什么 | AI 说"建议归档"，但用户必须自己找到归档按钮、再点一次。**没有"照做"按钮**（P1-08） | `RowAdviceStrip.swift:137-146`（只有"查看邮件"和"忽略"两个动词） |
| 没有 AI Key 时也有建议 | 启发式路径**不产生 advice**：`classifyWithReasons` 只返回 `(group, reason)`（`Heuristics.swift:58-67`），**不产 advice**；而 `persistAdvice` 只在 AI 分支被调用（`BriefingRoutes.swift:141`、`:159`）。启发式明明能给出建议（`Heuristics.swift:161-189` 的 `advice(forReason:)` 能给出 archive/unsubscribe/wait），但这个函数在生产路径上**从未被调用**（`Heuristics.classify` 是唯一调用者，而 `classify` 本身在生产路径上也没有调用者——`BriefingRoutes` 调的是 `classifyWithReasons`）。**所以没有 AI Key 的用户，AI 建议面板永远是空的。** | `Sources/LagoonServer/AI/Heuristics.swift:50`（`advice:` 只在 `classify` 里）、`:58-67`（`classifyWithReasons` 不产 advice）、`:161-189`（`advice(forReason:)` 有能力但无生产调用者）；`Sources/LagoonServer/Routes/BriefingRoutes.swift:120`（调 `classifyWithReasons`）、`:141`/`:159`（`persistAdvice` 只在 AI 分支） |
| AI 能读到邮件内容 | 分类阶段**不读正文**（P1-03，**有意设计**） | `AIGateway.swift:247-248` |
| "AI Inbox Operating System" | 更像"AI 分类的邮件客户端"。**Operating System** 意味着它管理你的收件箱状态机：入箱 → 分诊 → 执行 → 反馈 → 学习。现在只有前两步和一部分反馈（dismissed），没有执行的一键化和学习闭环 | P0-02、P1-08 |

### 结论

**差异化成立，但只成立在"读"这一侧，不成立在"做"这一侧。**

Lagoon 真正比 Gmail/QQ邮箱强的地方是：
1. **AI 判断的可见性和诚实度** —— 每条建议都带理由、置信度、来源（模型还是规则）、以及不可撤销标记（`RowAdviceStrip.swift:87-91`）。这是 Gmail 的 Smart Reply 完全没有的。
2. **搜索能按 AI 的判断召回** —— 用户搜"营销"能搜到从没写过"营销"两字的邮件。
3. **全可撤销 + 审计**（除了发送/退订/永久删除）。

但用户真正想要的"10 分钟清零"，需要的是**执行的一键化**（批量接受建议 → 批量归档），而这一环是断的（P0-02、P1-08）。

**最低限度的补救:** 加上"照做"按钮 + 简报页批量。这两件事加起来大概 300 行代码，就能让产品的核心叙事从"AI 告诉你该做什么"变成"AI 帮你做完了，你只需要确认"。

## 8. 明确**不建议**做的

一份好报告要包含"不要做什么"。以下几件事看起来诱人，但本报告认为不该做：

| 不做 | 理由 |
|---|---|
| **自动归档 / 规则自动执行** | 宪法 §2 rule 5 明确否决，`auto_archive_rules` 表已被删除。这是**对的决定**，不要因为"Superhuman 有"就加回来 |
| **规则引擎（条件 + 动作 + 顺序）** | 同上。而且 P1-12 说明当前连"改一条规则"都做不到 —— 先把简单的做好 |
| **富文本编辑器 / HTML 发信** | README:220-221 明确列为非目标，且 HTML 发信会带来 XSS 与安全面 |
| **多服务商支持（Gmail/Outlook OAuth）** | README:50-55 说是"QQ-only MVP"。在 P0-02/P1-08（核心闭环）修好之前扩服务商，是在漏水的桶里加桶 |
| **iOS 客户端** | 明确非目标 |
| **阅读回执** | 隐私争议大，且对"AI 分诊"这个定位无贡献 |
| **S/MIME / PGP** | 明确非目标 |
| **在批量操作里加"一键全选并删除"** | 两段式全选（`docs/使用说明.md:68`）是刻意的安全设计。加简报批量时**必须继承这个约束**，不要为了顺手把它简化掉 |
