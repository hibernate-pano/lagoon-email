**最该先修的三件事**：

1. **D3-01** —— 用户把某个发件人的邮件整组归类，样本邮件被彻底删除后，这条规则**无声消失**（`ai_overrides` 无外键，`overridesBySender` 又必须 JOIN `message_headers` 才能拿到发件人地址）。这是"用户教过 AI 的东西被悄悄忘掉"，而且没有任何提示。

## 1. P0 —— 数据丢失

### D3-01 · 发送方级改分组规则在样本邮件消失后静默失效

- **文件:行**：
  - `Sources/LagoonKit/LagoonDatabase.swift:451-460`（`ai_overrides` 表定义：只有 `account_id` 外键，**没有** `(account_id, remote_id) → message_headers` 的复合外键；索引只有 `ai_overrides_remote_id_idx ON ai_overrides(remote_id)`）
  - `Sources/LagoonServer/Storage/AIActionStore.swift:750-758`（`overridesBySender` 的 SQL）
  - `Sources/LagoonServer/Storage/MessageStore.swift:1152-1189`（`hardDeleteSync` 显式删 `ai_overrides`）
  - `Sources/LagoonServer/Storage/MessageStore.swift:497-551`（`reconcileInbox` 的 `DELETE FROM message_headers`）
- **问题**：
  `ai_overrides` 存的是"这封邮件（remote_id）的这个发件人（from_address）以后归到 X 组"。`overridesBySender` 要拿到 `from_address`，**只能 JOIN `message_headers`**：

  ```sql
  WITH ranked AS (
      SELECT o.to_group, m.from_address, o.created_at,
          row_number() OVER (PARTITION BY m.from_address ORDER BY o.created_at DESC, o.rowid DESC) AS rn
      FROM ai_overrides o
      JOIN message_headers m ON m.remote_id = o.remote_id AND m.account_id = o.account_id
      WHERE o.account_id = ? AND o.scope = 'sender'
  )
  SELECT from_address, to_group FROM ranked WHERE rn = 1
  ```

  这条 JOIN 是 **INNER JOIN**：样本邮件行一旦从 `message_headers` 消失，`ai_overrides` 里那行就再也匹配不到任何 `message_headers` 行，于是**从结果里彻底消失**。而 `ai_overrides` 本身**还留在表里**（它没有指向 `message_headers` 的外键，`ON DELETE CASCADE` 管不到它；`hardDeleteSync` 会显式删它，但 `reconcileInbox` 的 `DELETE FROM message_headers` 不会）。

  也就是说：**删除样本邮件 = 永久删掉这条用户规则**，而用户界面上没有任何地方提示"你教的这条规则因为一封邮件被删了就没了"。

- **触发条件**（具体失败场景）：
  1. 用户对 `boss@example.com` 的邮件做「把这个发件人的邮件归到「可归档」」（`scope = 'sender'`），落库一行 `ai_overrides(remote_id = 'M1', scope = 'sender')`，`M1` 是当时那封样本邮件的 remote_id。
  2. 用户把 `M1` 移进废纸篓，再「彻底删除」（`purgeHandler` → `hardDeleteSync`）→ `ai_overrides` 那行被显式 DELETE。**这一步是干净的**，规则真的没了。
  3. **真正的漏洞在第 3 步**：如果 `M1` 不是被彻底删除，而是被 `reconcileInbox` 判定"服务端确认已不存在"而 `DELETE FROM message_headers`（`MessageStore.swift:541-544`）——`ai_overrides` 行**留下**（无外键级联），但 JOIN 失配 → 规则从查视图里消失。**这与"彻底删除"的最终结果一样，却完全没有经过用户的"彻底删除"手势。**
  4. 另一条路径：`MessageStore.deleteLiveRows`（`MessageStore.swift:435-442`，UIDVALIDITY 重置时）删掉所有收件箱行，`ai_overrides` 行同样残留成"活着但查不出来"的行。

- **为什么是问题**：
  - 用户教 AI 分类是这个产品"越用越准"的核心承诺。规则**无声消失**属于"数据丢失"级别的信任破坏：用户以为「以后这个人的邮件都归 X 组」，实际它只在那封样本邮件还在的时候有效。
  - 更糟的是**它不是立刻消失**：如果用户后来又收到 `boss@example.com` 的新邮件并被同步进 `message_headers`，JOIN 又能匹配上（因为 `remote_id` 相同吗？**不能** —— `remote_id` 是 Message-ID，新邮件的 Message-ID 不同）。所以新邮件**不会**命中这条规则：用户教的规则对它最该生效的那批新邮件完全无效。
  - 这与 `ai_overrides` 缺复合外键是**同一个根因**（第一轮 Q-04 已指出缺外键，但当时只把它记成"孤儿行"级别的 P2 质量问题，**没有追到"规则静默失效"这个后果**）。本轮把它升级为 P0。

- **建议修法**：
  1. **给 `ai_overrides` 补上发件人地址列**，让规则不再依赖 JOIN 才能被读到：新增 `from_address TEXT` 列（在 `lagoon-v9` 迁移里 `ALTER TABLE ai_overrides ADD COLUMN from_address TEXT`，并用 `UPDATE ... FROM message_headers` 回填历史行；SQLite 的 `ALTER TABLE ADD COLUMN` 无 `IF NOT EXISTS`，所以该列**不能**出现在 `lagoon-v1` 的 `schema` 里，这正是本文件既有的 `is_sent` / `scope` 注释所说明的陷阱）。
  2. `overridesBySender` 改成**不 JOIN** `message_headers`：直接从 `ai_overrides` 读 `from_address`（`INSERT` 时由 `classifyOverrideHandler` 一起写入），把窗口函数作用在 `ai_overrides` 自身上。
  3. 若暂时不补列，**至少**在 `reconcileInbox` 的 `DELETE FROM message_headers` 分支里同步删掉对应的 `ai_overrides` 行（与 `hardDeleteSync` 对齐），并把"规则随样本邮件一起消失"这件事在 UI 上说出来。但这只是止血 —— 规则仍然是"寄存在一封邮件上"的，正确做法是第 1 步。
  4. 顺带：给 `ai_overrides` 补 `(account_id, remote_id)` 复合外键 + `ON DELETE CASCADE`，让"规则依附于邮件"这个语义在 schema 层就是真的（注意这会让第 3 步变成"规则随邮件消失"——所以**必须先做第 1 步**，把规则从"依附某封邮件"改成"依附某个发件人"）。

- **验证方式**：
  - 单元测试：插入 `ai_overrides(sender scope, remote_id='M1')` + 一行 `message_headers(remote_id='M1')` → 断言 `overridesBySender` 返回该发件人；再 `DELETE FROM message_headers WHERE remote_id='M1'` → 断言 `overridesBySender` **仍返回**该发件人（修好后应成立；修好前会失败并复现本条）。
  - 本轮已用 `sqlite3` CLI 在 `/tmp/ovr2.db` 上复现了修好前的行为（删除样本行后查询返回空、而 `ai_overrides` 仍有 1 行残留）。
  - 端到端：造一封 `boss@example.com` 的邮件 → 在简报里「改这个发件人的分组」→ 彻底删除该邮件 → 刷新简报 → `boss@example.com` 的新邮件应仍落在用户指定的那一组。

## 2. P1 —— 用户可见的错误行为

### D3-02 · 预算跨月不换账：12 月 31 日开的 app，1 月 3 日还在把花费记到 12 月

- **文件:行**：`Sources/LagoonServer/AI/UsageBudget.swift:36`（`self.yearMonth = Self.currentYearMonth()`）、`:124-133`（`record` 把这个常量写进每一行）、`:259-261`（`accountBreakdown()` 用同一个常量）、`:177`（`summary` 按 `year_month = ?` 求和）
- **问题**：
  `yearMonth` 是 `let`，**在 actor 构造时算一次，之后永不刷新**。`UsageBudget` 的生命周期等于应用进程的生命周期（`Runtime.swift:136` 构造，全局共享）。而 `usage_log.year_month` 是每次 `record` 写进去的分列键、`summary`/`accountBreakdown` 也是按它过滤——**同一个常量贯穿了写入和读取两侧**。

  应用跨过月初后：
  - 1 月 3 日的每一次 AI 调用都被写进 `year_month = '2026-12'`；
  - 客户端「本月 LLM 用量」面板（`UsageSheet.swift:22` 标题是"本月 LLM 用量"）显示的是 12 月 + 1 月的合计；
  - `checkBeforeCall` 的上限判定（`UsageBudget.swift:100-103`）用的是"12 月累计 + 1 月新增"与上限比 —— **1 月的调用被算进 12 月的额度里**。

  代码里对此有一段明确的说明（`UsageBudget.swift:255-258`）：

  > `yearMonth` is fixed at construction, so asking this actor rather than passing a date keeps the report and the cap describing the same month — including across a month boundary, where a freshly computed "now" and the cap's month would disagree for one request.

  这段注释把 bug 说成了特性：它承认了"跨月边界时新算的 now 和上限的月份会不一致"，但选择的解法是**让两者一直保持一致地错**——不是让月份滚上去，而是让 1 月的花费永远挂在 12 月的账上。

- **触发条件**：
  macOS 应用是**常驻**的（菜单栏应用，不主动退出就一直在跑）。用户 12 月 31 日晚上打开 Lagoon，1 月 3 日早上还在用：
  - 1 月 3 日的所有 AI 调用记入 `year_month='2026-12'`；
  - 「本月 LLM 用量」显示的数字包含 12 月的花费；
  - 上限（`LAGOON_BUDGET_USD_PER_MONTH`）按 12 月累计额判定 → 1 月初用户可能突然收到"预算已超"的错误，而 12 月的账其实早就该清零了。

- **为什么是问题**：
  这是**关于钱的数字**，而且是用户唯一能看到的"这个月花了多少 AI 费"。跨月后它说的不是这个月。`usage_log` 表本来就有 `year_month` 列、也有 `usage_log_year_month_idx` 索引 —— **数据模型是按月分列设计的，读取侧也确实按月过滤，只是月这个值被冻住了**。一个月界就能触发，触发后一直错到下次重启 —— 而 macOS 应用可能几个月不重启。

- **建议修法**：
  1. 把 `yearMonth` 从 `let` 改成 `private var`，并加一个**惰性刷新**：每次 `record` / `checkBeforeCall` / `accountBreakdown` 前比较 `Self.currentYearMonth()` 与当前值，不同则重新 `summary(db:yearMonth:)` 水合并把 `yearMonth` 更新为新月。
  2. 月份切换时的水合必须**放进同一个 `db.write` 事务**（或至少保证读到的 total 与写入用的 `year_month` 是同一个月的），否则恰好在月初那一刻并发来的一批调用会被拆到两个月里。
  3. 顺带：客户端「本月 LLM 用量」面板应显示**具体是几个月**（如"2026-12"），这样即使服务端再出问题，用户也能一眼看出数字不对。
  4. 建议补一条**契约测试**：把 `currentYearMonth()` 抽成可注入的时钟，测试"跨月时 `record` 写入新月、`accountBreakdown` 只统计新月"。

- **验证方式**：
  - 单元测试（需把时间源抽出依赖）：把 `currentYearMonth` 替换为可注入闭包，构造 budget 于"1 月"，把时钟拨到"2 月"，调 `record`，然后断言 `usage_log` 里出现 `year_month='2026-02'` 的行，且 `accountBreakdown()` 的合计 **只含 2 月**（修好前会是 0 或含 1 月）。
  - 端到端手工验证：改 `LAGOON_BUDGET_USD_PER_MONTH` 为 0.01，先跑通一次调用，再把系统时间拨到下个月，重启前再跑一次调用 → 用量面板的数字应只反映新的月份。

### D3-03 · 跨客户端回复信号被当成"Lagoon 发过信"混进"最近操作"

- **文件:行**：
  - `Sources/LagoonServer/Sync/SyncEngine.swift:250-261`（`recordSentReplies`，写入 `kind: .send`，payload `["remoteId": id, "sentFolder": "true"]`，**没有 `status` 键**）
  - `Sources/LagoonServer/Storage/AIActionStore.swift:186-203`（`pageSQL`）与 `:205-219`（`countSQL`）
  - `Sources/LagoonKit/Action.swift:48-55`（`AIActionKind.isUndoable`：`.send` 不可撤销）
  - `Sources/Lagoon/Localization/L10n.swift:796`（`case .send: pick("发送邮件", "Sent message")`）
- **问题**：
  简报/时间节省统计都把 `sentFolder` 标记排除掉了（`AIActionStore.timeSavedEvents:714` 明确写 `AND NOT (a.kind = 'send' AND json_extract(a.payload, '$.sentFolder') IS NOT NULL)`），**但"最近操作"面板读的 `pageSQL` / `countSQL` 没有这个排除**。而 `pageSQL` 对 `send` 行的唯一过滤是"状态必须是 NULL 或 sent"——`sentFolder` 行的 payload 里**没有 `status` 键**，`json_extract(payload,'$.status') IS NULL` 成立，于是**通过过滤**。

  后果：用户在**别的客户端**（手机网页版 / 另一个邮件 App）回复的邮件，会被同步引擎从 Sent 文件夹收上来、记成一条 `send` 审计行，然后出现在"最近操作"列表里，标题写着「发送邮件」。用户会认为 Lagoon 替他发过这封信 —— **而 Lagoon 根本没有参与这次发送**。这正是"审计日志说谎"，是宪法 §3 明确禁止的。

  同一批行还污染：
  - `totalCount`（`countSQL` 同样不过滤 `sentFolder`）→ "还有 N 条" 的 N 里混着不是 Lagoon 做的操作；
  - `ActionHistorySheet` 的 `remainingCount`（`ActionHistorySheet.swift:216-219`）基于这个 total。

  顺带：这些 `sentFolder` 行**永不被清理**（见 D3-07），而 `recordSentReplies` 每轮同步都要 `repliedRemoteIds` 全表扫一遍去重（`SyncEngine.swift:252`）——数量只增不减。

- **触发条件**：
  用户在 QQ 邮箱网页版回复了一封邮件（不是从 Lagoon 发的）。下一次同步轮，引擎的 `collectSentReplies` 收上这个 Sent 邮件的 `In-Reply-To` / `References` 里的 Message-ID，写一条 `send` 审计行。用户打开"最近操作"（⌘-或菜单栏入口），列表里出现一条「发送邮件」。

- **为什么是问题**：
  - 审计历史是产品的诚实性锚点。一条"我做了我没做过的事"的记录，比没有记录更糟。
  - 客户端已经**准备好了**正确的文案区分（`isUndoable == false` → 显示"不可撤销"），但 `sentFolder` 行的 `kind` 就是 `send`，客户端无从区分"Lagoon 发的"和"从 Sent 目录收割到的"。
  - 数量也不可信：`countSQL` 和 `pageSQL` 的谓词不一致于产品语义。

- **建议修法**：
  1. **在 `pageSQL` 与 `countSQL` 里加与 `timeSavedEvents` 相同的 `sentFolder` 排除**（两处必须同步改，否则"还有 N 条"与实际行数会再次分歧）：
     ```sql
     AND NOT (kind = 'send' AND json_extract(payload, '$.sentFolder') IS NOT NULL)
     ```
  2. 或者更彻底：把"跨客户端回复信号"从 `ai_actions` 里挪出去（它不是"Lagoon 做的动作"，只是**信号**），单独存一张 `sent_replies` 表或放到 `message_headers` 的一个布尔列上。这样 `ai_actions` 就真的只装"Lagoon 做的动作"，语义自洽。
  3. 若选方案 1，还要同步处理 `repliedRemoteIds`（它**需要**读这些行）——把它改成读新表或读 `sentFolder` 行，不受 `pageSQL` 过滤影响即可（它目前用的是自己的 SQL，不受影响）。
  4. 补测试：插入一条 `send` + `sentFolder` 行动作 → 断言 `AIActionStore.page` 的 `actions` **不含**它，且 `totalCount` 不含它。

- **验证方式**：
  - 单元测试（`AIActionStore` 层）：种入三种行 —— 普通 `send`（无 `sentFolder`）、`send` + `sentFolder`、`send` + `status='failed'` —— 断言 `page()` 只返回第一种。
  - 端到端：在网页版回复一封 → 等一次同步 → 打开"最近操作" → 不应出现这条记录。

### D3-04 · 批量删除/归档把"失败"算成"已处理"，"还有 N 封未处理"报成 0

- **文件:行**：`Sources/LagoonServer/Routes/ActionsRoutes.swift:927`（删除）、`:986`（归档）
  ```swift
  let truncated = max(0, requestedTotal - sweep.count)
  ```
  其中 `sweep` 是 `runBulkSweep` 的返回值，`runBulkSweep`（`:1124-1190`）**对每一个尝试过的 id 都 append 一条 item**，成功 append `ok: true`、失败 append `ok: false`。所以 `sweep.count` = **尝试过的数量**，不是成功的数量。
- **问题**：
  `requestedTotal` 是用户要求的总数（`allMatching` 走 `liveTotal` = `MessageStore.count(...)`；显式 id 走 `req.remoteIds.count`），`sweep.count` 是尝试过的数量。两者相减得到"没尝试过的数量"——**这个算式本身没错**，错在**语义被混用了**：
  - 用户没尝试到的邮件 → 确实"未处理"，计入 `truncatedCount` 是对的；
  - 用户尝试了但**失败**的邮件 → 服务端已经试过了，但邮件**还在收件箱里**。它既没有被成功处理，也**不会被重试**（客户端的重试按钮只重试 `response.items` 里 `ok == false` 的那些，见 `BriefingFeedView.swift:1470-1480`）。

  现在的问题在于**客户端的分支**。以删除为例（`MessageListView.swift:2176-2221`）：
  ```swift
  let failedIds = Set(response.items.filter { !$0.ok }.map(\.remoteId))
  let succeeded = response.items.filter(\.ok).count
  ...
  if let truncated = response.truncatedCount, truncated > 0 {
      // 报"已移入废纸篓 N 封，还有 M 封未处理"
  } else {
      // 报"已将 N 封邮件移入废纸篓"
  }
  ```
  **失败的邮件在 `failedIds` 里、留在列表里（`mutateMessages { $0.removeAll { !failedIds.contains($0.remoteId) } }`），但当 `truncatedCount == 0` 时，弹出的横幅写的是"已将 N 封邮件移入废纸篓"** —— 而 N 是成功的数量，失败的邮件**没被任何文案提及**。用户看到"已移入废纸篓 400 封"（绿色/info 级别，4 秒自动消失），而收件箱里还躺着 100 封刚才那批里失败的邮件。

  更严重的组合：**500 封全部失败** → `sweep.count = 500`、`requestedTotal = 500` → `truncated = 0` → `truncatedCount = nil` → 客户端报"已将 0 封邮件移入废纸篓"（info 级），**并且不显示任何失败信息**（`MessageListView` 的删除路径只检查 `truncatedCount`，从不检查 `response.items` 里的失败项；而 `BriefingFeedView` / `SenderSheet` / `StackSheets` 的路径**有** `if !failed.isEmpty` 分支，`MessageListView` 的 `deleteAllMatching` **没有**）。

  逐条对照客户端的三个调用点：
  | 调用点 | 有 `!failed.isEmpty` 分支？ | 失败被说出来？ |
  |---|---|---|
  | `BriefingFeedView.swift:1376` / `:1470` | 有 | 是 |
  | `StackSheets.swift:442`（`failed.isEmpty` 才看 truncated） | 有 | 是（`sweepPartial`） |
  | `SenderSheet.swift:480` | **无**（只读 `truncatedCount`） | **否** |
  | `MessageListView.swift:2209`（全选删除） | **无** | **否** |

- **触发条件**：
  用户「全选全部 → 删除」，500 封邮件里有一批（比方说被 QQ 判为"发件人已注销"或已过期的）`provider.trash` 抛 `MailError`：
  - 失败的邮件留在收件箱（本地 `is_deleted` 已被 `release` 回滚，见 `ActionsRoutes.swift:1149-1162`）——数据是对的；
  - 但用户只看到"已将 400 封邮件移入废纸篓"，**没有任何地方说"还有 100 封没删掉"**。用户以为删完了，去手动找那 100 封时发现还在。
  - 另一条路径（`SenderSheet` 的批量归档）：`truncatedCount` 为 nil 时，连 `failed` 都被静默吞掉。

- **为什么是问题**：
  这属于"数字与列表不一致"这一类本项目反复修过的缺陷的**最后一块**：服务端如实返回了每项的 `ok`/`errorCode`，但**批量删除的主路径（"全选全部"）根本不读它**。用户被告知"删完了"而事实是"删了一半"。

- **建议修法**：
  1. **客户端**：在 `MessageListView.deleteAllMatching` 和 `SenderSheet.archiveAll` 里补上 `if !failed.isEmpty` 分支（照抄 `BriefingFeedView.swift:1376-1390` 的写法：`title: l10n.senderBulkPartial` + `detail: l10n.senderBulkPartialDetail(bulkFailureReason(failed))` + 重试按钮只覆盖失败项）。`MessageListView` 目前**没有** `bulkFailureReason` 这个辅助函数，需要一并加上。
  2. **服务端**：把 `truncatedCount` 的语义收紧 —— 它现在混着"没尝试"和"尝试了但失败"两件事。更干净的做法是**新增一个字段**（如 `failedCount`）或者让 `truncatedCount` 只算"没尝试的"，失败项由 `items` 各自携带（现在已经是这样了）。既然 `items` 已经逐项带 `ok`，**关键是客户端必须读它**。
  3. 至少要在 `bulkDeleteTruncated` / `sweepTruncated` 之外补一条"有失败"的文案（`L10n.swift:1173-1184` / `:1332-1334` 已有 `sweepPartial` 可复用）。

- **验证方式**：
  - 单元测试（`DeleteBulkTests`）：种一个"永远失败"的 provider，删 3 封 → 断言 `body.items` 有 3 条 `ok == false`；再断言**客户端逻辑**（`BulkSheetTruncationTests` 已有同类测试位）：失败时必须出现失败提示而不是"已移入废纸篓 N 封"。
  - 端到端：制造一次部分失败的批量删除 → 横幅必须同时说"成功几封"和"失败几封"，且重试只覆盖失败项。

### D3-05 · 简报的"遗漏数"跨两个快照计算，可能报出与列表矛盾的数

- **文件:行**：`Sources/LagoonServer/Routes/BriefingRoutes.swift:126-167`
  ```swift
  messages = try await MessageStore.recent(forAccount:, limit:, receivedAfter: windowStart, db:)
  let inWindow = try await MessageStore.count(forAccount:, receivedAfter: windowStart, db:)
  omitted = max(0, inWindow - messages.count)
  ```
  这两个是**两次独立的 `db.read`**（每次各自从连接池借一个 reader），中间可以夹进一次写。
- **问题**：
  `omitted` 的定义是"窗口内总共有的邮件数 − 实际返回的条数"。这个算式在**同一个快照**里成立（两次读看到同一批行），但这里不是同一个快照：
  - 若在两次读之间**新来一封**邮件（同步轮落地）：`inWindow` 比 `messages` 多 1 → `omitted` 多算 1 → 用户看到"另有 N 封…未纳入简报"，而这封邮件其实**在下一轮就会被纳入**（不是被截断的）。文案 `briefingOmitted`（`L10n.swift:163-166`）说的是"另有 N 封在近 30 天内，未纳入简报"，这句话对新来的邮件是**假的** —— 它是被时间窗漏掉的，不是被条数上限截掉的。
  - 若在两次读之间**同步把一封移出窗口**（`is_archived` 翻真）：`inWindow` 比 `messages` 少 → `omitted` 变成 `inWindow - messages.count` 可能是**负数**，被 `max(0, ...)` 夹成 0 → 恰好掩盖了截断（若真有 500 封被截掉，omitted 应该是几百）。这是**静默丢失截断信息**的方向。

  同一个文件里的 `AIActionStore.page`（`AIActionStore.swift:112-137`）**恰好做对了**，而且注释就写着这件事：

  > Both reads share a single `db.read` closure on purpose: two separate reads could straddle a write, and the panel would then say "已显示 100/101 条" about a history that has 100 rows.

  简报路由是同一份代码库里**没有**遵守这条自己写下的规则的唯一一处。
- **触发条件**：
  客户端每 30 秒轮询一次简报（`BriefingFeedView` 的刷新）。同时后台同步轮正在落地新邮件（IMAP 轮询间隔 30 秒，`IMAPProvider.swift:34`）—— 两个时间窗口重叠的概率不低。落地的瞬间恰好夹在 `recent` 与 `count` 之间，就多报 1 封；同步把邮件归档的瞬间夹在中间，就少报甚至归零。
- **为什么是问题**：
  "未纳入简报 N 封"是一个**关于用户邮箱状态的断言**。它要么多报（新来的邮件被说成"没纳入"），要么少报（真正被 500 上限截掉的邮件被说成"没有"）—— 后者尤其糟：简报的 `maxItems = 500` 截断正是"看起来完成了、其实缺了一块"这个产品反复修的失败模式。
- **建议修法**：
  把 `recent` 与 `count` 放进**同一个 `db.read` 闭包**（照抄 `AIActionStore.page` 的形状），并用 `LagoonDB(transaction:)` 把句柄传下去：
  ```swift
  let (messages, inWindow) = try db.read { raw in
      let tx = LagoonDB(transaction: raw)
      return (try MessageStore.recent(..., db: tx), try MessageStore.count(..., db: tx))
  }
  ```
  `LagoonDB` 的 `transaction:` 初始化器（`LagoonKit/LagoonDB.swift:28-31`）已经存在，`AccountStore.reconcileActive`（`Sources/LagoonServer/Storage/AccountStore.swift:199-204`）就是这个用法。
- **验证方式**：
  - 单元测试：在 `recent` 与 `count` 之间插入一个并发写（`Task` + `db.write`），断言 `omittedCount` 要么是真实截断数、要么为 nil，**不会**因为新来一封就变成 1。
  - 更简单的回归网：给 `BriefingRoutes` 加一条断言 ——"当返回的条数 < limit 时，`omittedCount` 必须为 nil"（因为没截断就没有遗漏）。这条断言在当前实现下**会失败**（新来一封时 omitted = 1 而条数 < limit）。
  - 现有测试位：`Tests/LagoonServerTests/BriefingWindowTests.swift`。

### D3-06 · 一条读不懂的建议行会让整个建议队列 500

- **文件:行**：`Sources/LagoonServer/Storage/AdviceStore.swift:327-342`
  ```swift
  static func decode(_ row: Row) throws -> AdviceRecord {
      guard let actionRaw: String = row["action"],
            let action = AdvisedAction(rawValue: actionRaw),
            ... else {
          // A row whose enum no longer decodes is either corrupt or written
          // by a newer build. Raising here would turn one unreadable
          // suggestion into a 500 for the whole queue; the caller cannot
          // show it, so skipping is the honest answer.
          throw StoreError.insertFailed
      }
  ```
- **问题**：
  注释说"**skipping** is the honest answer"，但代码是 `throw` —— **抛异常不是跳过，是让整个查询失败**。`AdviceStore.list`（`:184-190`）对所有行做 `.map { try decode($0) }`：一行解不出来 → 整个 `list` 抛 → 路由 `AdviceRoutes.swift:60-68` catch → **500 `internal-error`**。

  也就是说，一行 `action` 字段被写坏（或被一个更老/更新的 build 写成了现在不认识的枚举值）的建议，会让**整个建议队列页返回 500**，用户一封建议都看不到。

  同一个文件里另一处已经做对了：`acceptedStats`（`:293-297`）对解不出的行是 `continue`（跳过）而不是抛。**同一个文件里两种策略**。
- **触发条件**：
  `advice.action` / `confidence` / `source` / `decision` 四个字段都是 TEXT 且**没有 CHECK 约束**（`LagoonDatabase.swift:493-511` 的建表语句），所以任何写进去的字符串都合法。触发路径：
  - 某个 build 改名或删除了一个枚举 case（`AdvisedAction` / `AdviceConfidence` / `AdviceSource` / `AdviceDecision` 任一），旧库里那批行解不出来；
  - 模型返回了一个不在 `AdvisedAction` 枚举里的 action（`AdviceStore.upsertSync` 是直接写 `advice.action.rawValue`，`advice` 列没有 CHECK 约束，所以**模型侧的意外值也能落库**）；
  - 磁盘位翻转等极端损坏。
- **为什么是问题**：
  - 建议页是 AI 功能的门面。整个面板 500 意味着**用户完全无法查看任何建议**，而原因是一行数据的枚举值。
  - 更实际的触发路径是上面第二条：`AdvisedAction` 的 case 集合若与模型输出的取值空间不完全一致，一行坏值就能打挂整个页面。注释自己承认了这一点（"written by a newer build"），却把处理方式写反了。
  - 注释与实现相反还意味着**下一个读代码的人会相信注释**，以为已经有兜底了。
- **建议修法**：
  1. 把 `decode` 拆成"可解码"与"跳过"两种结果：`list` / `byRemoteIds` / `acceptedStats` 遇到解不出的行时**跳过该行**（`compactMap`），而不是让整个查询失败。
  2. 若确实希望"坏行要有人知道"，在跳过的同时 `logger.warning` 记一行（带 `id`），这样是可观测的而不是静默的。
  3. 给 `advice` 表的四个枚举列加 `CHECK` 约束（SQLite 支持，且 `INSERT` 失败可以精确归因），或者在 `upsertSync` 写入前**校验**枚举值、非法值不落库 —— 这样"坏行"根本不会产生。
  4. 修正注释，让它描述代码实际做的事。
- **验证方式**：
  - 单元测试：直接 `INSERT` 一行 `advice(action='not-a-real-action', confidence='medium', source='heuristic', decision='pending')` → 调 `AdviceStore.list` → 断言**不抛异常**，且返回其余正常行（修好后成立；修好前抛 `StoreError.insertFailed`）。
  - 路由级测试：种一条坏行 + 一条好行 → `GET /api/advice` 应返回 200 且包含好行。
  - 现有测试位：`Tests/LagoonServerTests/AdviceStoreTests.swift`（目前**没有**任何一条测试覆盖"行解不出来"的情况 —— 这本身说明这个分支从未被执行过）。

### D3-07 · `ai_actions` 只增不减：`expires_at` 写了 30 天，却从没有生产代码删过它

- **文件:行**：`Sources/LagoonKit/LagoonDatabase.swift:414-421`（`ai_actions` 建表，`expires_at TEXT NOT NULL DEFAULT (strftime(...,'now','+30 days'))`）、`Sources/LagoonServer/Storage/AIActionStore.swift:291-298`（**唯一**的 `DELETE FROM ai_actions`，且带 `AND kind = 'undo'`）
- **问题**：
  `expires_at` 被声明为"30 天后过期"，`undoOne`（`ActionsRoutes.swift:1784-1786`）也确实用它拒绝过期撤销。**但没有任何代码删除过期的行**。这张表只增不减。

  第一轮报告的 Q-02 已经指出了这一点（"`ai_actions` 只写不删"），**本轮的新证据是它的实际量级**：
  - 每次归档 / 删除 / 发信 / 撤销 / 改分组都追加一行；
  - **每次同步轮**，`recordSentReplies`（`SyncEngine.swift:250-261`）为 Sent 目录里每一个新的 Message-ID 追加一行 `send`；
  - 每次批量操作 500 封 = **500 行**（`ActionsRoutes.swift:1083-1088`，逐条 `recordSync`）；
  - 撤销一次批量 = 再 500 行 `undo`（`ActionsRoutes.swift:1790-1794`）。
- **触发条件**：
  一个用了半年的用户：几百次单封操作 + 几十次批量操作（每次 500 行） + 每次撤销（再 500 行）→ `ai_actions` 轻松到**十万行量级**。这直接放大 D3-08（撤销探测的成本）和 D3-03（计数被污染）。
- **为什么是问题**：
  1. `expires_at` 是一个**没有任何实现支撑的契约** —— 字段说了 30 天，行为是永久。撤销在 31 天时会被拒绝（`UndoRejection.expired`），但行还在。
  2. 索引同步膨胀：`ai_actions_account_created_idx`、`ai_actions_undo_of_idx`、`ai_actions_send_request_idx` 三个索引都随表增长。

- **建议修法**：
  在一个已有周期里做清理（同步轮尾部、或简报路由 —— 它已经有 `AdviceStore.pruneDismissed` 的先例，`BriefingRoutes.swift:334-354`）：

  ```sql
  DELETE FROM ai_actions WHERE expires_at < strftime('%Y-%m-%d %H:%M:%f','now')
  ```

- **验证方式**：
  - 单元测试：写一条 `expires_at` 在过去的 `ai_actions` 行 → 触发清理 → 断言行被删；写一条未过期的 → 断言还在。
  - 规模验证：造 10 万行 → 跑一次简报 → 断言 `ai_actions` 表大小下降、简报响应时间不劣化。

### D3-09 · 撤销探测用不上表达式索引的第二列，成本随撤销次数线性增长

- **文件:行**：`Sources/LagoonKit/LagoonDatabase.swift:430-432`（索引定义）、`Sources/LagoonServer/Storage/AIActionStore.swift:186-203`（`pageSQL`）、`:705-732`（`timeSavedEvents`）
  ```sql
  CREATE INDEX ai_actions_undo_of_idx
      ON ai_actions (account_id, json_extract(payload, '$.undoOf'))
      WHERE kind = 'undo';
  ```
- **问题**：
  索引把 `json_extract(payload,'$.undoOf')` 放在**第二列**，而所有用它的查询都是**相关子查询**，比较的右边是**外层行的值**（`ai_actions.id` 或 `CAST(ai_actions.id AS TEXT)`）。

  实测（`sqlite3` CLI，`/tmp/js3.db`）：SQLite **不会**用表达式索引的第二列做相关比较的 seek：
  ```
  === A) 相关子查询，比较列是表达式 ===
  `--SEARCH u EXISTS USING COVERING INDEX t2_idx (k=?)     ← 只用了第 1 列
  === B) 对照组：比较列是普通列 ===
  `--SEARCH u EXISTS USING COVERING INDEX t3_idx (k=? AND v=?)   ← 两列都用上了
  ```
  也就是说：**`ai_actions_undo_of_idx` 只被当成"该账号的 undo 行"的小集合用**（`account_id = ?` 这一列），真正的 `undoOf` 比较是在这个小集合里**逐行算表达式**完成的。

  这不是"索引没用"（它把候选集从全表缩到该账号的 undo 行，已经省了很多），但**省得不够**：探测成本随"该账号的 undo 行数"线性增长，而撤销行数只增不减（见 D3-07）。

  实测（`/tmp/ts.db`：3000 条 undo 行 + 5000 条普通行动作，跑 `timeSavedEvents` 形状的查询）：
  ```
  有 ai_actions_undo_of_idx：real 1.40s
  删掉该索引后          ：real 7.49s
  ```
  索引确实有效（快 5 倍），但 1.4 秒的**单次**聚合对一个每 30 秒刷新一次的界面来说太贵了。

  再看未撤销行的分布（`/tmp/q*.db`，5000 普通行 + N 条 undo 行）：
  ```
  undo 行 = 100  → real 0.03s
  undo 行 = 500  → real 0.17s
  undo 行 = 2000 → real 0.80s
  ```
  **清晰的线性增长**。
- **触发条件**：
  用户半年内撤销了 2000+ 次（撤销行是永久保留的，见 D3-07），每次打开"最近操作"或"时间节省"面板都要跑一次这个探测。`timeSavedEvents` 由 `TimeSavedRoutes` 每次请求都跑。
- **为什么是问题**：
  索引的**存在**给了人"这个查询是 O(log n) 的"的错觉，实际是 O(该账号 undo 行数)。表越用越大，这个查询越慢 —— 而它在一个**每 30 秒刷新**的界面上跑。
  需要说明的是：**这不是新引入的缺陷**（第一轮没有覆盖它），但它与 D3-07（表只增不减）是**乘法关系**，所以本轮把它列出来。
- **建议修法**：
  1. **最有效的一步是 D3-07 的清理** —— 删掉过期行，undo 行数自然被限制在 30 天窗口内。这条单独就能把这个查询的规模从"用户 lifetime"压回"30 天"。
  2. 若要进一步优化：把 `undoOf` 从 JSON 提取改成**独立列**（`undo_of INTEGER`），并建 `(account_id, undo_of)` 索引。SQLite 对**普通列**的相关比较是能做双列 seek 的（上面的对照组 B 已证明：`SEARCH u ... (k=? AND v=?)`）。代价是 `ai_actions` 的写入路径要改（`recordSync` 拆 payload）。
  3. 或者：把"是否被撤销"**物化**到被撤销的那一行上（加一个 `undone_by INTEGER` 列），这样探测就是 `WHERE undone_by IS NULL` —— 一个可以用部分索引直接回答的问题，根本不需要相关子查询。
  4. 无论如何，**先做 D3-07**。
- **验证方式**：
  - 计划验证：`EXPLAIN QUERY PLAN` 应显示 `SEARCH u USING INDEX ... (account_id=? AND undo_of=?)`（两列），而不是现在的 `(account_id=?)`。
  - 耗时验证：造 3000 条 undo 行 → 跑一次 `timeSavedEvents` 形状的查询 → 断言耗时 < 100 ms（当前 1.4 s）。
  - 规模验证：清理生效后，`ai_actions` 的行数应稳定在 30 天窗口内。

### D3-10 · `ai_overrides` 没有 `(account_id, scope)` 索引，两个覆盖查询每次都要全表扫 + 排序

- **文件:行**：`Sources/LagoonKit/LagoonDatabase.swift:451-460`（`ai_overrides` 建表，**只有** `ai_overrides_remote_id_idx ON ai_overrides(remote_id)`）、`Sources/LagoonServer/Storage/AIActionStore.swift:746-775`（`overridesBySender`）、`:789-813`（`overridesByMessage`）

  ```
  === overridesBySender ===

  |--SEARCH o USING INDEX ai_overrides_remote_id_idx (remote_id=?)   ← 驱动表是 o，从 remote_id 索引起

  `--USE TEMP B-TREE FOR LAST 2 TERMS OF ORDER BY
  ```

  ```
  === overridesByMessage ===
  |--SEARCH o USING INDEX ai_overrides_account_scope_idx (account_id=? AND scope=?)
  ```
  谓词**从"扫全表"变成"定点 seek"**。
- **触发条件**：
  `overridesBySender` / `overridesByMessage` 在**每一次简报请求**里都跑（`BriefingRoutes.swift:145-152`），而简报每 30 秒轮询一次。加上 `classifyOverrideHandler` 在每次改分组时也要读这两个查询来算 `fromGroup`（`ActionsRoutes.swift:1478-1503`；真正写入覆盖行的是 `AIActionStore.insertOverrideSync`，在同函数的 `db.write` 块里，`ActionsRoutes.swift:1516`）。

- **为什么是问题**：
  目前规模还小（实测 200 行覆盖 5000 封邮件时是毫秒级），但这是**每 30 秒一次、随使用线性变慢**的查询，而且它在**简报**这条产品的热路径上。`ai_overrides` 又没有清理策略（只有 `hardDeleteSync` 会删），所以它只增不减。

- **建议修法**：
  1. 在 `lagoon-v9` 迁移里加：`CREATE INDEX IF NOT EXISTS ai_overrides_account_scope_idx ON ai_overrides (account_id, scope);`（`IF NOT EXISTS` 是安全的，因为这个索引不存在于 `lagoon-v1` 的 `schema` 里，也不存在于任何旧库）。
  2. 若 D3-01 采纳了"加 `from_address` 列"的方案，索引可以进一步设计成 `(account_id, scope, from_address)`，让 `overridesBySender` 变成**单表覆盖扫描**（不再 JOIN `message_headers`）—— 一举解决正确性与性能两件事。
- **验证方式**：
  - 计划验证：`EXPLAIN QUERY PLAN` 应显示 `SEARCH o USING INDEX ai_overrides_account_scope_idx (account_id=? AND scope=?)`。
  - 回归测试：种 1000 条不同 scope 的覆盖行 → 断言 `overridesBySender` 只返回 `scope='sender'` 的那些（防止索引引入新的过滤错误）。

### D3-11 · 搜索会把**每一条**缓存正文解密一遍

- **文件:行**：`Sources/LagoonServer/Routes/DraftRoutes.swift:390-400`（搜索谓词）、`Sources/LagoonKit/BodyCipher.swift:201-215`（`lagoon_cipher_contains`）
- **问题**：
  搜索谓词的 OR 链里有两支走 `lagoon_cipher_contains`：
  ```sql
  OR lagoon_cipher_contains(m.snippet_cipher, ?)
  OR lagoon_cipher_contains(b.body_cipher, ?)
  ```
  `lagoon_cipher_contains` 的实现是 `try BodyCipher.open(cipher)` —— **一次完整的 AES-GCM 解密**（`BodyCipher.swift:84-95`），然后做一次 case-insensitive 字符串查找。

  注释（`BodyCipher.swift:184-196`）把这个设计说成"把决定留在 SQLite 里，行只在查询真的走到那一支时才被解密，`LIMIT` 仍然作用于最终结果"。

  但**这个论证只在 OR 链的"短路"语义成立时才对**。SQLite 对 `A OR B OR C` 的求值顺序是**由查询计划决定的**，而不是"从左到右短路"。实测计划（`/tmp/sp2.db`）：
  ```
  |--SEARCH m USING INDEX message_headers_account_received_idx (account_id=?)
  |--SEARCH b USING INDEX sqlite_autoindex_message_bodies_1 (account_id=? AND remote_id=?) LEFT-JOIN
  `--SEARCH a USING INDEX sqlite_autoindex_advice_1 (account_id=? AND remote_id=?) LEFT-JOIN
  ```
  `m` 的扫描是按 `account_id` 走的 —— **该账号的每一行**。对每一行，OR 链的每一支都要被求值。`subject LIKE ?` 这一支通常最快命中；但当用户搜的是正文里才有的词（`body_cipher` 那一支）时，**每一行都要解一次密**：`snippet_cipher` 一支要解密 snippet，`body_cipher` 一支要解密整个正文（可能几十 KB）。

  也就是说：**搜一个只出现在正文里的词，会把该账号所有缓存正文的加密全部解开一遍**。
- **触发条件**：
  用户在搜索框里输入一个只有正文里才有的词（很常见 —— 搜索就是为了找正文）→ 服务端对该账号所有 `message_headers` 行执行 `lagoon_cipher_contains(snippet_cipher, …)` + `lagoon_cipher_contains(body_cipher, …)`。
  规模决定代价：5000 封邮件、平均 20 KB 正文 → 约 100 MB 的 AES-GCM 解密 + 100 MB 的字符串查找，**在搜索请求的路径上同步完成**（`BodyCipher.containsFunction` 是同步闭包）。
- **为什么是问题**：
  1. **延迟**：搜索会明显变慢，而且邮件越多越慢（无上界）。客户端的超时是 `APITimeout.interactive`，超时后用户看到"搜索失败"，而服务端还在算。
  2. **安全姿态**：注释说"没有明文离开进程边界"—— 这句是对的，但**明文在进程内被大量重建**（每次搜索重建一遍全部正文），而正文是用 Keychain 密钥封着的。这不违反规格，但把"密文存储"的经济性抵消了大半。
  3. 注意 `lagoon_cipher_contains` 被声明为 `pure: true`（`BodyCipher.swift:206`）—— 这个声明是**正确**的（解密是确定性的，nonce 在封存时已定），不会引入缓存正确性问题。
- **建议修法**（按性价比排序）：
  1. **给 `message_bodies` 加一个"是否可能命中"的预筛**：例如存一个 `body_lower` 的**哈希 n-gram 索引**（比如把正文切成 3-gram 的 Bloom filter 存成 BLOB），查询时先比 Bloom filter，命中才解密。这是标准做法，但工程量大。
  2. **更简单**：把 `lagoon_cipher_contains` 的解密结果**缓存**在 SQLite 的**临时表**里？不行 —— 那等于把明文落盘。
  3. **最实际的**：给 `message_bodies` 加一列 `body_len` 与 `body_has_ascii` 之类的粗特征，先做廉价的**否定筛**（"这行一定不含该词"就可以跳过解密）。对 CJK 正文效果有限。
  4. **另一条实际路线**：把搜索限制在**有缓存正文**的行上（`b.body_cipher IS NOT NULL`）并把正文臂从 OR 链里**拆出来**、用一条独立的、可用 `LIMIT` 的子查询来做 —— 这样 SQLite 先用 `subject`/`from`/`advice` 臂出结果，正文臂只对**剩下的**候选做，并且有明确的上限。
  5. 至少要**给这条路径加一个上界**：超过 N 封时先只搜 snippet（快），并在响应里说明"正文搜索已跳过 X 封"（与产品其它地方"截断必须说出来"的规则一致）。
- **验证方式**：
  - 性能测试：种 5000 封邮件，每封带 20 KB 密文正文 → 跑一次只命中正文的搜索 → 断言耗时 < 500 ms（当前会是秒级）。用一个计数版的 `lagoon_cipher_contains`（临时插桩）可以直接数出解密次数。
  - 计划验证：`EXPLAIN QUERY PLAN` 里应能看到正文臂被限制在 `LIMIT` 之内，而不是对 `account_id` 的全量扫描。
  - 现有测试位：`Tests/LagoonServerTests/BodyEncryptionTests.swift`、`AdviceSearchRecallTests.swift`。

### D3-12 · "已发送"的两事务窗口：`upsert` 与 `markSent` 之间那一行会被对账删掉

- **文件:行**：`Sources/LagoonServer/Routes/SentRoutes.swift:157-171`
  ```swift
  for row in rows {
      // Two steps, two transactions, on purpose. ...
      try await MessageStore.upsert(row, db: db)          // 事务 1
      try db.write { raw in
          try MessageStore.markSent(
              remoteId: row.remoteId, accountId: account.id, db: raw
          )                                                 // 事务 2
      }
  }
  ```
  以及 `Sources/LagoonServer/Storage/MessageStore.swift:435-442`（`deleteLiveRows`）、`:497-551`（`reconcileInbox`）
- **问题**：
  第一个事务写进去的那一行 `is_sent = FALSE`（`upsert` 的 ON CONFLICT 子句**故意不写** `is_sent`，见 `MessageStore.swift:69-78` 的 ON CONFLICT 子句，与 `:95-108` 的设计说明注释）。第二个事务才把它翻成 TRUE。**两个事务之间**（几毫秒到几十毫秒，取决于写锁等待），这行是"一封 `is_sent=FALSE` 的收件箱邮件"。

  如果这期间跑一次 `reconcileInbox`（`MessageStore.swift:497-551`），它的谓词是 `filterSQL(archived:false, deleted:false, sent:false)` —— **恰好命中这行**。但复核后的结论比第一轮 F-05 温和：
  - `reconcileInbox` 的三个分支里，`archivedRemoteIds` / `trashedRemoteIds` 走 UPDATE（改成归档态/删除态），`removedRemoteIds` 走 DELETE；
  - **"下落不明"（既不在 INBOX、也不在归档/废纸篓、也没被确认删除）的行会被保留**（`MessageStore.swift:545-547` 的注释："Otherwise: whereabouts unknown. The row stays."）—— 这正是 D-02 修复后的行为。

  所以第一轮 F-05 写的"中间窗口里这行邮件会被同步循环当成收件箱邮件删掉"，**在 `reconcileInbox` 这条路径上已不成立**。但有**两条路径仍然成立**：

  1. **`deleteLiveRows`（UIDVALIDITY 重置路径，`MessageStore.swift:435-442`）没有这个保护**：
     ```sql
     DELETE FROM message_headers
     WHERE account_id = ? AND is_archived = FALSE AND is_deleted = FALSE AND is_sent = FALSE
     ```
     重置轮期间插入的 `is_sent=FALSE` 行**会被删掉**。`deleteLiveRows` 的注释只说"只清收件箱轴"，它**不知道**这一行其实是刚刚从 Sent 目录写进来的。这个函数的唯一调用点是 `SyncEngine.swift:200`（`changes.resetRequired` 分支），而 `resetRequired` 由 `IMAPProvider.swift:389` 在 **INBOX 的 UIDVALIDITY 变化**时置真。
  2. **`removedRemoteIds` 命中时**：`reconcileInbox` 的 DELETE 分支（`MessageStore.swift:537-544`）会删掉这行。`removedRemoteIds` 来自 `IMAPProvider.locateWhereabouts`（`:1345-1365`）—— 它在**归档夹**和**废纸篓夹**里各查一次 Message-ID，**两处都查不到就算"removed"**（`:1352-1354`）。**Sent 夹不在查找范围内**（`locate`（`:1296-1324`）只 resolve 归档夹与废纸篓夹）。所以一封从 Sent 目录写进来的邮件，如果在别处没有副本，会被判为 "removed" 而删除。
- **触发条件**：
  路径 1：用户打开"已发送"（`/api/sent` 触发 `refresh`）**同时**后台同步轮检测到 INBOX 的 UIDVALIDITY 变化（QQ 邮箱偶尔会重建 INBOX 的 UID 空间）。两个窗口重叠时，刚写进来的已发送邮件行被删 → 它在"已发送"列表里消失。
  路径 2：一封已发送的邮件**在服务端没有副本**（例如用户在 QQ 网页版删了它、或它已被 QQ 的清理策略移除），同时 `SentRoutes.refresh` 正在写这一行 → `reconcileInbox` 判定它 "removed" → 删掉。
  **缓解因素**（必须一并说明，否则会高估影响面）：`/api/sent` 的 refresh 每次都会重新从服务端拉取 Sent 目录（`SentRoutes.swift:79-81`），所以被删掉的行**下次打开"已发送"时会被重新写回来**。用户可见的症状是"列表偶尔少一封，刷新后回来"，而不是"永久丢失"。
- **为什么是问题**：
  - 症状是**已发送列表随机缺信**，用户会以为系统丢信。产品的宪法要求"说出来的才是真的"（§3），这里的反面是"没说的丢了"。
  - 第一轮 F-05 把这个描述成"会被同步循环当成收件箱邮件删掉"，**比实际情况严重**。本轮复核后必须修正它：真正成立的是上面两条特定路径，不是"每次同步都会删"。
  - 影响面：被删的行会带走它的 `message_bodies`（`ON DELETE CASCADE`，`LagoonDatabase.swift:473-475`）和 `advice`（同表 `:508-510`）—— 后者意味着**这封邮件的 AI 建议也被清掉了**。这两条复合外键指向 `message_headers(account_id, remote_id)`，而 `message_headers` 上有 `UNIQUE (account_id, remote_id)`（`:364`），所以级联本身是成立的（与 `docs/审查-运行时实测-2026-10-20.md` 报告的 `accounts.id` 编码不匹配是**另一个**外键，不影响这两条）。
- **建议修法**：
  1. **让 `upsert` 一次性写入 `is_sent`**：给 `upsert` 加一个 `isSent: Bool = false` 参数，在 INSERT 列表里带上它，并在 ON CONFLICT 子句里写 `is_sent = CASE WHEN EXCLUDED.is_sent THEN TRUE ELSE message_headers.is_sent END`（只升不降，跟 `is_read` 的 OR 合并同构）。这样两个事务合成一个，窗口消失。
     —— 代价：`upsert` 的"ON CONFLICT 故意不写 `is_sent`"这条设计有它的道理（`is_sent` 来自"这行是从哪个文件夹同步来的"，不是邮件本身的属性 —— `MessageStore.swift:99-108` 把这条理由写得很清楚）。但 `SentRoutes` 的场景恰恰**知道**它来自 Sent 目录 —— 所以让调用方显式声明是合理的，不是破坏设计。
     —— 事实上 `MessageHeader` **已经有** `isSent` 字段（`Sources/LagoonKit/MessageHeader.swift:25, 46, 64`），`IMAPProvider.listSent` 也已经把它设成 `true`（`IMAPProvider.swift:1537-1541`）—— 也就是说**这个信息在 `upsert` 的入参里已经有了，只是被丢掉了**。修复可以只是"把它用起来"。
  2. 或者：把 `upsert` + `markSent` 放进**同一个** `db.write` 闭包，一次提交（需要一个同步版的 `upsert`；目前 `MessageStore` 只有异步的 `upsert`，见 `:30`）。
  3. 无论选哪条，**`deleteLiveRows` 都应加保护**：它可以改成只删"本轮同步确认过的收件箱行"，或者加一个 `synced_from_sent` 列并把它排除在外。
  4. `locate` 应当把 **Sent 夹**也纳入查找范围（或者明确把"不在归档/废纸篓"与"已被删除"区分开），否则 `removedRemoteIds` 的语义是"不在归档或废纸篓"而不是"已被删除"。
- **验证方式**：
  - 单元测试：写一行 `is_sent=FALSE` 的 `message_headers` → 调 `deleteLiveRows` → 断言它**还在**（修好后成立；修好前被删）。
  - 单元测试：插入一行 `is_sent=FALSE` 且不在 `inboxRemoteIds` / `archivedRemoteIds` / `trashedRemoteIds` / `removedRemoteIds` 里的邮件 → 调 `reconcileInbox` → 断言它**还在**（这一条**现在就已经通过**，用来钉住"下落不明就保留"的行为不被回归掉）。
  - 端到端：`/api/sent` 的 refresh 与一次 UIDVALIDITY 重置并发 → 断言已发送列表不丢行。
  - 现有测试位：`Tests/LagoonServerTests/SentListingTests.swift`、`AdvisoryOnlySyncTests.swift`。

  - 规则与项目里实际的做法**不一致**：`MessageStore.swift:210-236` 的注释明确写着，实际做法是"用 `[literal, whereClause].joined()` 拼接**静态片段**、值全部绑定"，而不是"集中到 SQLBuilder"。护栏的措辞和代码库的约定对不上。
- **触发条件**：
  任何人（人或 AI 助手）按规则 1 的字面描述去建 `Sources/LagoonKit/SQLBuilder.swift` 并把插值搬进去 → 护栏**从那一刻起开始放过那个文件里的所有插值**，包括用户数据。那是一个"护栏自己开的洞"。
- **为什么是问题**：
  规则 1 本身工作得很好（`MessageStore.remoteIds` 的注释记录了它曾经漏掉 `LIMIT` 的历史）。问题在于**排除名单指向一个空地址**，这让规则失去了自测，也让读规则的人对"插值应该去哪里"产生误解。
- **建议修法**（三选一，从轻到重）：
  1. **最轻**：把排除名单里的 `SQLBuilder.swift` 删掉（它没有对应的文件），并在规则注释里改成描述代码库的真实约定："SQL 文本里不得出现**值**；静态片段用 `[...].joined()` 拼，值一律绑定"。同时把 `test-guardrails.sh` 的自测改成断言"该文件不存在"（把这条护栏的**契约**从"有一个豁免点"改成"没有豁免点"）。
  2. **中**：保留豁免机制，但让它**有测试覆盖**：在 `test-guardrails.sh` 里用临时目录造一个同名文件验证豁免生效（而不是依赖仓库里真的存在那个文件）。
  3. **最重**：真的建 `SQLBuilder.swift`，把 SQL 构造集中到那里 —— 但这会是一次大重构，且与代码库现有的 `joined()` 约定冲突。**不推荐**。
- **验证方式**：
  - 删掉排除名单后跑 `scripts/ci-guardrails.sh` → 应当仍然通过（当前没有任何一处依赖这个豁免）。
  - `scripts/test-guardrails.sh` 全绿，且**新增**一条断言："规则 1 的排除名单里的每个路径都必须真实存在，否则自测视为失败"。

### D3-14 · `AdviceStore.decode` 的注释说"跳过"，代码是"抛异常"

- 见 D3-06 的引文。**单独列出是因为它是 P3 级的整洁性问题**：注释与实现相反，会误导下一个读代码的人。
- **建议修法**：随 D3-06 一并修 —— 改实现（跳过）或改注释（说明为什么抛），二者必须一致。**优先改实现**（D3-06 的理由成立）。
- **验证方式**：同 D3-06。

## 5. 经核实不成立（候选发现，已排查并放弃）

> 这一节记录**查过但证据不成立**的候选，公开本轮搜索的边界与诚实度。
> 原则：一条无法被证实的发现，比一条漏掉的发现代价更高 —— 所以下面每一条都附了"为什么不成立"的**具体依据**。

| 候选 | 结论与依据 |
|---|---|
| **撤销过滤器 `json_extract(u.payload,'$.undoOf') = ai_actions.id` 的类型不匹配会破坏撤销历史** | **不成立。** 在 `sqlite3` CLI 上直接实测：文本 `'1'` 与整数 `1` 比较为真（SQLite 的比较亲和性会把 TEXT 侧转成数值）；`EXPLAIN QUERY PLAN` 确认子查询走 `ai_actions_undo_of_idx`；构造"一条被撤销的行动 + 一条 undo 行"的库后，`pageSQL` 正确地只返回 undo 行本身、隐藏被撤销的那条。`CAST(a.id AS TEXT)` 形式同样正确。 |
| **搜索的 `LEFT JOIN message_bodies` / `LEFT JOIN advice` 会把行数放大，`COUNT(*)` 与返回行数不一致** | **不成立。** `message_bodies` 的主键是 `(account_id, remote_id)`、`advice` 上有 `UNIQUE (account_id, remote_id)`（`LagoonDatabase.swift:472, 507`），两个 JOIN 对每个 `message_headers` 行最多各贡献 1 行。`DraftRoutes.swift:446-448` 的注释说的"两个 JOIN 不会放大行数"经核对属实。查询计划也确认两个 JOIN 走各自的唯一索引做 seek（`/tmp/sp2.db`）。 |
| **`BriefingRoutes` 的 `omitted` 会因为两次读之间新增邮件而虚报** | **部分成立，已作为 D3-05 记录。** 但需要说明：查到的失败模式是"虚报 1 封"（新来的邮件被说成"未纳入"）与"少报"（归档动作使 `omitted` 归零，从而掩盖真实截断）。**不是**"count 与 rows 来自不同谓词"那种严重的错位 —— 两者用的是同一个 `filterSQL`，谓词一致。 |
| **`MessageStore.upsert` 的 ON CONFLICT 不写 `is_archived` / `is_deleted` / `is_sent`，会在同步轮把用户刚归档的邮件"复活"** | **不成立。** 枚举了全部三处写点：`MessageStore.swift:524/532`（reconcile 的归档/删除标记）、`:720`/`:1106`（`setArchivedSync`/`setDeletedSync`）、`ActionsRoutes.swift:1376`（退订）、`:1891`（撤销归档）。`upsert` 确实不写这三列，但**没有任何路径把它们重置为 FALSE** —— 归档/删除状态是单向的（只有显式的 unarchive/restore 才会翻回）。 |
| **`lagoon_cipher_contains` 被声明为 `pure: true` 但解密不纯（nonce 每次不同）会导致 SQLite 缓存错误结果** | **不成立。** `BodyCipher.seal` 在**封存**时抽 nonce（`BodyCipher.swift:73`），`open` 只用封存的 nonce 解密（`:90`），所以同样的密文 + 同样的 key + 同样的 needle 总是同样的结果 —— `pure: true` 是**正确**的。`sealFunction`（`:223-230`）才是 `pure: false`，且它确实每次抽新 nonce，声明也对。 |
| **`ai_overrides` 的 undo counter-row 会让"最新一行胜出"选出错误的一行** | **不成立。** 排序键是 `ORDER BY o.created_at DESC, o.rowid DESC`（`AIActionStore.swift:753`、`:796`），`rowid` 是**单调递增**的 SQLite 隐式行号，因此同一毫秒内写入的多行也有确定的全序。`AIActionStore.swift:760-763` 的注释解释了为什么需要 rowid，且这个理由成立。 |
| **密钥/凭据以明文形式存在于仓库** | **不成立（符合规则）。** `EmbeddedServer.swift:44-74` 的两个 AES key 都是**首次启动时用 `SecRandomCopyBytes` 生成并存进 Keychain**（`lagoon.tokenKey` / `lagoon.bodyKey`），仓库里没有硬编码的密钥。`Runtime.swift:98-113` 在打开数据库**之前**注入 `keyProvider`（迁移 `lagoon-v6` 需要它来封存遗留正文）。API token 也是 Keychain 生成或来自环境变量。 |
| **`catch` 块静默吞掉错误** | **未发现违反规则的情况。** 逐处检查了数据层里的 `catch`：绝大多数都**记日志**（`logger.error` / `logger.warning`）或转成带上下文的错误。`BriefingRoutes.swift:405-407` 的 `catch { failed += 1 }` 是**计数**而非静默（同函数末尾有 `advice.persistPartial` 的 warning 日志）。`BackupService.swift:290-303` 的 per-message catch 是**计数并上报**（`skipped`），不是吞。 |
| **`DatabaseQueue` 与 `DatabasePool` 混用导致共享可变句柄的并发问题** | **不成立。** 全仓只有一个 `DatabasePool`（`LagoonDatabase.open`，`LagoonDatabase.swift:315`），所有 store / route / 同步循环共享它，`LagoonDB` 是它上面的**接缝**（`LagoonDB.swift:37-47`：`write` 走 `pool.write`、`read` 走 `pool.read`）。`LagoonDB(transaction:)` 只在**调用方已持有事务**时使用，句柄不跨事务存活。`BackupService` 的 `DatabaseQueue` 是**另一个文件、一个独立的只读连接**（`BackupService.swift:148-165`），不共享池状态。 |
| **`reconcileInbox` 的逐行 UPDATE 循环是 N+1，值得单列** | **不成立（不构成独立缺陷）。** 它在**一个 `db.write` 事务内**（`MessageStore.swift:509`），每行一条 `UPDATE ... WHERE account_id = ? AND remote_id = ?`（`:522-544`），走 `message_headers` 的 `UNIQUE (account_id, remote_id)` 索引。行数等于"本轮离开收件箱的邮件数"，通常很小。把它列为 N+1 会夸大问题。 |
| **`usage_log` 的 `year_month` 与 `created_at` 不一致会导致统计错乱** | **不成立（数据本身是自洽的）。** `year_month` 由 `UsageBudget.currentYearMonth()`（`UsageBudget.swift:149-154`）在写时算出，与 `created_at` 同月。真正的缺陷是**那个月份值被冻结**（D3-02），不是两者不一致。 |
| **草稿表 `draft_replies` 的 `list(remoteId: nil)` 只返回 50 条，客户端会漏看草稿** | **不成立（按设计）。** `AIActionStore.swift:929-965` 的 `list` 在 `remoteId` 为 nil 时 `LIMIT 50`，这是"最近的草稿"列表的**明确上限**，且 `remoteId` 给了精确查询。`draft_replies` 是派生数据（草稿会过期），第一轮也没有把它列为用户可见缺陷。**不作为发现。** |
| **`LagoonDatabase` 的 8 个迁移里没有 `CREATE TABLE` 只在全新库运行的路径** | **不成立。** 逐个核对：`lagoon-v2` 全是 `IF NOT EXISTS` / `IF EXISTS`（`LagoonDatabase.swift:230-251`）；`lagoon-v3` 是 `DROP TABLE IF EXISTS`（`:259-261`）；`lagoon-v4` / `lagoon-v7` 是 `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`（`:266-289`、`:163-183`）；`lagoon-v5` 的 `ADD COLUMN is_sent` **故意不在 `schema` 里**（`:204-218` 有专门注释说明"SQLite 没有 `ADD COLUMN IF NOT EXISTS`，若同时写进 `schema` 会在全新安装时报 duplicate column"）；`lagoon-v6` 是 `RENAME COLUMN`（`:196-202`）；`lagoon-v8` 的 `ADD COLUMN scope` 同样**故意不在 `schema` 里**（`:96-110` 同样有注释）。**两条 ADD COLUMN 路径都正确。** |
| **GRDB 把 `Date` 存成 REAL / 与 `strftime` 的 TEXT 格式不一致，导致 `MIN/MAX(received_at)` 解码失败** | **不成立。** GRDB 7 的默认 `Date` 存储格式确认为 `"yyyy-MM-dd HH:mm:ss.SSS"`（UTC）：`.build/checkouts/GRDB.swift/GRDB/Core/Support/Foundation/Date.swift:157` 的 `formatter.dateFormat = "yyyy-MM-dd HH:mm:ss.SSS"`，与 `LagoonDatabase.swift:14-19` 的注释、以及 SQLite `strftime('%Y-%m-%d %H:%M:%f','now')` 的输出**同格式**。`MessageStore.parseStoredDate`（`:1052-1054`）对聚合列走的是手写解析（因为聚合表达式没有声明列类型，GRDB 只能给 String）—— 处理正确。 |

## 6. 本轮的覆盖边界与建议的下一步

**已覆盖**：schema 与 8 个迁移、14 张表的写入路径、`LagoonDB` 接缝与事务边界、所有 store 的读路径与索引覆盖、11 个 route 文件的计数/分页一致性、客户端 4 个批量调用点的失败呈现、`UsageBudget` 的记账周期、`BodyCipher` 的静态 SQL 函数、备份/快照路径、Keychain 与凭据路径。

**未覆盖（下一轮建议）**：
- **并发压测**：本轮用的是 `sqlite3` CLI 的单线程查询计划与耗时，**没有**在真实的 GRDB `DatabasePool`（WAL、多 reader）下测。`LagoonDB` 的写串行化在高压下的表现、以及 D3-09 的探测在真实 WAL 下的耗时，都需要实测。
- **10 万封量级**的查询计划：本轮的性能数字（1.4 s / 7.49 s）是在 2000–3000 undo 行、5000 普通行的合成库上测的；真实量级下线性增长会到什么程度需要专门测量。
- **客户端与服务端的契约一致性**：本轮只抽查了批量操作的失败呈现（4 个调用点）与简报的 `omittedCount`；其余路由的字段级契约没有全量比对。
- **IMAP 协议层**：本轮未覆盖 `IMAPClient` / `IMAPProvider` 的协议细节（第一轮已覆盖 F-02 / F-08 / F-09 等），只追了它们与数据层交互的边界。
- **迁移的真实升级路径**：`SchemaMigrationTests` 覆盖了迁移标识符与幂等性，但没有"从 3.2.0 时代的旧库真实升级"的端到端演练（`docs/审查-运行时实测-2026-10-20.md` 报告的 `accounts.id` 编码不匹配问题正属于这一类）。
