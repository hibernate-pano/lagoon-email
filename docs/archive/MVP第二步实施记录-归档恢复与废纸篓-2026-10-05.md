## 做了什么

### 1. 两条新路由（协议能力已存在，只是没接线）

| 路由 | 作用 | 底层 |
|---|---|---|
| `POST /api/messages/{id}/unarchive` | 取消归档：档案柜 → 收件箱 | `provider.unarchive`（早已实现） |
| `POST /api/messages/{id}/restore` | 从废纸篓恢复：废纸篓 → 收件箱 | `provider.restoreFromTrash`（早已实现） |

**关键判断**：这两个能力在 `MailProvider` 协议里一直有实现，但只被 ⌘Z 的 8 秒撤销窗口用到。归档不是 8 秒的决定——用户三月归档、七想找回是常态。所以补的是**路由**，不是 IMAP 能力。风险因此远低于新建 `expunge`。

两个处理器都严格复刻 `archiveHandler` 的形状：同样的能力门控、同样的「远端先动、本地后翻」、本地提交失败时**补偿回滚**、同样写审计行。写成另一个形状正是「恢复功能半可用」的来源——远端动了本地没动，或本地翻了但没审计行导致 ⌘Z 静默无效。

### 2. 废纸篓终于能列出内容

**这是审计里最严重的一项，之前完全没人发现**：

- `MessageStore.filterSQL` 里 `is_deleted = FALSE` 是**硬编码**的
- 也就是说**没有任何 API 能列出废纸篓里的邮件**
- 用户删错邮件时，唯一出路是 8 秒的撤销 toast，或换一个邮件客户端

现在 `/api/messages?deleted=true` 可以列了。

### 3. 修掉一个孤儿邮件 bug（测试抓到的）

`TrashListingTests` 写完后立刻失败：先归档、后删除的邮件**在两个列表里都不出现**。

- 废纸篓查询问 `is_archived = FALSE`，而这封是 TRUE
- 档案柜查询问 `is_deleted = FALSE`，而这封也是 TRUE

结果：邮件在服务器 Trash 文件夹里，但在应用里**永久不可见**。这比"没有废纸篓视图"更糟。

修复：废纸篓列表**完全忽略归档维度**——废纸篓的定义是"服务器 Trash 文件夹里的一切"，而档案柜保持镜像规则（排除已删除）。这样每封邮件恰好出现在一个地方。

### 4. 侧边栏「废纸篓」不再指向错误的列表

`Lens.init` 里 `case .deleted: self = .all` 改成了 `self = .deleted`。

这是**我上一轮引入的**：当时注释写"Reachable only for restore"，但我没实现那个 restore UI，留下一个点开显示收件箱的按钮。假按钮比没有按钮更糟——用户会以为删除没生效。

### 5. 三个列表的行内菜单按位置分化

| 位置 | 菜单内容 | 滑动操作 |
|---|---|---|
| 收件箱 | 标已读、置顶、归档、聚合、发件人邮件、删除 | 归档 |
| **档案柜** | **取消归档**、标已读、置顶、删除 | 归档 |
| **废纸篓** | **恢复到收件箱**、删除 | **恢复**（绿色） |

废纸篓的菜单刻意短：其他项要么已完成（标已读），要么无意义（归档一封在废纸篓里的邮件）。

## 测试抓到的三个自身错误

这一轮的三个错误全部由测试或守卫发现，值得记录：

### 1. 测试 fixture 默认没有能力位

`Account` 的 `capabilities` 默认是 `MailCapabilities.unknown`（全 false），所以 `unarchive` 一直返回 409 而不是我期望的 200——**测试在断言能力门控，而不是在测路由**。

修法：`makeAccount(archiveFolder:)` 显式传能力。顺带让 409 那个用例把账户能力也关掉，这样它证明的是"路由读账户标志"而不是"路由问 provider"。

### 2. `RefreshGateTests` 抓到漏掉的 invalidate

`insertBack`（恢复失败后把行放回去）直接改 `messages`，没有 `invalidatePendingRefresh()`。守卫报："removes a row without retiring the in-flight poll; the row will come back"。

守卫是对的：一次在恢复失败前就发出的 poll，会把恢复前的快照写回来，让刚放回去的行又消失——看起来像应用在丢邮件。

修法：把 invalidate 放进 `removeRow` 本身，而不是每个调用点。守卫要求 invalidate 与它保护的 mutation 相邻，而且放进唯一入口是唯一不会漏的方式。

### 3. `Account` 的 `capabilities` 是 `let`

我先写成了 `account.capabilities = ...`，编译不过。它是 `init` 参数。

## 还没做（需要你决策）

### P0-1 剩余：永久删除与清空废纸篓

协议里**没有** `expunge`，需要新建 IMAP 能力。这与上面两条性质不同——不是接线，是新增能力，且触及同步热路径。

**需要你决定**（详见 `功能审计报告-2026-10-05.md` 第五节）：

1. 永久删除的确认强度。宪法 §2 要求所有变更可撤销，而永久删除天然不可撤销。Gmail 的做法值得注意：**「Empty Trash」带 Undo 按钮**，把不可逆操作做成了可撤销的；网易则用二次确认弹窗。
2. 是否要做 Gmail 的两段式全选（"已选 48 封" + "选择全部 3,142 封"）。这个纯客户端，数据基础（`serverTotalCount`）已现成。

## 附：本次学到的最重要一课

**`is_deleted = FALSE` 硬编码在共享的 filter clause 里，这件事本身没有错**——它让所有默认视图正确地排除已删除邮件。

错的是**没人问过"那废纸篓里的邮件怎么列出来"**。这个缺失在代码里是完全不可见的：一行硬编码，一个 200 响应，没有任何报错。侧边栏的废纸篓计数甚至是对的（`deletedCount` 单独查），所以从数字上完全看不出问题。

它是被"点开废纸篓却看到收件箱"这个 UI 现象暴露的——而那个现象又是三栏导航把废纸篓放到显眼位置才被看见的。

**功能缺失最危险的形态不是"报错"，是"看起来正常"。**
