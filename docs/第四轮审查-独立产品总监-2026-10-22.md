## 0. 一句话结论

**Lagoon 的骨架是干净的（advisory-only 真的由编译器保证、撤销体系是真的、草稿是真的存盘的），但它现在对外说话的方式在骗人：产品承诺说"每天开两次、10 分钟清零、常驻即失败"，代码交付的却是一个常驻收信的常驻进程；一条本地密钥故障被文案说成"你的邮箱设置不完整"并把用户推向重新输入 QQ 授权码；一次不可逆的"清空废纸篓"报的数字不是它真删的数字。** 拿出去给人看，会被问住三个问题：**你到底常驻还是无常驻？你的 AI 建议是几号说的？你的授权码为什么要我重输？**

P0 2 条、P1 6 条、P2 8 条、P3 5 条。

## 1. 发现清单

### P0 · 破坏性

#### PV-01 · 本地密钥读不出来时，产品把原因说成「你的邮箱设置不完整」，并把用户推向重新输入 QQ 授权码

- **现象**：当本机钥匙串读取被系统授权弹窗挡住、或本地加密密钥与库里的数据对不上时，Lagoon 顶部挂出红色横幅「**需要重新连接 —— 重新连接后继续同步。/ 邮箱设置不完整，请重新连接并补全授权信息。**」，唯一的按钮是「重新连接」，点开是 QQ 授权码表单。用户照做 → 回 QQ 邮箱重新生成一枚授权码 → **原来那枚还能用的授权码被 QQ 立即作废**。
- **证据**：
  - `Sources/LagoonServer/IMAP/IMAPProvider.swift:923-931` —— 三种**本地**故障全部塌缩成一个标签：
    ```swift
    do {
        credentials = try CredentialVault.open(blob)
    } catch {
        throw MailError.notConfigured("credentials unreadable")   // ← 密钥解不开
    }
    ...
    throw MailError.notConfigured("imap credentials missing")     // ← 库里没有
    ...
    throw MailError.notConfigured("credential kind mismatch")      // ← 类型不对
    ```
  - `Sources/LagoonServer/Mail/MailProvider.swift:289` —— `.notConfigured: return "not-configured"`，那个 `String` 原因被丢掉了。
  - `Sources/Lagoon/Localization/SyncErrorReason.swift:47-48` + `Sources/Lagoon/Localization/L10n.swift:656-658` —— `not-configured` → 「邮箱设置不完整，请重新连接并补全授权信息。」
  - `Sources/Lagoon/Views/RootView.swift:929-936` —— `.needsReconnect` → 标题 + 「重新连接」按钮 → `reconnect()`（`RootView.swift:1196-1200`）→ `ConnectView(prefillEmail:)`。
  - **实机复现**：本次审查实跑 App，服务端日志 `imap.capabilitiesFailed label=not-configured` / `sync.needsReconnect`，界面正是这条红色横幅（截图 `07-main.png`）。而当时**根本没有网络问题、也没有凭据问题**——只是我的沙箱里读不到 `lagoon.tokenKey`。
- **为什么不对**：三种本地故障被一句话说成"用户配置不全"，责任被推给用户。**重新输入授权码修不了本地密钥问题**；而"授权信息有问题"这个说法最自然的用户动作就是去 QQ 邮箱重置授权码——那会真的把一枚可用凭据作废。这是把一次可自愈的本地故障，变成一次真实的凭据损失。README 里「授权码…不会出现在日志、错误信息或任何 API 响应里」的保护是到位的，但保护的是密钥，**误导的是人**。
- **建议怎么修**：
  1. `Sources/LagoonServer/Mail/MailProvider.swift:289` —— `notConfigured(String)` 把原因编进 label：`credentials-unreadable` / `credentials-missing` / `credential-kind-mismatch`（保留 `not-configured` 给真正的 provider 缺失）。
  2. `Sources/Lagoon/Localization/SyncErrorReason.swift` + `Sources/Lagoon/Localization/L10n.swift` —— 为这三个新标签各写一句人话，例如「本机密钥与本地数据对不上（Lagoon 无法解密已保存的授权信息）。点『重试』；若仍然不行，请到设置里重新填一次授权码。」
  3. `Sources/Lagoon/Views/RootView.swift:929-936` —— 这三个标签下的按钮**不要**是「重新连接」，改成「重试」；只有真正的 `auth-failed`（QQ 明确拒绝）才给「重新连接」。
  4. `Sources/Lagoon/Views/ConnectView.swift` —— 覆盖旧凭据前给一次明示：「重新连接会用新授权码覆盖当前保存的那枚」。

#### PV-02 · 「清空废纸篓」告诉用户的数字，不是它真删的数字

- **现象**：用户点「清空废纸篓」，确认框写「即将永久删除 N 封」，执行完提示「已永久删除 N 封」。但服务端实际把**服务器废纸篓文件夹里的全部 UID** 都 EXPUNGE 掉——包括 Lagoon 从没见过、别的客户端删掉、还没同步进来的邮件。而 N 是 Lagoon **本地缓存**里废纸篓的行数。两个方向都会错：服务器里更多 → 少报；用户已从别处删掉的本地还留着 → 多报。
- **证据**：
  - `Sources/LagoonServer/IMAP/IMAPProvider.swift:1095-1115` —— 整夹清空：
    ```swift
    let uids = try await client.allUIDs()
    for uid in uids { try await client.store(uid: uid, add: ["\\Deleted"]) }
    try await client.uidExpunge(uids: Array(uids))
    ```
  - `Sources/LagoonServer/Routes/ActionsRoutes.swift:648-654` —— `remoteIds = MessageStore.trashedRemoteIds(...)`（**本地行**）。
  - `Sources/LagoonServer/Routes/ActionsRoutes.swift:693-696` —— `purged: remoteIds.count`（**本地行数**）。
  - 路由自己的注释已经承认了：`Sources/LagoonServer/Routes/ActionsRoutes.swift:617-622` ——「The count reported is the number of **local** rows … it is the one place the number the user sees is not a number the provider confirmed.」
  - `Sources/Lagoon/Views/MessageListView.swift:735` —— 确认框用 `l10n.emptyTrashConfirm(serverTotalCount ?? messages.count)`（还是本地数）。
  - `Sources/Lagoon/Views/MessageListView.swift:2068` —— `mutateMessages { $0.removeAll() }`（本地列表整列清空，不管服务器删成功几条）。
- **为什么不对**：不可逆操作给的确认数字必须等于它真正销毁的范围。Apple Mail 的「清空废纸篓」同样整夹清空，但它给的数字是**服务器的真实数量**。Lagoon 给的是一份可能过期两周的本地缓存的条数——用户拿它当"我只会毁掉这些"的依据，这个依据是错的。`docs/使用说明.md` 里还写着「面板会逐项回报成功/失败的数量」，而 `PurgeResponse`（`Sources/Lagoon/Services/ClientResponses.swift:54-58`）里根本没有失败计数字段。
- **建议怎么修**：
  1. `Sources/LagoonServer/Routes/ActionsRoutes.swift:623-696` —— 先 `provider.trashedCount()` 拿服务器真实条数，塞进 `PurgeResponse`（加 `serverCount` / `failedCount`）。
  2. `Sources/Lagoon/Views/MessageListView.swift:735` 与 `:2071-2075` —— 确认框与结果提示都改用服务器数，并明说「将永久删除服务器废纸篓里的全部 N 封（包括其他客户端移进去的）」。
  3. `Sources/Lagoon/Views/MessageListView.swift:2068` —— 只清掉真正被确认删除的 remoteId，剩下的留在列表里并标「已不在服务器上」。

### P1 · 违背承诺

#### PV-03 · README 的头号定位句，和产品实际形态正好相反

- **现象**：README 第一句把产品的成功标准写成「*open twice a day, ten minutes to zero; **running resident all day = failure***」；`docs/superpowers/specs/2026-09-23-v2-inbox-os-final-design.md:16` 写的是「成功标准：每天打开 2 次、每次 10 分钟清零。**常驻挂着 = 失败。**」但 Lagoon 交付的恰恰是一个**常驻进程**：每个账号一条 IMAP IDLE 长连接、App 级 30 秒轮询、窗口关掉后继续跑的系统通知和 Dock 角标。`docs/使用说明.md` 甚至把常驻写成**卖点**：「通知和 Dock 角标在窗口关掉之后仍然工作——这是它们的全部意义」。
- **证据**：
  - `Sources/LagoonServer/Sync/SyncEngine.swift:12-14` —— `/// it is never quieter than one round per 5 minutes even when idle.` / `public static let waitBudget: Duration = .seconds(300)`；`:47-55` 的 `run()` 是 `while !Task.isCancelled` 的无限循环。
  - `Sources/Lagoon/Platform/MailboxMonitor.swift:63-71` —— `pollInterval = .seconds(30)`，App 级轮询。
  - `Sources/Lagoon/LagoonApp.swift:9-11` —— 「The badge and the notification need a poller that outlives the window, so it lives here rather than in a view.」
  - `docs/使用说明.md`「macOS 系统集成」表格下：「通知和 Dock 角标在**窗口关掉之后仍然工作**——这是它们的全部意义，所以轮询在 App 级别，不在窗口级别。」
- **为什么不对**：这不是措辞问题，是**产品定义问题**。「每天开两次」和「常驻收信 + 后台分类 + 主动推送」是两种不同的产品，对用户的要求、对电池的要求、对 QQ 邮箱连接稳定性的要求全不一样。更要命的是：**「10 分钟清零」这个承诺其实只有在后台一直在分类的前提下才成立**——你不在的时候没人替你把 272 封分好组，第二天的「清零」其实是上一班的成果。现在的产品既没兑现那句话，也没承认它变了。另外，"running resident = failure" 这条写在 README 里，等于在对外说"我们现在做的事就是失败"。
- **建议怎么修**：**二选一，然后三处口径统一（README 第一段 / `docs/使用说明.md` 的集成表 / 宪法或 V2 spec 的成功标准）**。
  - 推荐 (a)：承认常驻，把 README 改成「**一直在收信，两次打开清零**」，并把 V2 spec 的"常驻挂着 = 失败"标为"已废弃的早期判据"；理由是常驻能力（角标、通知、后台分类）已经落地且价值真实，砍掉它比改文案贵得多。
  - (b) 若坚持无常驻：IDLE 循环、30 秒轮询、系统通知、Dock 角标四件全砍，产品退回"打开才同步"，这基本等于重做。
  - 另外无论选哪个，"10 分钟清零"应该**可度量**：现在 `TimeSavedBar` 显示的是"估算节省 X 分钟"，口径是"按动作条数乘常数"（`Sources/LagoonKit/TimeSaved.swift:5-8` 自己写着"declared estimates, not measurements"）。产品应该有一个真的计时器：从你打开简报到收件箱归零用了多久，那个数字才是这句话的兑现。

#### PV-04 · 第一次打开的用户拿不到这个产品的主卖点：AI Key 藏在 ⋯ 溢出菜单里

- **现象**：新用户连上 QQ 邮箱后的第一屏，是一条蓝色 info 横幅「**AI 未配置 / 填上服务商 Key 即可启用摘要和草稿，邮件不受影响。**」+ 一个「AI 设置」按钮。在那之前，简报里的每封邮件都只有本地启发式分组——**没有摘要、没有 AI 建议、没有草稿按钮**。而 Lagoon 整个产品定义就是 AI 驱动的分拣机。更糟的是这条横幅**每 30 秒自己回来一次**，用户关不掉。
- **证据**：
  - `Sources/Lagoon/LagoonApp.swift:71-76` —— 首次启动只有 ConnectView，连上后直接 RootView，**没有 AI 步骤**。
  - `Sources/Lagoon/Views/ConnectView.swift:84-147` —— 连接页三步：说明 / 拿码 / 表单，全是 QQ 邮箱，**一句 AI 都没有**。
  - `Sources/Lagoon/Views/RootView.swift:1250-1291` —— 「AI 设置」在工具栏 ⋯ 溢出菜单的第 2 项。
  - `Sources/Lagoon/Views/RootView.swift:983-994` —— 横幅 severity 是 `.info`，按钮 `showAISettings = true`。
  - `Sources/Lagoon/Views/RootView.swift:712-723` —— 每次 30 秒轮询把 `aiStatusDismissed = false` 重置回去：
    ```swift
    // A dismissal only lasts until the next poll: if the
    // underlying state is still bad, the banner comes back.
    syncHealthDismissed = false
    loadErrorDismissed = false
    aiStatusDismissed = false
    ```
  - **实机复现**：截图 `07-main.png`（红横幅）与 `10-banner-dismissed.png`（关掉红色后蓝色立刻顶上）。
- **为什么不对**：产品的全部价值主张是 "AI Inbox OS"（`docs/superpowers/specs/2026-10-02-advisory-only-ai-constitution-design.md` 里 AI 平面是主轴）。首次路径却把 AI 降级成一个设置项，还塞在溢出菜单里——这是"把主菜写在配料表上"。Superhuman 的 onboarding 第一屏就是粘 API key；这里应该是一步，或者至少在连接成功后**立刻弹出一次** AI 设置（而不是靠一条可以被关掉的横幅）。
- **建议怎么修**：
  1. `Sources/Lagoon/LagoonApp.swift:71-76` —— 连接成功后，如果 `directory.aiStatus?.configured == false`，把首次 `AISettingsSheet` 直接顶上来（一次性），标题写「最后一步：接上 AI，Lagoon 才能替你分拣」，并说明「不接也能用，但只有本地规则」。
  2. `Sources/Lagoon/Views/ConnectView.swift` —— 第 3 步加一句「第 3 步（可选）：填 AI Key」。
  3. `Sources/Lagoon/Views/RootView.swift:712-723` —— 见 PV-10：把「AI 未配置」改成用户关掉就记住。

#### PV-05 · AI 额度用尽时，横幅的按钮是「重试」，而重试的是邮件同步

- **现象**：当月度 AI 额度用尽，横幅写「AI 额度已用尽 / …」，按钮是「**重试**」。用户点下去触发的是 `api.requestSync()`——重新拉一遍邮件。这不会恢复 AI，不会告诉他钱花完了，也不在任何一个能充值的界面上。
- **证据**：`Sources/Lagoon/Views/RootView.swift:995-1003`
  ```swift
  if status.creditExhausted {
      return ErrorBanner(
          severity: .warning,
          title: l10n.aiCreditTitle,
          detail: l10n.aiCreditDetail,
          actionLabel: l10n.retry,                          // ← 「重试」
          action: { [self] in await self.retrySync() }      // ← 重试的是邮件同步
      )
  }
  ```
  `retrySync()` 在 `Sources/Lagoon/Views/RootView.swift:1169-1182`：`try await api.requestSync()` + `await directory.refresh()`。
  `circuitOpen` 分支（`RootView.swift:1004-1011`）更糟：**根本没有按钮**——而 `RootView.swift:838-843` 的注释自己写着「on the circuit-open banner that ✕ was the *only* thing to click」。
- **为什么不对**：`docs/使用说明.md` 给全产品立的规矩是「标题说『什么失败了』，第二行说『为什么』，然后给**一条能走的路**」。这里标题说"额度用尽"，按钮说"重试"，重试的是另一件事——用户被送到一个不会解决问题的按钮前。真正该给的入口是 `AISettingsSheet` 里的预算/上限设置（`Sources/Lagoon/Views/AISettingsSheet.swift` 就有），而它就在 ⋯ 菜单里躺着。
- **建议怎么修**：
  1. `Sources/Lagoon/Views/RootView.swift:995-1003` —— `actionLabel` 改为 `l10n.aiSettingsTitle`，`action` 改为 `showAISettings = true`（并把 detail 写清"当前上限 $X，已用 $Y，去 AI 设置调整上限"）。
  2. `Sources/Lagoon/Views/RootView.swift:1004-1011` —— `circuitOpen` 同样给一个按钮（「AI 设置」或「知道了」，且这个是可自愈的，30 秒回弹可以接受）。

#### PV-06 · 快捷键表把 ⌘[ 说成「返回上一级」，还宣称是全局的——而它其实是三件事

- **现象**：快捷键表（⌘/）第一行：`⌘[ → 返回上一级`，**没有作用域标签**（这张表里没有标签 = 全局）。实际：简报页 ⌘[ 是「清空当前选择」、收件箱页 ⌘[ 也是「清空当前选择」、只有搜索面板里 ⌘[ 才是「返回上一级」（弹出搜索结果路径）。
- **证据**：
  - `Sources/Lagoon/Views/ShortcutsSheet.swift:83` —— `Entry(id: "back", keys: "⌘[", description: l10n.backHelp, scope: .global)`
  - `Sources/Lagoon/Localization/L10n.swift:156-158` —— `backHelp = pick("返回上一级（⌘[）", "Back one level (⌘[)")`
  - `Sources/Lagoon/Views/BriefingFeedView.swift:885-891` —— `Button(l10n.back) { selection = [] }` ← 清空选择
  - `Sources/Lagoon/Views/MessageListView.swift:836-843` —— `Button(l10n.back) { selection.removeAll(); selectedAllOnServer = false }` ← 清空选择
  - `Sources/Lagoon/Views/SearchSheet.swift:289-293` —— `if !path.isEmpty { path.removeLast() }` ← 这才是「上一级」
- **为什么不对**：`Sources/Lagoon/Views/ShortcutsSheet.swift:18-24` 自己写着「**A ghost key in a cheatsheet is worse than no cheatsheet**: the user presses it once, sees nothing, and stops trusting the whole sheet.」这张表教的正是一个不存在的全局行为。
- **建议怎么修**：拆成两行——`⌘[ 返回上一级`（scope: 搜索面板）+ `⌘[ 清除当前选择`（scope: 邮件列表）；或者统一语义（都改成"清除选择"）并把 `backHelp` 改成对应文案。另外 `ShortcutsSheet` 现在的 `scope` 只有"全局/仅简报/邮件列表/仅收件箱/仅阅读器/仅写信时"，缺一个"搜索面板"，得补一个 case。

#### PV-07 · ⌘K 到不了废纸篓 / 档案柜 / 已发送 / 置顶——键盘优先的产品，在不可逆动作前必须用鼠标

- **现象**：命令面板（⌘K）只有 14 个**动作**，没有任何"导航到某个位置"的条目。用户要彻底删除一封邮件、或查看已归档 / 已发送，必须先用鼠标点侧边栏。⌘K 里没有它们。
- **证据**：
  - `Sources/Lagoon/Views/CommandPaletteView.swift:64-95` —— `allCommands` 全部 14 条：`new-message / search / toggle-surface / refresh / get-new-mail / usage / ai-settings / advice / reminders / senders / density / history / shortcuts / sound`，**没有一条是 destination**。
  - `Sources/Lagoon/Platform/AppCommandRouter.swift` —— `Command` 枚举里唯一的 destination 是 `.showUnread`（且只被 `lagoon://unread` 深链接用，UI 无入口）。
  - `Sources/Lagoon/Views/Sidebar.swift:117-132` —— 废纸篓 / 档案柜 / 已发送 / 置顶只在这里。
  - 面板本身是 `.sheet`（`Sources/Lagoon/Views/RootView.swift:550-552`），所以这些位置在 ⌘K 里**永远**不可达。
- **为什么不对**：README 第一句就是 "keyboard-first triage machine"，`docs/superpowers/specs/2026-09-23-v2-inbox-os-final-design.md:108` 的验收是「j/k/⌫/R 全程不用鼠标清零 50 封」。清零走得到，但**清完之后处理废纸篓、彻底删除回不到键盘**——而彻底删除恰恰是唯一不可逆的那个动作，最需要键盘路径和确认。

#### PV-17 · 写了一半的邮件草稿存在 UserDefaults 明文里，和产品宣称的"落盘即密文"不一致

- **现象**：用户自己写的草稿（新建 / 回复 / 转发）序列化成 JSON，**明文**写进 `UserDefaults`（`~/Library/Preferences/…`），不是 SQLite、不是钥匙串、也没有用 `BodyCipher` 封。
- **证据**：`Sources/Lagoon/Views/ComposeFlow.swift:61-66`
  ```swift
  func save(_ draft: Draft) {
      if draft.isEmpty { defaults.removeObject(forKey: key) }
      else if let data = try? JSONEncoder().encode(draft) { defaults.set(data, forKey: key) }
  }
  ```
  槽位 key：`Sources/Lagoon/Views/NewMessageSheet.swift:82`（`lagoon.compose.<accountId>`）、`Sources/Lagoon/Views/ComposerSheet.swift:127`（`lagoon.composer.<accountId>.<remoteId>`）、`Sources/Lagoon/Views/ForwardSheet.swift:91`（`lagoon.forward.…`）。
  对比 README「Security posture」一节：「Message bodies are sealed at rest with AES-256-GCM (BodyCipher) … the key lives in the Keychain (lagoon.bodyKey), never on disk」。
- **为什么不对**：一封还没发出去的回复，往往是用户整个邮件生活里最敏感的一段文字（合同、报价、病情、薪酬）。产品对**收件箱里**的正文做到了落盘密文，对自己写的草稿却是明文 plist——同一个产品里两套标准，而用户看不到区别。另外 `defaults` 里的 plist 还会被 Time Machine / 迁移助手带走。
- **建议怎么修**：把 `ComposeFlow.DraftSlot` 的存储从 `UserDefaults` 换成 SQLite + `BodyCipher`（`Sources/LagoonKit/BodyCipher.swift` 已有现成的），或至少换成一个文件级的 AES-GCM 加密文件。

#### PV-18 · 草稿存了，但没有草稿箱——用户不知道自己有草稿，也找不回其中某一封

- **现象**：用户给 5 封邮件各写了半封回复、逐个关掉窗口，这些草稿**都还在磁盘上**，但：侧边栏没有「草稿箱」入口，⌘K 里没有，界面上任何地方都不显示"你有 5 份草稿"。唯一的找回路径是：**回到那一封邮件，再点一次「回复」**。
- **证据**：
  - `Sources/Lagoon/Views/ComposeFlow.swift:44-77` —— 槽位是按 `accountId + remoteId` 命名的**独立** key，没有索引。
  - `grep -rn "DraftPickerSheet" Sources/` 只有两处：`Sources/Lagoon/Views/DraftPickerSheet.swift:7`（定义）和 `Sources/Lagoon/Views/MessageDetailView.swift:256`（**那是挑 AI 草稿变体，不是用户草稿**）。
  - 侧边栏 `Sources/Lagoon/Views/Sidebar.swift:117-132` 里没有任何草稿入口。
- **为什么不对**：这是典型的"**功能没有入口**"：数据被好好地存下来了，但没有索引、没有入口、没有提示。用户既不知道草稿存在，也没法一次看完它们。一封被"稍后继续"关掉的回复，用户很可能再也不会回来找——那这个"稍后继续"按钮实际上等于"丢弃但假装保存"。
- **建议怎么修**：给 `ComposeFlow.DraftSlot` 加一个"列出全部草稿"的接口（`UserDefaults.dictionaryRepresentation()` 过滤 `lagoon.compose./composer./forward.` 前缀即可），在侧边栏「位置」下加一行「草稿（N）」，点进去是一个列表（收件人 / 主题 / 更新时间 / 打开 / 删除）。数量徽章在有草稿时显示。

#### PV-19 · 「移除账号」的确认框列了会被删的三样东西，唯独没提草稿——而草稿确实还在磁盘上明文躺着

- **现象**：「移除账号？」的正文写「会删掉这个账号在 Lagoon 里的本地缓存（**邮件、建议、撤销记录**）。服务器上的邮件不会被删除」。用户据此认为"这个账号的东西都清干净了"。实际上：草稿（收件人地址 + 正文）**明文留在 UserDefaults 里**，而且因为槽位 key 带 `accountId`，账号删掉之后**再也无法被打开**——它变成了永久不可达的明文残留。
- **证据**：
  - `Sources/Lagoon/Localization/L10n.swift:577-583` —— 那句确认文案。
  - `Sources/Lagoon/Views/RootView.swift:1084-1096` —— `removeAccount` 只调 `directory.remove(account)` → `DELETE /api/accounts/:id`；`grep` 全仓**没有任何**代码在删账号时清理 `lagoon.compose.` / `lagoon.composer.` / `lagoon.forward.` 前缀的 UserDefaults 项。
- **为什么不对**：不可逆操作给出的说明必须完整。它现在漏了一样东西，而漏掉的恰好是**明文保存的那一样**。
- **建议怎么修**：`Sources/Lagoon/Views/RootView.swift:1084-1096` —— 移除账号成功后遍历 UserDefaults，删掉 `lagoon.compose.<id>` / `lagoon.composer.<id>.*` / `lagoon.forward.<id>.*`；同时把 `removeAccountConfirmMessage` 的清单补上「草稿」。

#### PV-20 · ⌘K 面板缺语言切换 / 设置 / 关于，且面板下方留了一大片空白

- **现象**：命令面板 14 条命令里没有「语言」「设置（⌘,）」「关于」——这三样在工具栏 ⋯ 菜单和菜单栏里都有，用户按 ⌘K 找它们会扑空。另外面板高度固定，14 条命令只占上半屏，下半屏是空白（实测截图 `08-palette.png`）。
- **证据**：`Sources/Lagoon/Views/CommandPaletteView.swift:64-95`（14 条）；`Sources/Lagoon/Views/RootView.swift:1279-1286`（语言 Picker / 关于按钮在 ⋯ 菜单里）；`Sources/Lagoon/Views/CommandPaletteView.swift:120-123` —— `.frame(width: LagoonSheetSize.standard.width, height: LagoonSheetSize.standard.height)` 是固定高度。
- **为什么不对**：⌘K 是这个产品宣称的"power-user fast path"。一个面板如果不能到达设置和关于，它就不是"所有动作的索引"，只是"常用动作的索引"——用户预期落空一次就会退回用鼠标。
- **建议怎么修**：加 `language`（切换中/英）、`settings`（⌘,）、`about` 三条命令；面板高度改成 `.frame(minHeight: ...)` 或用 `LagoonSheetSize` 的紧凑档，让内容自适应。

#### PV-21 · 命名与入口的小碎步：同一个地方两个名字、同一件事两个设置页

- **现象**：（a）侧边栏写「已归档（**档案柜**）」，而 `docs/使用说明.md` 通篇叫它「档案柜」，`docs/superpowers/specs/2026-09-23-v2-inbox-os-final-design.md` 也叫「archive cabinet」——一个东西三个叫法；用户自己的分组也叫「我的分组」，简报的五个分组也叫"分组"，`Sidebar.swift:133-168` 专门加了 caption 才说得清。（b）「关于」有两个入口：应用菜单的「关于」打开 `AboutSheet`，而设置窗口里还有一个「关于」页签（`Sources/Lagoon/Views/SettingsView.swift:55`）。
- **证据**：`Sources/Lagoon/Localization/L10n.swift:1263`（`stackArchivedRow = "已归档（档案柜）"`）、`Sources/Lagoon/Localization/L10n.swift:1099`（`sidebarDeleted = "废纸篓"`）、`Sources/Lagoon/Views/SettingsView.swift:49-55`（四个页签）、`Sources/Lagoon/Views/RootView.swift:562-564` + `Sources/Lagoon/Views/AboutSheet.swift`（应用菜单的关于）。
- **为什么不对**：不是大错，但"拿出去给人看"的时候，命名不一致是最容易被指出来的粗糙处——尤其「已归档（档案柜）」这种括号式双名，读起来像没想清楚。
- **建议怎么修**：定一个名（建议「档案柜」或「已归档」二选一），全局统一；「关于」只留应用菜单那一个，或设置页签改名成「数据与版本」。

## 2. 与产品定位的系统性矛盾

### 2.1 「无常驻」 vs 「常驻是卖点」（见 PV-03）

这是**最根本**的一条。README 的定位句、V2 spec 的成功标准、宪法精神（用户不在的时候不该有后台行为）说的是"无常驻"；代码交付的是常驻进程 + 后台分类 + 主动推送。

产品必须选一个。而且选"常驻"其实是更诚实的那个——因为"10 分钟清零"这个承诺**只有在后台持续分类时才成立**。所以真正要改的不是代码，是那句 README。改完之后，"10 分钟"也需要一个真的度量（见 PV-03 的建议）。

### 2.2 「AI 只是副驾」 vs 「AI 是这个 App 的主角」

宪法 `docs/superpowers/specs/2026-10-02-advisory-only-ai-constitution-design.md:12` 的定义是「AI 只读、只理解、只建议；任何对用户数据的变更都必须由用户亲自触发」。

**这份宪法在"写"这一层是成立的，而且做得比大多数产品干净**：`Sources/LagoonServer/Mail/MailProvider.swift:309-330` 的 `MailSyncReading` 协议真的没有写方法，同步循环持有的类型真的编译不过写调用；`Sources/LagoonServer/Storage/MessageStore.swift:99-102` 的 `upsert` 真的不写 `is_deleted` / `is_sent`；`is_archived` 只由用户触发的路由写。**这是本次审查里我最愿意表扬的一处。**

但产品叙事上有一处错位：**简报——也就是这个 App 的默认落地页、产品的门面——的五分组是 AI（或 AI 的替身：本地启发式）决定的**。AI 关掉时，分组会换成启发式的；AI 熔断时，也会换。用户自己的「我的分组」和简报的五组是两套机制，`Sources/Lagoon/Views/Sidebar.swift:133-168` 专门加了三行 caption 才说得清。

所以产品实际上同时在讲两个故事：**"AI 只是个建议者"**（宪法、文案）和 **"AI 替我决定了收件箱怎么分"**（界面现实）。两者不冲突（分组不是写操作、不可逆），但**用户读到的不是同一件事**。建议把话说明白：README 现在的副标题 "An AI Inbox Operating System" 读起来像"AI 是操作者"，而宪法说 AI 不是。这个矛盾会同时影响潜在用户对**信任边界**的判断——而信任边界恰恰是这个产品最值钱的资产。

### 2.3 「键盘优先」 vs 「最不可逆的动作只能用鼠标」

README 说 "keyboard-first triage machine"。分拣（j / k / ⌫ / ⌘E / ⌘A）确实全程键盘。但**回收与彻底删除**——唯一不可逆的一组动词——只在侧边栏和行内右键菜单里，⌘K 到不了（PV-07）。一个自称键盘优先的产品，把最需要确认、最需要鼠标停留的动作排除在键盘路径之外，是定位上的残缺，不是实现疏忽。

### 2.4 「诚实」 vs 「文案比事实更确定」

产品为自己立了一条很好的规矩（`docs/使用说明.md`：「标题说『什么失败了』，第二行说『为什么』，然后给一条能走的路」），并在多处严格执行（撤销的"没有可撤销的操作 / 已过期"区分、误删的兜底、防抖动的锁、hint 的分层）。但同一个产品里也有三处**文案比事实更确定**：

- 本地密钥故障 → 「邮箱设置不完整」（PV-01）——责任错配；
- 清空废纸篓 → 一个不是真实删除数的数字（PV-02）——不可逆操作的确认数不可信；
- AI 建议 → 「判断明确」，但可能是两周前的判断、且不显示来源（PV-14）——**在产品最核心的资产（AI 判断的可信度）上撒谎**。

**这三处的共同点是：它们都发生在"用户没法自己验证"的地方**——本地状态、服务器文件夹内容、建议的时间戳。越是用户看不见的真相，越是需要产品说实话。

## 3. 缺失的标准能力（在当前定位内）

按"单机 macOS + QQ 邮箱 + advisory-only AI"这个定位判断，以下是**在定位内、现在没有、但一个成熟用户会期待**的：

| 能力 | 现状 | 为什么在定位内 | 建议级别 |
|---|---|---|---|
| **稍后处理 / Snooze** | 无（PV-15） | "10 分钟清零"的另一半就是"明确推迟"；归档是可撤销但已经动过服务器的动作 | P2 必修 |
| **写信签名** | 无 | 产品已经能真发信（SMTP 465），签名是发信的地基；QQ 邮箱客户端默认都带落款 | P2 必修 |
| **快速回复 / 常用短语** | 无 | 一天几十封邮件，每封重打一遍是"10 分钟"最大的漏点 | P2 |
| **草稿箱入口 + 草稿索引** | 数据存了但没入口（PV-18） | 草稿已经是产品的一部分（有"已保存 ✓"和未保存拦截），没有索引就是半成品 | P2 必修 |
| **附件预览**（PDF / 图片直接看） | 只有下载（`MessageDetailView.swift:702-758`） | 收到发票 / 简历 / 合同附件时必须先存到本地再打开，这个来回足以毁掉一次 triage | P3 |
| **列表密度快捷键** | 无（PV-16） | 密度直接决定吞吐 | P3 |
| **可读性 / 字体大小** | 无 | macOS 邮件客户端的基线设置 | P3 |
| **"已发送"的搜索/过滤** | `/api/sent` 是只读列表，无游标 | 已发送是"我是不是漏回了谁"的唯一证据；它现在只能整页翻 | P3 |

**明确不算缺陷的**（避免被误当成需求）：多设备同步、多邮箱服务商（Gmail/Outlook OAuth）、手机端、S/MIME/PGP、对话式线程视图——这些超出当前定位，是非目标。
